## 2. 태스크 형식

```
### <ID> <제목>
- 날짜·시간: 11/5(목) · 3h        - 선행: 다른 태스크 ID
- 문서화(+0.25h, 공통 ⑦): 이 태스크가 남길 문서(10절)
- 모듈 문서 일괄 갱신(+0.5h, 공통 ⑦) · 대상: … · 코드를 바꿨다면: … · 모듈: …   ← 흐름별 그날 마지막 태스크에만
- 입력: 계약·픽스처·선행 산출물     - 산출물: 저장소 경로
- 완료 조건: 검사 가능한 항목(테스트 이름·명령·수치·증빙 파일)
- 근거: 기획서 절, 계약 문서
```

- ID: `흐름-날짜-순번`(예: `A-05-01` = A 흐름, 11/5, 1번). 통합은 `INT-07` 등. 발표 트랙은 `S-날짜-순번`(결정 대기 `P-xx`와 겹치지 않게 S).
- **하루 시간 예산**: 공통 1.5시간(스탠드업 0.25, 오후 5시 병합·전체 테스트 0.5, PR 리뷰 0.5, 증빙 정리 0.25) + 태스크 한도. A~D는 1인 9시간(태스크 **7.5시간 이하**), **E는 10.5시간(태스크 9시간 이하, P-22)**. 태스크 시간에는 "문서화(+Nh)"와 "모듈 문서 일괄 갱신(+Nh)" 시간이 더해진다. 날짜별 시간은 [team_plan 전체 시간표](../team_plan.md#전체-시간표)에 있고, `python -m tools.tasks_to_issues --hours`가 다시 계산한다. **발표 트랙(S)은 담당이 정해질 때까지(P-24) 흐름별 한도 계산에서 빼고 시간표에 별도 줄로 보인다.** 시간 배분 조정은 P-23.
- 각 태스크의 "완료 조건" 외에 아래 공통 완료 정의를 **모두** 만족해야 완료다.
- **단순 확인은 태스크로 따로 두지 않는다**(11/5 PM 결정): 자기 산출물(코드·문서·결정·설정·태그)이 없고 다른 태스크의 결과나 상태를 확인·기록만 하는 일은 관련 태스크(같은 흐름·같은 날)의 완료 조건 한 줄로 넣고 시간도 그 태스크에 더한다. 증빙 문서·트러블 기록은 자기 산출물로 치지 않는다. 예외(태스크로 유지): INT 통합 참여, `[검수]` 태스크(⑧·검수자 분리), 정식 사용자 테스트 당일 지원·수정(B-09-03 등. 후보 버전 리허설 1판 확인은 해당하지 않는다), 자체 스크립트·측정 도구를 만드는 시험, 결정을 문서에 반영하는 태스크, 조사 후 선택하는 태스크, 실행 작업(비용 차단 등), 발표 S 트랙.
- 저녁 입력 검수(team_plan 8절)는 공통 시간에 더하지 않는다. E-08-10·E-09-02·D-09-02 태스크 시간 안에서 한다.
- **인계 시각**: 같은 날 다른 흐름의 산출물을 받는 태스크는 "선행" 옆에 인계 시각을 적었다(예: `C-06-03(12:00)`). 인계하는 쪽은 그 시각까지 해당 조건만 먼저 병합하고, 받는 쪽은 그 전에는 픽스처·가짜 구현으로 진행한다. 인계 시각을 놓치면 스탠드업이 아니라 그 즉시 PM에게 알린다.
- 시간 초과: 태스크가 적힌 시간의 1.5배를 넘길 것 같으면 담당자가 체감으로 PM에게 알리고, PM이 11/11 수정 시간 또는 다른 흐름으로 재배치한다. 실제 소요 시간은 기록하지 않는다(11/5 PM 결정). 시간 추정은 11/5 실측(C-05-01, D-05-02)과 11/6 09:00 스탠드업의 흐름별 구두 보고로 한 번 다시 맞춘다(P-23).
- **확장 태스크**(제목 `[확장]`, 11/5 PM 결정으로 범위 축소): 여유 되면 하는 태스크다. 필수 태스크가 끝난 뒤에만 착수한다. ID와 이슈는 유지하고(라벨 `scope:extension`), 시간은 원래 흐름이 아니라 시간표의 `확장` 줄에 모아 흐름별 한도에서 뺀다. 일괄 갱신 줄의 대상이 아니며(끝낸 날 담당이 모듈 문서 `변경 이력`에 행을 직접 추가, 10절 규칙 2), 통합(INT) 판정 항목에도 넣지 않는다. 필수 태스크는 확장 태스크를 선행으로 갖지 않는다(`test_tasks_to_issues`가 검사). 프리셋은 5~8인(창귀 1명)이 필수, 9·11인(창귀 2명)이 확장이다.
- **담당 변경 절차**: 태스크 ID는 바꾸지 않는다. 태스크 첫 줄에 `담당 <흐름>(<날짜> PM 결정으로 담당 변경, ID 유지)`를 적고, GitHub 이슈 담당자는 `--assign` 동기화가 그 흐름의 로그인으로 덮어쓴다(11절). 받는 사람이 그 태스크의 검토자였으면 검토자도 다른 흐름으로 바꾼다. 인계 시각은 그대로다. 7절 결정 기록에 "담당 변경(<날짜> PM 결정)" 한 줄을 남기고, 이유·평가는 쓰지 않는다. 시간표(`hours_table`)는 흐름(ID) 기준이라 옮긴 시간은 원래 흐름 행에 남는다(team_plan 전체 시간표 각주).
- **사전 작업**(예정일 전에 로컬에서 미리 하는 작업): 결과는 "로컬 사전 구현"으로 보고하고 태스크는 미완으로 둔다. PR 병합과 필수 체크 통과(3절 ①②⑧)까지 끝나야 완료다. 모듈 문서 `변경 이력` 날짜는 태스크 예정일을 쓴다(10절). 사전 작업을 여러 개 병행하면 새 테스트 파일 이름을 작업마다 나눠 같은 파일을 동시에 고치지 않고, PM 세션이 브랜치를 하나씩 순서대로 통합 브랜치 `dev`에 병합한 뒤 최신 태스크 문서 기준으로 전체 테스트를 다시 돌린다.

| ⑦ | **문서화**: 태스크의 "문서화" 줄에 적힌 문서를 10절 기준대로 남긴다(트러블 기록, docstring, 계약 문서, 라우팅 문서). 모듈 문서는 흐름별로 **그날 마지막 태스크**의 "모듈 문서 일괄 갱신" 줄에서 한 번에 갱신한다. "문서화(+Nh)"와 "일괄 갱신(+Nh)"이 그 시간이다 | `check_docs --task <ID>`(`--complete`에 포함)와 `check_docs --diff`(CI `docs` 체크) |
| ⑧ | **PR 승인**: 작성자가 아닌 팀원 1명이 GitHub에서 승인(Approve)한다. 리뷰 시간은 공통 시간의 "PR 리뷰 0.5h"다. 승인 뒤 수정 커밋을 올려도 기존 승인은 유지된다(재승인 부담을 줄이려고 "새 푸시 시 승인 무효화"는 끈다)<br>저장소 배정 전: 10-1절 임시 대체(다른 흐름의 검토 기록 + 원장) | `dev`·`main` 보호 규칙(승인 1명 필수, 관리자도 우회 불가)이 승인 없는 병합을 막는다(E-05-01) |

- **브랜치 모델**(11/5 PM 결정, 저장소 배정 때):
  - `dev`는 통합 브랜치이고 GitHub 기본 브랜치다. 태스크 브랜치 `task/<ID>`는 `dev`에서 따고, 모든 태스크 PR은 `dev`를 대상으로 연다. ①②⑧과 11절 규칙은 `dev` 대상 PR 기준이다. 이슈를 닫는 `Closes #`도 기본 브랜치인 `dev`에 병합될 때 동작한다.
  - `main`은 배포 브랜치다. 안정 시점에만 PM이 `dev` → `main` 승격 PR을 연다: **최종 배포 전**(시연 전, 사용자가 시점을 정한다). 사용자 테스트(11/10) 전에는 승격하지 않는다(11/8 사용자 결정). 승격 전 `dev`에서 전체 테스트·`check_docs --all --until <오늘>`이 통과해야 하고, 승격 PR도 `precheck` 통과 줄과 작성자가 아닌 1명의 승인을 받는다. 승격 PR은 태스크 PR이 아니어서 `Task:` 줄이 없고, `dev`에서 `python -m tools.precheck --base origin/main`(비교 기준을 `main`으로)으로 바뀐 증빙의 형식만 본다(11절).
  - 병합 규칙은 `dev`·`main` 둘 다 같다: PR 필수, PR 본문의 `precheck: 통과` 줄(②), 작성자 외 승인 1명, 직접 푸시·강제 푸시 금지. 저장소가 비공개·무료 플랜이라 GitHub 보호 규칙으로 강제할 수 없으므로(P-11, 11/5) **병합 버튼은 PM만 누르고, 누르기 전에 승인 1명과 `precheck` 통과 줄을 PR 화면에서 확인한다**. 팀원은 `dev`·`main`에 직접 푸시하지 않는다. `main`에는 `dev`에서 온 승격 PR만 병합한다(급한 수정도 `dev`를 거친다).
  - 시연 환경은 `main`의 커밋으로 띄운다. 11/10 사용자 테스트 환경은 11/10 09:00 배포한 후보 커밋으로 띄우고, E-08-04 리허설을 통과하면 그 커밋에 태그(`v-usertest-1`)를 만든다(11/8 사용자 결정, [`user_test/plan.md`](../user_test/plan.md) 1절). 그 밖의 통합(INT)·일일 확인은 `dev` 기준이다.
  - **dev 받는 시점**(11/6 PM 결정 P-26): 태스크 브랜치는 `dev`가 바뀔 때마다 받지 않는다. 기본 시점은 둘이다. (1) 시작할 때 `git fetch origin` 후 최신 `origin/dev`에서 브랜치를 딴다. (2) PR을 올리기 직전에 `git fetch origin` → `git merge origin/dev`로 받는다. PR을 연 뒤에는 충돌(PM이 PR에 알림)·검사 실패·필요한 선행 변경이 있을 때만 다시 받는다. 받은 뒤에는 충돌 해결까지 커밋하고 `python -m tools.precheck --pr-body <PR 본문 파일>`(에셋 관련 변경이면 `--with-assets`)을 기본 base로 다시 돌려 PR 본문의 `precheck: 통과` 줄을 바꾼다. 이전 검사의 base SHA를 고정해 다시 쓰지 않는다. 리베이스·강제 푸시는 하지 않는다. ⑧ 승인은 새 푸시 뒤에도 유지되지만, 충돌 해결로 동작·계약·증빙의 의미가 바뀌면 승인자에게 알리고 확인받는다. 충돌은 PR 작성자가 자기 브랜치에서 풀고, 다른 흐름 담당 파일이면 그 담당자에게 확인한다. dev를 받은 뒤 전에 통과하던 검사가 실패하면(예: 필요한 README 변경이 이미 dev에 있어 10절 규칙 6에 걸림) 의미 없는 수정으로 통과시키지 말고 PM에게 알린다. `git push` 때 자동 검사는 훅을 설치해야 돌고(`git config core.hooksPath .githooks`), PR 본문 검사는 하지 않는다.
  - **여럿이 고치는 파일**(`paldo/README.md`, `docs/tasks/README.md`, `docs/contracts/structure.md`, P-26): 루트 `README.md`에는 새 최상위 폴더와 공용 항목만 넣고, 영역 안의 폴더·작업 행은 그 영역 문서 `docs/routing/<흐름>.md`에 넣는다(P-27). 표에 행을 넣을 때는 기존 분류와 순서를 지켜 관련 항목 근처에 넣는다. 표 끝에 덧붙이거나 표 전체를 재정렬하거나 서식을 바꾸지 않는다. 태스크와 무관한 정리는 태스크 PR에 섞지 않고 PM에게 알린다. 태스크에 필요한 계약·라우팅·구조 문서 변경(10절 규칙 6: 새 최상위 폴더의 루트 README, 두 번째 단계 새 폴더의 영역 문서, 계약 파일의 `docs/contracts/`, 새 폴더의 `structure.md` 6절)은 같은 PR에 둔다. 텍스트 충돌이 없어도 생기는 의미 충돌은 PM이 오후 5시 병합·전체 테스트에서 확인한다.
- 가짜 구현으로 통과한 것은 "착수 완료"다. 진짜로 교체해 계약 테스트를 다시 통과해야 완료로 센다(`docs/contracts/parallel_dev.md` 3절).
- 조건을 만족하지 못하면 완료 처리하지 않는다. 대신 증빙 맨 위에 `상태: 실패`와 원인·재시도 계획을 남겨 병합할 수 있다(형식 검사 `--format`만 통과). 이 문서는 **완료 검사 `--complete`를 통과하지 못한다.** 스탠드업에서 PM이 재배치를 정한다.
- **막는 결함(`blocker` 라벨)**: 시연 장면(S-10-01의 4개)·끝에서 끝까지 흐름 2개·INT 항목을 막는 결함이다. `blocker` 이슈는 "보류"로 닫을 수 없다. 보류는 `blocker`가 아닌 이슈에만 허용한다. 라벨은 이슈를 연 사람이 붙이고, 애매하면 `blocker`로 둔다.
- **사람 판단 조건**: 의미 보존, 말투, 이미지 유사성, 해설의 인과 같은 조건은 자동 검사로 보장할 수 없다. 이런 조건은 **다른 흐름 담당자 1명이 검수자**가 되어 기준표·검수한 샘플 ID·판정을 증빙의 "검수" 절에 남긴다. 자동 검사는 그 기록이 있는지만 확인한다. 검수자는 결과물 작성자와 다른 사람이어야 한다(PM이 아니어도 된다). 검수자와 작성자는 흐름 ID(A~E, 발표 트랙은 S)로 적고, 검수자 흐름이 증빙의 `작성자(흐름)`과 다르면 통과다(4절 규칙 5). 검수(기준표에 따른 판정 기록)는 PR 승인(⑧, 변경 전체 리뷰)과 별개이고, 같은 사람이 둘 다 해도 된다.
- **에셋 검수는 한 번에 한다**(11/4 PM 결정): 이미지 에셋은 개별 `[에셋]` 태스크에서 검수하지 않는다. 11/11 E-11-10에서 검수자 E(실제 에셋 작성자 D와 다른 사람. 11/5 PM 결정으로 이 검수를 E 태스크로 옮겼고, 같은 날 실제 에셋 제작을 B에서 A 흐름으로 옮겼다. 담당 변경으로 A 흐름 `[에셋]` 태스크는 D가 맡는다. 증빙의 `작성자(흐름)`에는 결과물 작성 흐름 A를 적는다. 탈락분 재생성은 D가 A-11-01 안에서)가 모든 실제 파일의 에셋1(스타일 가이드 준수)·에셋5(체크리스트)와 아이콘의 작은 크기 구분을 한 번에 판정한다. 개별 에셋 태스크는 자동 검사 조건(에셋2~4)으로 완료한다. 예외: 스타일 가이드 문서 자체는 11/5 E-05-05에서 검토한다(일괄 검수의 기준이므로, 작성자 E). 11/6 PM 결정으로 B 검수 대신 Claude 검토(PM 지시)와 Codex 교차검토로 했다(7절). 품질 문제가 11/11에야 드러나는 위험은 받아들였다.

**결과 JSON 형식**(측정 스크립트가 남기는 파일, 11/4 PM 결정)
- 위치: `docs/evidence/perf/<ID>/<이름>.json`. 한 태스크에 여러 파일을 둘 수 있다.
- 기록: 측정 스크립트는 `tools/evidence_result.py`의 `write_result(task, name, metrics, source)`로만 쓴다(E-05-02). `commit`(측정 시점 `HEAD`)과 `generated_at`은 이 함수가 채운다.
```json
{
  "task": "B-06-02",
  "commit": "<측정한 커밋 SHA>",
  "generated_at": "2026-11-06T09:12:00Z",
  "source": "python -m tools.perf.api_latency --seed 1",
  "metrics": {
    "api_p95": {"value": 412.3, "unit": "ms"},
    "error_count": {"value": 0, "unit": "건"}
  }
}
```
- `task`는 증빙 ID와 같다. `metrics`의 키는 영문 소문자·숫자·`_`. `value`는 숫자(정수 또는 소수)만. `unit`은 문자열이고 단위가 없는 값(비율 0~1 등)은 `""`.

**수치 표 작성 규칙**
- **측정값이 여러 개면 행을 나눈다.** 한 행 = 측정값 1개. 같은 조건 번호가 여러 행에 나와도 된다.
- **결과 파일 칸**: `<결과 JSON 경로>#<metrics 키>`(예: `docs/evidence/perf/B-06-02/api.json#api_p95`). 수치가 아닌 조건(테스트 통과, 파일 존재, 검수 기록 등)은 `-`.
- **기준 칸**: 수치 조건은 `<연산자> <수> <단위>` 또는 `<수>~<수> <단위>`. 연산자는 `<=`, `<`, `>=`, `>`, `==`. 범위 `a~b`는 양 끝을 포함한다. 단위가 없는 값은 단위를 생략한다. 예: `<= 1000 ms`, `40~60 %`, `== 0 건`, `<= 0.05`. 수치가 아닌 조건은 `-`.
- **측정값 칸**: `<수> <단위>`. 단위는 기준 칸·JSON `unit`과 **글자까지 같아야** 한다. 단위 환산은 하지 않는다(초와 ms를 섞으면 실패).
- 기준 칸이 수치 문법이면 결과 파일 칸은 `-`일 수 없다(④: 수치는 계측값만). 기준 칸이 `-`이면 결과 파일 칸도 `-`이고 측정값 칸은 자유 서술이다.
- **대조**: JSON `value`를 측정값 칸에 적힌 소수 자릿수로 반올림(사사오입, `decimal.ROUND_HALF_UP`)한 값이 측정값 칸과 같아야 한다(예: `412.3` → 칸에 `412 ms`라고 쓰면 일치, `413 ms`면 불일치).
- **판정**: 기준과의 비교는 반올림하지 않은 JSON `value`로 다시 계산한다. 결과("예"/"아니오")가 통과 칸과 다르면 실패.

**`check_evidence --format` 검사**: 양식 제목이 모두 있고(`## 검수`는 `[검수]` 태스크만 요구), `- 작성자(흐름):` 값이 A~E 또는 S다. `--complete`도 이 검사를 포함한다. `- 실제 소요 시간(h):` 줄은 11/5 PM 결정으로 폐지해 보지 않는다(기존 증빙에 남은 줄은 그대로 둔다).

**`check_evidence --complete` 검사 규칙**(E-05-02가 구현)
1. 태스크 문서(`docs/tasks/*.md`)에서 그 ID의 완료 조건 번호 목록을 읽어, 증빙 "수치" 표에 번호가 모두 있는지 본다.
2. 모든 행의 통과 칸이 "예"이고 `상태: 실패`가 없다.
3. 결과 파일 칸이 `-`가 아닌 행은 위 "수치 표 작성 규칙"대로 검사한다: 파일과 키가 있고, JSON `task`가 증빙 ID와 같고, 단위가 일치하고, 측정값이 반올림 규칙으로 JSON 값과 같으며, 다시 계산한 판정이 통과 칸과 같다. 기준 칸이 수치 문법인데 결과 파일이 `-`이거나 기준 칸을 해석할 수 없으면 실패.
4. 커밋 SHA(증빙의 `- 커밋:`과 결과 JSON의 `commit`)가 저장소에 있다.
5. 사람 판단 조건이 있는 태스크(문서 제목에 `[검수]` 표시)는 "검수" 표가 있고, 모든 행의 검수자 흐름이 `- 작성자(흐름):` 값과 다르다. `[검수]`가 아닌 태스크는 검수 절을 보지 않는다.
6. 문서화 검사 `check_docs --task <ID>`(10절 검사 규칙 1~3)가 통과한다. (`check_evidence`는 `check_docs`를 부르지만, `check_docs`는 `check_evidence`를 부르지 않는다. 10절 "완료된 태스크")

## 5. 로그·계측 규칙

**로그(모든 서비스·배치·스크립트)**
- 형식: JSON 한 줄. 표준 출력 + 파일(`/var/log/paldo/<서비스>.jsonl`, 로컬은 `out/logs/`). 보존 7일.
- 필수 필드: `ts`(UTC ISO8601), `level`, `service`, `component`, `msg`.
- 해당하면 반드시 넣는 필드: `request_id`(HTTP 요청마다 발급, 응답 헤더 `X-Request-ID`), `game_id`, `command_id`, `event_id`, `attempt_id`, `job_id`, `serve_id`, `charge_id`, `model_version`, `duration_ms`.
- 원문 자유 입력·설문 의견은 로그에 넣지 않는다(마스킹된 원문은 이벤트에만. `docs/contracts/privacy.md`).
- 오류는 `level=error`와 `error_type`을 넣는다. 예외를 삼키는 코드는 반드시 `warning` 이상 로그를 남긴다.

**계측(Prometheus)**
- 이름: `paldo_<구성요소>_<측정>_<단위>`(예: `paldo_http_request_duration_seconds`, `paldo_llm_render_duration_seconds`, `paldo_ad_serve_total`).
- 지연은 히스토그램(라벨: `route` 또는 `stage`, `status`). p50·p95는 Grafana에서 `histogram_quantile`로 계산한다.
- 서비스마다 `/metrics` 엔드포인트. 배치·스크립트는 Pushgateway 또는 실행 후 결과 JSON을 남긴다. 증빙에 쓰는 결과는 4절 "결과 JSON 형식"대로 `docs/evidence/perf/<ID>/`에 커밋한다(그 밖의 실행 결과는 `out/perf/`, 커밋하지 않음).
- 측정 스크립트는 `tools/perf/`에 두고, 같은 명령으로 다시 돌릴 수 있어야 한다(시드·입력 고정).

2. 집계 기준·원본 대조 부족 → C-08-02의 집계 정의서와 건별 대사, INT-11 대조

## 10. 문서화 기준 (공통 ⑦)

모든 태스크는 "문서화(+Nh)" 줄에 적힌 문서를 남긴다. 문서마다 역할이 다르다. 같은 내용을 두 곳에 쓰지 않고 링크한다.

**가볍게 쓰는 기준(P-22, 11/5 PM 결정)**

| 태스크 종류 | 태스크마다 쓰는 것 | 시간 |
|---|---|---|
| 구현 태스크(2h 이상) | 트러블 기록, 공개 함수·클래스 docstring, (새 폴더면) 라우팅 문서 | +0.25h |
| 짧은 태스크(2h 미만)·가벼운 태스크(점검·참여·운영·주관·리허설) | **트러블 기록만**("트러블만" 표시). docstring은 코드를 바꿨을 때 CI가 검사 | +0h(그날 일괄 갱신 시간에 포함) |
| 문서 산출 태스크(발표·리포트) | 산출물 자체 + 트러블 항목("없음"이어도 둔다) | +0h |
| **그날 마지막 태스크**(흐름별) | 위에 더해 "모듈 문서 일괄 갱신" 줄: 그날 그 흐름의 태스크가 쓴 모듈 문서를 한 번에 갱신 | 대상이 있으면 +0.5h, "코드를 바꿨다면" 대상만 있으면 +0.25h |

일괄 갱신 줄 형식(파서 `tools/tasks_md.py`가 읽는다): `- 모듈 문서 일괄 갱신(+0.5h, 공통 ⑦) · 대상: <ID, …> · 코드를 바꿨다면: <ID, …> · 모듈: <모듈 문서 링크, …> · 할 일: …`. "대상"은 구현 태스크(그날 모듈 코드를 반드시 바꾸는 태스크), "코드를 바꿨다면"은 가벼운 태스크다.

| 문서 | 위치 | 역할 | 누가 |
|---|---|---|---|
| 모듈 문서 | `docs/modules/<모듈>.md` | 그 모듈이 **무엇을, 왜** 하고 **어떻게 쓰는지**. 코드를 처음 보는 사람이 읽는 설명서 | 흐름별 그날 마지막 태스크(일괄 갱신) |
| 트러블 기록 | `docs/troubles/<흐름>.md` | 문제 → 원인 → 대응 → 결과 수치. 발표의 담당자별 트러블 슬라이드 재료 | 모든 태스크(없으면 "없음") |
| 계약 문서 | `docs/contracts/*.md` | 흐름 사이의 약속(타입·API·이벤트). 바뀌면 다른 흐름이 영향받는다 | 계약 파일을 바꾼 태스크 |
| 증빙 문서 | `docs/evidence/<ID>.md` | 이 태스크가 조건을 만족했다는 기록(명령·출력·수치). 설명은 쓰지 않는다 | 모든 태스크 |
| 라우팅 문서 | 1단 `paldo/README.md`(영역 안내, 공용 폴더·작업), 2단 `docs/routing/<흐름>.md`(영역별 폴더·작업, P-27) | 무엇을 하려면 어디를 보라. **위치와 역할만** 적고 상세는 모듈 문서로 넘긴다. 영역 문서는 그 흐름이 관리하고, 다른 흐름도 자기 작업 행은 직접 넣는다(관리 흐름이 PR에서 확인) | 새 폴더를 만든 태스크 |
| docstring | 코드 | 공개 함수·클래스의 한 줄 요약(+ 인자·반환이 자명하지 않으면 설명) | 공개 함수·클래스를 만들거나 바꾼 태스크 |
| 발표·리포트 | `docs/presentation/`, `docs/reports/` | 산출물 자체가 문서인 태스크(문서화 +0h) | 해당 태스크 |

**발표 트랙(S)**: 모듈 문서와 일괄 갱신 줄이 없다. 문서 산출 태스크(구성안, 구간 자료, 발표 자료)는 "산출물 자체가 문서다"(규칙 3), 나머지(이미지, 시연 영상, 리허설)는 "트러블만"(`docs/troubles/S.md`, 규칙 1).

**모듈 목록**(`docs/modules/`): `engine`, `sim`, `web`, `infra`, `pipeline`, `ops`, `aws`, `ml_ops`, `privacy`, `intent`, `ml`, `ads`, `content`, `llm`, `assets`, `user_test`, `ci`, `perf`, `project`. 새 모듈이 필요하면 이 목록과 `docs/modules/README.md`에 추가한다.

**모듈 문서 필수 절**(이 제목 그대로, 이 순서): `## 무엇을`, `## 왜`(설계 근거와 기획서 절), `## 사용법`(실행 명령), `## 설정값`(환경 변수·파라미터·기본값), `## 한계`, `## 변경 이력`(표: `| 태스크 | 날짜 | 바뀐 점 |`). 양식은 [`docs/modules/_template.md`](../modules/_template.md).

**트러블 기록 형식**(`docs/troubles/<흐름>.md`): 태스크마다 `### <ID> <제목>` 아래 `- 문제:`, `- 원인:`, `- 대응:`, `- 결과:`(수치 + 증빙 링크) 4줄. 트러블이 없으면 `- 없음` 한 줄. 양식은 [`docs/troubles/_template.md`](../troubles/_template.md).

**`변경 이력`의 날짜**: 태스크 문서에 적힌 **예정일**(태스크 ID의 날짜, 예: `E-05-05` → `11/5`)을 쓴다. 사전 작업 등으로 실제 작업일이 다르면 실제 일자는 증빙(커밋 SHA)에 남는다. 검사 규칙 2의 "그날 날짜"도 예정일이다.

**완료된 태스크**(`check_docs`가 쓰는 정의): `docs/evidence/<ID>.md`가 있고, `상태: 실패`가 없으며, "수치" 표의 통과 칸이 모두 "예"인 태스크. `check_docs`는 이 판정을 직접 하고 `check_evidence --complete`를 부르지 않는다(`--complete`가 `check_docs --task`를 부르므로 순환을 막는다). GitHub 이슈 상태는 보지 않는다(로컬에서 같은 결과가 나와야 한다).

**검사 규칙**(`tools/check_docs.py`, E-05-02가 구현. 태스크 정보는 `tools/tasks_md.py`로 읽는다)
1. `--task <ID>`(모든 태스크): `docs/troubles/<흐름>.md`에 `### <ID>` 항목이 있고 4줄 형식이거나 `- 없음`이다. 증빙 문서의 "트러블" 절이 그 항목을 링크한다.
2. `--task <ID>`(일괄 갱신 줄이 있는 태스크 = 그날 흐름의 마지막 태스크): 줄의 "모듈"에 적힌 모듈 문서마다 필수 절 6개가 순서대로 있다. `변경 이력` 표에 "대상" 태스크마다 `| <ID> | <그날 날짜> |` 행이 있다. "코드를 바꿨다면" 태스크는 그 태스크 증빙의 커밋이 모듈 코드(모듈 → 코드 대응은 `docs/modules/README.md` 표)를 바꿨을 때만 행을 요구한다. 대상 태스크 중 아직 "완료된 태스크"(위 정의)가 아닌 것(밀린 태스크)은 이 검사에서 빼고, 태스크 문서의 대상은 옮기지 않는다. 그 태스크가 끝난 날 그 흐름 담당이 모듈 문서 `변경 이력`에 행만 추가한다(규칙 4가 누락을 잡는다, 11/5 PM 결정). `[확장]` 태스크는 처음부터 일괄 갱신 대상에 넣지 않고 같은 방식으로 끝낸 날 행을 추가한다. 그래서 그날 마지막 태스크의 이슈는 일괄 갱신까지 끝나야 닫힌다.
3. `--task <ID>`: 문서 산출 태스크(문서화 +0h, "산출물 자체가 문서다")는 태스크의 `산출물:` 줄에 적힌 파일이 있다. 태스크에 `- 필수 제목:` 줄(제목 문자열을 백틱으로 나열)이 있으면 그 제목이 파일에 모두 있어야 한다. 이 줄이 없으면 파일 존재만 본다(11/4 PM 결정: 기계가 읽을 형식이 없던 "구간 제목"을 이 줄로 대체).
4. `--all --until <날짜>`: 예정일이 그 날짜까지인 태스크 중 "완료된 태스크"(위 정의)이면서 일괄 갱신 "대상"에 든 태스크마다 어느 모듈 문서의 `변경 이력`에든 그 ID 행이 있다(일괄 갱신에서 빠진 태스크를 잡는다).
5. `--diff <base>`: 변경된 `.py`의 공개 함수·클래스(이름이 `_`로 시작하지 않는 최상위 정의와 공개 클래스의 공개 메서드)에 docstring이 있다(`ast`로 검사. `tests/`와 마이그레이션 제외).
6. `--diff <base>`: 계약 파일(`engine/domain/{model,events,serde,content}.py`, `engine/ports.py`, `server/app/dto.py`, `server/app/ads_port.py`, `server/api/viewmodels.py`, `ads/domain/*.py`, `contracts/datasets.py`)이 바뀌면 `docs/contracts/` 아래 문서도 같은 PR에서 바뀐다. 최상위 새 폴더가 생기면 루트 `paldo/README.md`가, 두 번째 단계 새 폴더가 생기면 루트 README 또는 영역 문서 `docs/routing/<A~E>.md` 중 하나가 같은 PR에서 바뀐다(P-27. 삭제는 변경으로 치지 않는다). 깊이 1·2 새 폴더에 라우팅 문서 변경이 있는지만 보고, 어느 영역 문서인지·안내 내용이 맞는지·세 번째 단계 이하와 기존 파일 이동·삭제는 리뷰에서 본다.

통합 태스크(INT-xx)에는 검사 규칙 1~4를 적용하지 않는다(11/4 PM 결정). INT-xx의 문서는 판정 결과(`docs/evidence/INT-xx.md`)이고, 미통과 항목의 원인은 담당 흐름의 트러블 기록에 남긴다. 시간은 주관 태스크(E-07-03, E-09-04, E-11-01)에 들어 있다.

## 10-1. 저장소 배정 전 임시 운영 (11/5 PM 결정)

**종료(11/5)**: 교육기관 저장소(`encore-ai-campus/mlo-01-p4-team3`)가 11/5에 배정되어 아래 "전환"을 마쳤다. 이 절의 NAS 번들 제출·원장·진행표 규칙은 **기록으로만 남기고 더는 쓰지 않는다.** 이후는 3절·11절 규칙만 쓴다.

**기간**: 시작 커밋 `02a6de1`부터 교육기관 저장소 배정(P-11) 후 아래 "전환" 6단계까지. 그 뒤로는 3절·11절 원래 규칙만 쓴다. GitHub가 있어야만 끝나는 조건은 태스크 문서에 **(저장소 배정 후)** 표시가 있고, 배정 전에는 판정하지 않는다(그 태스크는 진행표에서 `병합됨`으로 남는다).

**원칙**: NAS는 파일 공유만 한다(NAS에서 git 작업 안 함). git은 각자 노트북에서만 쓴다. 흐름(A~E, S)마다 따로 제출하고, **병합·통합 테스트는 PM만** 한다. 주고받는 형식은 git 번들(`git bundle`) 파일이다. 도구는 `python -m tools.interim`(설명 [ci 모듈 문서](../modules/ci.md)). 팀원용 순서는 [팀원 안내서](../ops/interim_guide.md).

**1. 공유 폴더**(경로·계정은 PM이 따로 알려 준다. 저장소·문서에 적지 않는다)

| 폴더 | 쓰는 사람 | 내용 |
|---|---|---|
| `inbox/<흐름>/` | 그 흐름만 | 제출 번들 `<ID>_<NN>_<HEAD SHA 12자>.bundle`과 같은 이름의 `.ci.txt` |
| `main/` | PM만 | main 번들 `main_<MMDD>_<HHMM>_<SHA12>.bundle`, 진행표 `status_<MMDD>_<HHMM>.md` |
| `review/<흐름>/` | 검토하는 흐름 | 검토 기록 `<ID>_<NN>.review.txt` |

- 한 폴더에는 한 사람만 쓴다. NAS로 복사할 때는 `<이름>.part`로 복사를 끝낸 뒤 이름을 바꾼다(`.part`는 도구가 읽지 않는다).
- 처음 받기: `git clone -b main <main 번들>`. 이후 새 main 번들이 올라오면 `git fetch <main 번들> main` 뒤 `git merge --ff-only FETCH_HEAD`(main에서). 번들 이름의 SHA12가 다음 제출의 base다.

**2. 제출**(각 흐름)
1. 받은 main에서 `task/<ID>` 브랜치를 만들어 작업하고 **전부 커밋**한다.
2. `python -m tools.interim submit --task <ID> --base <받은 main SHA> [--complete] [--kind fix]`
   - 커밋하지 않은 변경·추적 안 된 파일이 있으면 거부한다.
   - HEAD를 임시 `git worktree`로 꺼내 로컬 CI(아래 3)를 돌고 작업 트리를 지운다.
   - 통과하면 `out/interim/`(또는 `--out`)에 base..`task/<ID>` 번들을 만들고 `git bundle verify`, 같은 이름의 `.ci.txt`(단계별 결과, 대상·base SHA, 시각, Python 버전, 번들 SHA-256)를 쓴다.
3. 두 파일을 `inbox/<흐름>/`에 `.part`로 복사한 뒤 이름을 바꾼다.
4. 다시 제출하면 번호(`NN`)가 하나 오른다(출력 폴더와 `--seen <공유 폴더의 자기 inbox>`의 최대 번호 + 1). 이전 번들은 지우지 않고, **가장 큰 번호만 유효**하다. 강제 푸시에 해당하는 일은 없다.
- PR 본문 대신 제출 인자가 정보를 준다: 태스크 ID(`--task`), 완료 제출(`--complete`, PR의 `Closes`), 수정 제출(`--kind fix`, `fix` PR·라벨 대신).

**3. 로컬 CI**(`python -m tools.interim ci --base <SHA>`, 커밋된 커밋만 검사. CI 4체크 대체, 3절 ②)

| 단계 | 내용 |
|---|---|
| core | `python -m unittest discover -s tests -t .`, `check_secrets`, `check_structure --diff <base>`(새 폴더가 `docs/contracts/structure.md` 6절 허용 목록 안) |
| docs | `check_docs --diff <base>`(규칙 5·6) |
| evidence | `--complete`면 `check_evidence <ID> --complete`, 아니면 바뀐 증빙 `--format`. base 이후 커밋 메시지의 닫기 키워드 금지(11절) |
| service | `PALDO_SERVICE_TESTS=1`이면 `tests/infra`·`tests/ads`·`server/manage.py test`. `server/`·`ads/`·`tests/infra/`·`tests/ads/`를 바꿨는데 서비스 테스트를 안 돌렸으면 **실패**(Compose를 띄우고 다시) |

**4. PM 병합**(PM 노트북의 `main`)
1. `python -m tools.interim intake <번들>`: 이름·`.ci.txt` 통과·SHA-256·`git bundle verify`·대상 SHA를 임시 참조에서 확인한 뒤에만 `refs/inbox/<ID>/<NN>`을 만든다(같은 번호를 다른 커밋으로 덮어쓰지 않는다).
2. 선행·인계 순서대로 `python -m tools.interim merge --task <ID> --number <NN> [--complete]`: `--no-ff` 병합(메시지 `Task: <ID> (제출 <NN>)`, 닫기 키워드 없음. 받아 둔 더 큰 번호가 있으면 거부) 후 병합 결과를 base = 병합 전 SHA로 로컬 CI를 다시 돈다(충돌 해결분도 검사된다). 충돌이면 도구가 멈추고, 해결·커밋 뒤 `interim ci --base <병합 전 SHA>`로 검사한다.
3. 재검사 실패면 PM만 `git reset --hard <병합 전 SHA>`로 되돌린다. **위험**: 이미 main 번들로 공개한 커밋을 되돌리면 팀원 저장소와 갈라진다. 그래서 공개 전(같은 날 마감 전)에만 쓰고, 공개 뒤에는 되돌림 커밋(`git revert -m 1`)을 쓴다.
4. 일 마감: `python -m tools.interim publish --out <main 폴더> --until <오늘> --inbox <inbox 폴더>`가 unittest·`check_secrets`·`check_docs --all`·원장 검사를 통과해야 main 번들과 진행표를 쓴다(공유 폴더에 `.part`로 쓴 뒤 이름을 바꾼다).

**5. ⑧(PR 승인) 대체**
- 검토자는 **작성 흐름과 다른 흐름**이다. `반려`면 병합하지 않고 재제출을 받는다(원장의 병합 행은 판정 `통과`만). 받은 번들을 `git fetch <번들> task/<ID>`로 보고, `review/<검토 흐름>/<ID>_<NN>.review.txt`에 검토 흐름, 확인한 HEAD SHA(40자), 판정(`통과`/`반려`), 메모를 쓴다.
- PM은 병합 뒤 [`docs/ops/interim_ledger.md`](../ops/interim_ledger.md) 원장에 한 행을 더한다(칸: 태스크, 작성 흐름, 제출 번호, 제출 HEAD SHA, 검토 흐름, 검토 SHA, 판정, 병합 SHA, 로컬 CI).
- `python -m tools.interim check-ledger`: 검토 흐름 ≠ 증빙 `작성자(흐름)`, 검토 SHA = 제출 HEAD, 병합 SHA가 main에 포함되고 부모에 제출 HEAD가 있음, 로컬 CI `통과`. `[검수]` 태스크의 4절 규칙 5는 그대로 따로 적용한다.

**6. 진행표**(`python -m tools.interim status --until <날짜> [--inbox <폴더>]`, PM 감독 방법 3절의 대체)

| 상태 | 판정 |
|---|---|
| 완료 | `check_evidence --complete` 통과 + 원장 행 검사 통과(병합 SHA가 main에 있음, 검토 `통과`) |
| 병합됨 | 원장의 병합 SHA가 main에 있으나 완료가 아님 |
| 제출됨 | inbox에 번들만 있음 |
| 실패 | 증빙에 `상태: 실패` |
| 미착수 | 위 어디에도 없음 |

**GitHub 기능의 임시 대체**

| 원래(배정 후) | 배정 전 |
|---|---|
| PR 병합(①) | 원장 행 + 병합 SHA가 main에 포함 |
| Actions 4체크(②) | 제출·병합 때 로컬 CI 통과(`.ci.txt`, 원장 로컬 CI 칸) |
| PR 승인(⑧) | 다른 흐름의 검토 기록 + 원장(위 5) |
| `fix` PR·라벨 | `--kind fix` 제출(병합 메시지 `, fix`) |
| `bug` 이슈 | 원장 "결함" 절 표(ID, 영역, 내용, 상태, 보류 사유) |
| 이슈 닫힘 | 진행표 `완료` |

**원장 보존**: 원장은 저장소 안 문서라 배정 후에도 지우거나 고치지 않는다(행 추가만). 병합 SHA는 이력 재작성이 없으므로 원격에서도 그대로 유효하다.

**전환**(배정 받은 날, PM)
1. 제출을 멈춘다(공유 폴더에 공지).
2. 전환 SHA를 정하고 그 SHA에서 전체 로컬 CI(`interim ci --base <시작 SHA>`), `check_docs --all --until <오늘>`, `check-ledger`를 통과시킨다.
3. `main`을 원격에 푸시하고 곧바로 보호 규칙(3절 ⑧, E-05-01 1번)을 건다. 저장소 플랜 때문에 걸 수 없으면 3절의 운영 규칙(PM만 병합, 병합 전 승인·체크 확인)을 공지한다(11/5 P-11).
4. `python -m tools.tasks_to_issues --apply --repo <OWNER/NAME>`(E-05-01 4번).
5. 진행표 `완료` 태스크의 이슈는 원장 행과 병합 SHA를 코멘트로 남기고 닫는다. **11절 "이슈를 손으로 닫지 않는다"의 명시적 예외**이고, INT-11 #11 대조에서는 원장 행이 있는 이슈를 손으로 닫힌 이슈로 세지 않는다.
6. 이후는 원래 규칙(PR·Actions·승인). 진행 중이던 `task/<ID>` 브랜치는 원격에 푸시해 PR로 낸다.
7. 이력은 재작성하지 않는다(원장의 병합 SHA가 원격에서도 그대로 유효해야 한다).

**전환 기록(11/5)**: 저장소 배정 당일 NAS 제출 전에 전환했다. 전환 SHA `1a9df42`. 원격의 통합 브랜치 `dev`(기본 브랜치)를 이 SHA로 올리고, 배포 브랜치 `main`도 같은 SHA에서 시작한다(3절 브랜치 모델). 원장에 병합된 제출이 없어 5단계(이슈 닫기)는 해당 없음.

## 11. GitHub Issues로 관리하기

**원본 원칙**: 태스크 정의(할 일, 완료 조건, 시간, 선행)의 원본은 **이 저장소의 마크다운**이다. 조건을 바꾸려면 마크다운을 고치는 PR을 낸다(계약 변경과 같은 승인 규칙). GitHub Issues는 **진행 관리**(담당자, 상태, 토론, 막힌 것)에 쓴다. 이슈 본문은 `tools/tasks_to_issues.py`가 마크다운에서 만들므로 이슈 본문을 직접 고치지 않는다(다음 동기화 때 덮어쓴다). 토론과 진행 메모는 이슈 **댓글**에 쓴다.

- 이유: 평가가 저장소 검토 방식이라 조건이 저장소에 남아야 하고, 조건 변경이 PR 리뷰를 거쳐야 "조건만 만족하면 결과가 나온다"는 전제가 지켜진다. 이슈 본문을 원본으로 하면 누구나 조건을 고칠 수 있고 기록이 저장소 밖에 남는다.

**이슈 종류와 라벨**(정의: [`.github/labels.yml`](../../.github/labels.yml))

결정 대기(P-xx)와 발표 트랙(S-xx)은 이슈로 만들지 않는다(11/5 PM 결정). 결정 대기의 원본은 7절 결정 표, 발표 트랙은 [`P_presentation.md`](P_presentation.md)이고 PM이 별도로 관리한다. 11/5 처음 이슈를 만들 때 생긴 P·S 이슈는 "not planned"로 닫았다(조직 설정상 삭제 불가).

| 라벨 | 뜻 |
|---|---|
| `flow:A` ~ `flow:E` | 흐름 |
| `day:11-05` ~ `day:11-12` | 태스크 날짜 |
| `type:task`, `type:integration` | 태스크, 통합(INT) |
| `blocker` | 시연·통합을 막는 결함(3절). 보류로 닫을 수 없다 |
| `evidence-fail` | `상태: 실패` 증빙을 병합한 태스크(완료 아님) |
| `status:blocked` | 선행 태스크나 결정 대기 때문에 착수 못 함 |
| `review-required`, `asset`, `scope:extension` | `[검수]`, `[에셋]`, `[확장]` 태스크 |
| `bug`, `fix`, `contract-change` | 결함, 수정 PR, 계약 변경 PR |
| `engine`, `web`, `infra`, `ml`, `ads`, `content`, `llm` | 결함 이슈의 영역 |

**마일스톤**: `통합 1 (11/7)`, `통합 2 (11/9)`, `통합 3 (11/11)`, `발표 (11/12)`. 태스크는 자기 날짜 이후 첫 마일스톤에 들어간다(11/5~7 → 통합 1, 11/8~9 → 통합 2, 11/10~11 → 통합 3, 11/12 → 발표). 결정 대기는 기한 날짜로 같은 규칙을 따른다. 날짜별 보기는 `day:` 라벨로 한다. 마일스톤을 통합 단위로 둔 이유는 "통합까지 끝나야 할 일이 다 닫혔는가"가 감독의 핵심 질문이기 때문이다.

**이슈 만들기·동기화**
```
python -m tools.tasks_to_issues --dry-run                       # 기본. 만들 라벨·마일스톤·이슈를 출력만 한다
python -m tools.tasks_to_issues --hours                         # 흐름별 일별 시간표(문서화 포함)
python -m tools.tasks_to_issues --apply --repo OWNER/NAME       # 실제로 만든다(gh CLI 로그인 필요)
python -m tools.tasks_to_issues --apply --repo OWNER/NAME --assign A=login1,B=login2,...   # 담당자 지정(담당 흐름 기준 덮어쓰기, 발표 트랙은 P-24 뒤 S=login)
```
- 이슈 제목은 `[<ID>] <제목>`, 본문 첫 줄에 `<!-- task-id: <ID> -->` 표식이 있다. 같은 ID의 이슈가 있으면 새로 만들지 않고 본문·라벨·마일스톤만 갱신한다(멱등). 이슈의 열림·닫힘 상태, 담당자(`--assign`을 주지 않으면), 댓글은 건드리지 않는다. `--assign`을 주면 담당자를 태스크의 담당 흐름(첫 줄 `담당 X(...)`이 있으면 X, 없으면 ID의 흐름, INT는 E) 로그인 한 명으로 덮어쓰고 다른 담당자는 뺀다. 로그인을 주지 않은 흐름의 이슈는 건드리지 않는다. 같은 사람이 두 흐름을 맡으면 두 흐름에 같은 로그인을 준다(예: `A=pm,E=pm`).
- 선행 태스크는 본문에서 `#번호` 링크로 바뀐다(두 번째 단계에서 갱신).
- 태스크 문서를 고치는 PR이 병합되면 같은 명령으로 다시 동기화한다(E 담당, 매일 오후 5시 병합 뒤).

**PR과 이슈 잇기**
- **PR 하나 = 태스크 하나.** PR 템플릿([`.github/pull_request_template.md`](../../.github/pull_request_template.md))의 `Task:` 줄은 본문에 **정확히 1개**, ID도 1개다(`Task: E-05-02`). 결정 반영 PR은 `Task: P-xx`.
- 이슈 연결 줄은 `Closes #<번호>` 또는 `Refs #<번호>` 중 **정확히 하나**만 쓴다. 다른 닫기 키워드(`Fixes`, `Resolves`, `Close`, `Closed` 등)를 쓰면 증빙 검사(`precheck --pr-body`)가 실패한다(검사를 거치지 않고 이슈가 닫히는 것을 막는다).
- 조건을 모두 만족한 PR은 `Closes #<이슈 번호>`를 쓴다. 작성자는 PR 본문을 파일로 저장해 `python -m tools.precheck --pr-body <파일>`을 돌리고(그 태스크 ID로 `check_evidence --complete`까지 돈다) 마지막 줄을 본문에 붙인다. PM은 병합 전에 같은 검사를 로컬에서 다시 돌리고, 실패하면 병합하지 않는다. 그래서 **이슈는 `--complete`를 통과한 PR의 병합으로만 닫힌다.**
- **커밋 메시지의 닫기 키워드 금지**(11/4 PM 결정): GitHub는 기본 브랜치에 들어온 커밋 메시지의 닫기 키워드로도 이슈를 닫는다. 그래서 증빙 검사(`precheck --pr-body`)는 PR base 이후 커밋 메시지(`git log <base>..HEAD`)에 닫기 키워드(`Closes` 포함)가 하나라도 있으면 실패한다. 이슈는 PR 본문의 `Closes #` 한 줄로만 닫힌다. 병합은 merge commit만 허용한다(squash·rebase 병합은 증빙의 커밋 SHA를 dev 이력에서 없앤다, 11/5 PM 결정).
- 일부만 했거나 `상태: 실패` 증빙을 병합하는 PR은 `Refs #<번호>`를 쓰고 이슈에 `evidence-fail` 라벨을 붙인다. `Refs` PR은 바뀐 증빙에 `--format`만 돌린다.
- `precheck`는 PR 본문을 환경 변수로 `check_evidence --pr-body-env`에 넘기고 셸 명령에 직접 넣지 않는다. 변경 파일 비교 기준은 `origin/dev`와 HEAD의 merge-base다(`--base`로 바꿀 수 있다. 못 구하면 문서·증빙 검사를 실패로 본다).
- **push**: `git push` 때 `.githooks/pre-push`가 PR 본문 없이 `precheck`를 돌린다(바뀐 증빙은 `--format`만). 푸시하는 커밋이 지금 HEAD가 아니거나 커밋하지 않은 변경이 있으면 임시 worktree에 그 커밋을 꺼내 검사한다. 그 커밋이 깨끗한 작업 트리에서 같은 비교 기준(`origin/dev`와의 merge-base)으로 이미 `precheck`를 통과했으면 통과 기록(`<git 공용 폴더>/precheck-pass/<SHA>`)을 보고 검사를 생략한다(11/7 PM 결정, 끄기 `PALDO_PRECHECK_NO_CACHE=1`). 병합 뒤 `dev`·`main`에서는 자동 검사가 없다. PM이 매일 `dev`에서 `python -m tools.precheck`를 한 번 돌린다.
- 병합에는 작성자가 아닌 1명의 승인이 필요하다(3절 ⑧).
- **승격 PR**(`dev` → `main`, 3절 브랜치 모델): `Task:`·`Closes`/`Refs` 줄을 쓰지 않는다. 제목은 `승격: <날짜> <사유>`(예: `승격: 11/12 시연 전`). `dev`를 체크아웃하고 `python -m tools.precheck --base origin/main`으로 돌려 `main` 이후 바뀐 증빙의 `--format`만 본다(기본 기준 `origin/dev`로 돌리면 바뀐 것이 없어 아무것도 검사하지 않는다).
- 이슈를 손으로 닫지 않는다(예외: 저장소 배정 시 10-1절 전환 5단계). `check_evidence`는 GitHub를 조회하지 않으므로, 손으로 닫힌 태스크 이슈는 INT-11 #11에서 닫힌 태스크 이슈 목록(`gh issue list --state closed --label type:task`)과 `check_evidence --all --until` 통과 목록을 대조해 찾는다.
- **태스크 ID를 바꾸거나 태스크를 다른 파일로 옮기면**(예: 11/5 발표 트랙 분리, E 에셋 재배치) 동기화는 새 ID 이슈를 만들고 옛 이슈는 건드리지 않는다. `--apply`가 "원본에 없는 열린 이슈" 목록을 출력하므로, PM이 옛 이슈에 새 이슈 링크를 댓글로 남기고 닫는다(이 경우만 손으로 닫는다. 옛 ID는 태스크 문서에 없으므로 `check_evidence --all` 대상이 아니다). 이슈를 처음 만든 뒤에는 ID를 바꾸지 않는 것이 원칙이다.

**PM 감독 방법**(매일)
1. 마일스톤 화면: 다음 통합 마일스톤의 진행률. 오늘 날짜 라벨(`day:11-0X`)로 걸러 **오늘 닫혀야 할 이슈 중 열린 것**을 본다.
2. `blocker` 라벨 열린 이슈: 0건이어야 한다. 있으면 스탠드업 첫 안건.
3. `evidence-fail`, `status:blocked` 라벨: 재배치 대상.

5. 오후 5시 병합 뒤 `python -m tools.check_evidence --all --until <오늘>`(E-05-02) 결과가 녹색인지.
