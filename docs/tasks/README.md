## 2. 태스크 형식

```
### <ID> <제목>
- 날짜·시간: 11/5(목) · 3h        - 선행: 다른 태스크 ID
- 문서화(+0.25h, 공통 ⑦): 이 태스크가 남길 문서(10절)
- 모듈 문서 일괄 갱신(+0.5h, 공통 ⑦) · 대상: … · 코드를 바꿨다면: … · 모듈: …   ← 흐름별 그날 마지막 태스크에만
- 입력: 계약·픽스처·선행 산출물     - 산출물: 저장소 경로
- 완료 조건: 검사 가능한 항목(테스트 이름·명령·수치·증빙 파일)
- 근거: 기획서 절, 계약 문서
```

- ID: `흐름-날짜-순번`(예: `A-05-01` = A 흐름, 11/5, 1번). 통합은 `INT-07` 등. 발표 트랙은 `S-날짜-순번`(결정 대기 `P-xx`와 겹치지 않게 S).
- **하루 시간 예산**: 공통 1.5시간(스탠드업 0.25, 오후 5시 병합·전체 테스트 0.5, PR 리뷰 0.5, 증빙 정리 0.25) + 태스크 한도. A~D는 1인 9시간(태스크 **7.5시간 이하**), **E는 10.5시간(태스크 9시간 이하, P-22)**. 태스크 시간에는 "문서화(+Nh)"와 "모듈 문서 일괄 갱신(+Nh)" 시간이 더해진다. 각 파일 끝에 일별 합계가 있고, `python -m tools.tasks_to_issues --hours`가 다시 계산한다. **발표 트랙(S)은 담당이 정해질 때까지(P-24) 흐름별 한도 계산에서 빼고 시간표에 별도 줄로 보인다.** 발표 트랙을 뺀 뒤에도 모든 흐름이 한도를 넘는다(초과 합계 A 5.75h, B 6.75h, C 7.25h, D 6.5h, E 8.75h). 처리는 P-23.
- 각 태스크의 "완료 조건" 외에 아래 공통 완료 정의를 **모두** 만족해야 완료다.
- 저녁 입력 검수(team_plan 8절)는 공통 시간에 더하지 않는다. E-07-02·E-09-02·D-09-03 태스크 시간 안에서 한다.
- **인계 시각**: 같은 날 다른 흐름의 산출물을 받는 태스크는 "선행" 옆에 인계 시각을 적었다(예: `C-06-03(12:00)`). 인계하는 쪽은 그 시각까지 해당 조건만 먼저 병합하고, 받는 쪽은 그 전에는 픽스처·가짜 구현으로 진행한다. 인계 시각을 놓치면 스탠드업이 아니라 그 즉시 PM에게 알린다.
- 시간 초과: 태스크가 적힌 시간의 1.5배를 넘기면 담당자가 PM에게 알리고, PM이 11/11 수정 시간 또는 다른 흐름으로 재배치한다. 시간 추정은 11/5 실측(C-05-01, D-05-02)과 **11/5 실제 소요 시간**(증빙의 "실제 소요 시간(h)", `python -m tools.hours_report --until 11-05`) 뒤 11/6 스탠드업에서 한 번 다시 맞춘다(P-23).
- **사전 작업**(예정일 전에 로컬에서 미리 하는 작업): 결과는 "로컬 사전 구현"으로 보고하고 태스크는 미완으로 둔다. PR 병합과 필수 체크 통과(3절 ①②⑧)까지 끝나야 완료다. 증빙의 실제 소요 시간에는 실제로 한 시간만 적고, 모듈 문서 `변경 이력` 날짜는 태스크 예정일을 쓴다(10절). 사전 작업을 여러 개 병행하면 새 테스트 파일 이름을 작업마다 나눠 같은 파일을 동시에 고치지 않고, PM 세션이 브랜치를 하나씩 순서대로 `master`(원격 생성 뒤에는 `main`)에 병합한 뒤 최신 태스크 문서 기준으로 전체 테스트를 다시 돌린다.

## 3. 공통 완료 정의 (모든 태스크)

| # | 조건 | 자동 확인 방법 |
|---|---|---|
| ① | PR이 `main`에 병합됨. PR 제목에 태스크 ID | GitHub PR 목록 |
| ② | GitHub Actions 필수 체크 4개 통과: `core`(계약·엔진·ML·광고 도메인 unittest, 비밀정보 검사), `django`(`python manage.py test`, Mongo·MySQL 서비스 컨테이너), `evidence`(PR 본문의 태스크 ID로 증빙 검사, 11절), `docs`(문서화 검사, 10절). Kafka·Spark·Delta를 쓰는 검사는 CI가 아니라 통합(INT)에서 실제 스택으로 판정한다 | PR의 체크 표시(`.github/workflows/ci.yml`, E-05-02) |
| ③ | 증빙 문서 `paldo/docs/evidence/<태스크ID>.md` 커밋(양식 4절). 태스크 문서의 **완료 조건 번호마다 한 행**, 모든 행 "통과 = 예" | `python -m tools.check_evidence <태스크ID> --complete`가 통과(4절 검사 규칙) |
| ④ | **성능 관련 수치는 전부 계측값**이다. Prometheus 지표 또는 측정 스크립트(`tools/perf/`) 출력으로만 쓴다. 추정치·손으로 잰 값은 인정하지 않는다. 측정 결과는 결과 JSON(4절 "결과 JSON 형식", `docs/evidence/perf/<ID>/<이름>.json`)으로 함께 커밋한다 | `check_evidence`가 수치 행의 측정값을 결과 JSON 값과 대조하고, 기준과 비교한 통과 여부를 다시 계산한다(4절 규칙 3) |
| ⑤ | **동작하는 구성요소는 모두 구조화 로그를 남긴다**(5절 규칙). 새로 만든 서비스·배치·스크립트 포함 | 증빙에 로그 발췌 3줄 이상 + 로그 위치 |
| ⑥ | 비밀정보(IP, 계정, 비밀번호, 키, 토큰) 미포함 | `python -m tools.check_secrets`(CI) |
| ⑦ | **문서화**: 태스크의 "문서화" 줄에 적힌 문서를 10절 기준대로 남긴다(트러블 기록, docstring, 계약 문서, 라우팅 문서). 모듈 문서는 흐름별로 **그날 마지막 태스크**의 "모듈 문서 일괄 갱신" 줄에서 한 번에 갱신한다. "문서화(+Nh)"와 "일괄 갱신(+Nh)"이 그 시간이다 | `check_docs --task <ID>`(`--complete`에 포함)와 `check_docs --diff`(CI `docs` 체크) |
| ⑧ | **PR 승인**: 작성자가 아닌 팀원 1명이 GitHub에서 승인(Approve)한다. 리뷰 시간은 공통 시간의 "PR 리뷰 0.5h"다. 승인 뒤 수정 커밋을 올려도 기존 승인은 유지된다(재승인 부담을 줄이려고 "새 푸시 시 승인 무효화"는 끈다) | `main` 보호 규칙(승인 1명 필수, 관리자도 우회 불가)이 승인 없는 병합을 막는다(E-05-01) |

- 가짜 구현으로 통과한 것은 "착수 완료"다. 진짜로 교체해 계약 테스트를 다시 통과해야 완료로 센다(`docs/contracts/parallel_dev.md` 3절).
- 조건을 만족하지 못하면 완료 처리하지 않는다. 대신 증빙 맨 위에 `상태: 실패`와 원인·재시도 계획을 남겨 병합할 수 있다(형식 검사 `--format`만 통과). 이 문서는 **완료 검사 `--complete`를 통과하지 못한다.** 스탠드업에서 PM이 재배치를 정한다.
- **막는 결함(`blocker` 라벨)**: 시연 장면(S-10-01의 4개)·끝에서 끝까지 흐름 2개·INT 항목을 막는 결함이다. `blocker` 이슈는 "보류"로 닫을 수 없다. 보류는 `blocker`가 아닌 이슈에만 허용한다. 라벨은 이슈를 연 사람이 붙이고, 애매하면 `blocker`로 둔다.
- **사람 판단 조건**: 의미 보존, 말투, 이미지 유사성, 해설의 인과 같은 조건은 자동 검사로 보장할 수 없다. 이런 조건은 **다른 흐름 담당자 1명이 검수자**가 되어 기준표·검수한 샘플 ID·판정을 증빙의 "검수" 절에 남긴다. 자동 검사는 그 기록이 있는지만 확인한다. 검수자는 결과물 작성자와 다른 사람이어야 한다(PM이 아니어도 된다). 검수자와 작성자는 흐름 ID(A~E, 발표 트랙은 S)로 적고, 검수자 흐름이 증빙의 `작성자(흐름)`과 다르면 통과다(4절 규칙 5). 검수(기준표에 따른 판정 기록)는 PR 승인(⑧, 변경 전체 리뷰)과 별개이고, 같은 사람이 둘 다 해도 된다.
- **에셋 검수는 한 번에 한다**(11/4 PM 결정): 이미지 에셋은 개별 `[에셋]` 태스크에서 검수하지 않는다. 11/11 E-11-05에서 검수자 B가 모든 실제 파일의 에셋1(스타일 가이드 준수)·에셋5(체크리스트)와 아이콘의 작은 크기 구분을 한 번에 판정한다. 개별 에셋 태스크는 자동 검사 조건(에셋2~4)으로 완료한다. 예외: 스타일 가이드 자체의 B 확인은 11/5 E-05-05에서 한다(일괄 검수의 기준이므로). 품질 문제가 11/11에야 드러나는 위험은 받아들였다.

```json
{
  "task": "B-06-02",
  "commit": "<측정한 커밋 SHA>",
  "generated_at": "2026-11-06T09:12:00Z",
  "source": "python -m tools.perf.api_latency --seed 1",
  "metrics": {
    "api_p95": {"value": 412.3, "unit": "ms"},
    "error_count": {"value": 0, "unit": "건"}
  }
}
```
- `task`는 증빙 ID와 같다. `metrics`의 키는 영문 소문자·숫자·`_`. `value`는 숫자(정수 또는 소수)만. `unit`은 문자열이고 단위가 없는 값(비율 0~1 등)은 `""`.

**수치 표 작성 규칙**
- **측정값이 여러 개면 행을 나눈다.** 한 행 = 측정값 1개. 같은 조건 번호가 여러 행에 나와도 된다.
- **결과 파일 칸**: `<결과 JSON 경로>#<metrics 키>`(예: `docs/evidence/perf/B-06-02/api.json#api_p95`). 수치가 아닌 조건(테스트 통과, 파일 존재, 검수 기록 등)은 `-`.
- **기준 칸**: 수치 조건은 `<연산자> <수> <단위>` 또는 `<수>~<수> <단위>`. 연산자는 `<=`, `<`, `>=`, `>`, `==`. 범위 `a~b`는 양 끝을 포함한다. 단위가 없는 값은 단위를 생략한다. 예: `<= 1000 ms`, `40~60 %`, `== 0 건`, `<= 0.05`. 수치가 아닌 조건은 `-`.
- **측정값 칸**: `<수> <단위>`. 단위는 기준 칸·JSON `unit`과 **글자까지 같아야** 한다. 단위 환산은 하지 않는다(초와 ms를 섞으면 실패).
- 기준 칸이 수치 문법이면 결과 파일 칸은 `-`일 수 없다(④: 수치는 계측값만). 기준 칸이 `-`이면 결과 파일 칸도 `-`이고 측정값 칸은 자유 서술이다.
- **대조**: JSON `value`를 측정값 칸에 적힌 소수 자릿수로 반올림(사사오입, `decimal.ROUND_HALF_UP`)한 값이 측정값 칸과 같아야 한다(예: `412.3` → 칸에 `412 ms`라고 쓰면 일치, `413 ms`면 불일치).
- **판정**: 기준과의 비교는 반올림하지 않은 JSON `value`로 다시 계산한다. 결과("예"/"아니오")가 통과 칸과 다르면 실패.

**`check_evidence --format` 검사**: 양식 제목이 모두 있고(`## 검수`는 `[검수]` 태스크만 요구), `- 작성자(흐름):` 값이 A~E 또는 S이며, `- 실제 소요 시간(h):` 줄의 값이 숫자 형식이다(값의 크기는 보지 않는다). `--complete`도 이 검사를 포함한다.

**`check_evidence --complete` 검사 규칙**(E-05-02가 구현)
1. 태스크 문서(`docs/tasks/*.md`)에서 그 ID의 완료 조건 번호 목록을 읽어, 증빙 "수치" 표에 번호가 모두 있는지 본다.
2. 모든 행의 통과 칸이 "예"이고 `상태: 실패`가 없다.
3. 결과 파일 칸이 `-`가 아닌 행은 위 "수치 표 작성 규칙"대로 검사한다: 파일과 키가 있고, JSON `task`가 증빙 ID와 같고, 단위가 일치하고, 측정값이 반올림 규칙으로 JSON 값과 같으며, 다시 계산한 판정이 통과 칸과 같다. 기준 칸이 수치 문법인데 결과 파일이 `-`이거나 기준 칸을 해석할 수 없으면 실패.
4. 커밋 SHA(증빙의 `- 커밋:`과 결과 JSON의 `commit`)가 저장소에 있다.
5. 사람 판단 조건이 있는 태스크(문서 제목에 `[검수]` 표시)는 "검수" 표가 있고, 모든 행의 검수자 흐름이 `- 작성자(흐름):` 값과 다르다. `[검수]`가 아닌 태스크는 검수 절을 보지 않는다.
6. 문서화 검사 `check_docs --task <ID>`(10절 검사 규칙 1~3)가 통과한다. (`check_evidence`는 `check_docs`를 부르지만, `check_docs`는 `check_evidence`를 부르지 않는다. 10절 "완료된 태스크")

## 5. 로그·계측 규칙

**로그(모든 서비스·배치·스크립트)**
- 형식: JSON 한 줄. 표준 출력 + 파일(`/var/log/paldo/<서비스>.jsonl`, 로컬은 `out/logs/`). 보존 7일.
- 필수 필드: `ts`(UTC ISO8601), `level`, `service`, `component`, `msg`.
- 해당하면 반드시 넣는 필드: `request_id`(HTTP 요청마다 발급, 응답 헤더 `X-Request-ID`), `game_id`, `command_id`, `event_id`, `attempt_id`, `job_id`, `serve_id`, `charge_id`, `model_version`, `duration_ms`.
- 원문 자유 입력·설문 의견은 로그에 넣지 않는다(마스킹된 원문은 이벤트에만. `docs/contracts/privacy.md`).
- 오류는 `level=error`와 `error_type`을 넣는다. 예외를 삼키는 코드는 반드시 `warning` 이상 로그를 남긴다.

**계측(Prometheus)**
- 이름: `paldo_<구성요소>_<측정>_<단위>`(예: `paldo_http_request_duration_seconds`, `paldo_llm_render_duration_seconds`, `paldo_ad_serve_total`).
- 지연은 히스토그램(라벨: `route` 또는 `stage`, `status`). p50·p95는 Grafana에서 `histogram_quantile`로 계산한다.
- 서비스마다 `/metrics` 엔드포인트. 배치·스크립트는 Pushgateway 또는 실행 후 결과 JSON을 남긴다. 증빙에 쓰는 결과는 4절 "결과 JSON 형식"대로 `docs/evidence/perf/<ID>/`에 커밋한다(그 밖의 실행 결과는 `out/perf/`, 커밋하지 않음).
- 측정 스크립트는 `tools/perf/`에 두고, 같은 명령으로 다시 돌릴 수 있어야 한다(시드·입력 고정).

**발표 트랙(S)**: 모듈 문서와 일괄 갱신 줄이 없다. 문서 산출 태스크(구성안, 구간 자료, 발표 자료)는 "산출물 자체가 문서다"(규칙 3), 나머지(이미지, 시연 영상, 리허설)는 "트러블만"(`docs/troubles/S.md`, 규칙 1).

**모듈 목록**(`docs/modules/`): `engine`, `sim`, `web`, `infra`, `pipeline`, `ops`, `aws`, `ml_ops`, `privacy`, `intent`, `ml`, `ads`, `content`, `llm`, `assets`, `user_test`, `ci`, `perf`, `project`. 새 모듈이 필요하면 이 목록과 `docs/modules/README.md`에 추가한다.

**모듈 문서 필수 절**(이 제목 그대로, 이 순서): `## 무엇을`, `## 왜`(설계 근거와 기획서 절), `## 사용법`(실행 명령), `## 설정값`(환경 변수·파라미터·기본값), `## 한계`, `## 변경 이력`(표: `| 태스크 | 날짜 | 바뀐 점 |`). 양식은 [`docs/modules/_template.md`](../modules/_template.md).

**트러블 기록 형식**(`docs/troubles/<흐름>.md`): 태스크마다 `### <ID> <제목>` 아래 `- 문제:`, `- 원인:`, `- 대응:`, `- 결과:`(수치 + 증빙 링크) 4줄. 트러블이 없으면 `- 없음` 한 줄. 양식은 [`docs/troubles/_template.md`](../troubles/_template.md).

**`변경 이력`의 날짜**: 태스크 문서에 적힌 **예정일**(태스크 ID의 날짜, 예: `E-05-05` → `11/5`)을 쓴다. 사전 작업 등으로 실제 작업일이 다르면 실제 일자는 증빙(커밋 SHA, 실제 소요 시간)에 남는다. 검사 규칙 2의 "그날 날짜"도 예정일이다.

**완료된 태스크**(`check_docs`가 쓰는 정의): `docs/evidence/<ID>.md`가 있고, `상태: 실패`가 없으며, "수치" 표의 통과 칸이 모두 "예"인 태스크. `check_docs`는 이 판정을 직접 하고 `check_evidence --complete`를 부르지 않는다(`--complete`가 `check_docs --task`를 부르므로 순환을 막는다). GitHub 이슈 상태는 보지 않는다(로컬에서 같은 결과가 나와야 한다).

**검사 규칙**(`tools/check_docs.py`, E-05-02가 구현. 태스크 정보는 `tools/tasks_md.py`로 읽는다)
1. `--task <ID>`(모든 태스크): `docs/troubles/<흐름>.md`에 `### <ID>` 항목이 있고 4줄 형식이거나 `- 없음`이다. 증빙 문서의 "트러블" 절이 그 항목을 링크한다.
2. `--task <ID>`(일괄 갱신 줄이 있는 태스크 = 그날 흐름의 마지막 태스크): 줄의 "모듈"에 적힌 모듈 문서마다 필수 절 6개가 순서대로 있다. `변경 이력` 표에 "대상" 태스크마다 `| <ID> | <그날 날짜> |` 행이 있다. "코드를 바꿨다면" 태스크는 그 태스크 증빙의 커밋이 모듈 코드(모듈 → 코드 대응은 `docs/modules/README.md` 표)를 바꿨을 때만 행을 요구한다. 대상 태스크 중 아직 "완료된 태스크"(위 정의)가 아닌 것(밀린 태스크)은 이 검사에서 빼고, 그 태스크가 끝나는 날의 일괄 갱신 대상으로 옮겨 적는다(태스크 문서 수정 PR). 그래서 그날 마지막 태스크의 이슈는 일괄 갱신까지 끝나야 닫힌다.
3. `--task <ID>`: 문서 산출 태스크(문서화 +0h, "산출물 자체가 문서다")는 산출물 파일이 있고, 태스크 완료 조건에 적힌 구간 제목이 모두 있다.
4. `--all --until <날짜>`: 예정일이 그 날짜까지인 태스크 중 "완료된 태스크"(위 정의)이면서 일괄 갱신 "대상"에 든 태스크마다 어느 모듈 문서의 `변경 이력`에든 그 ID 행이 있다(일괄 갱신에서 빠진 태스크를 잡는다).
5. `--diff <base>`: 변경된 `.py`의 공개 함수·클래스(이름이 `_`로 시작하지 않는 최상위 정의와 공개 클래스의 공개 메서드)에 docstring이 있다(`ast`로 검사. `tests/`와 마이그레이션 제외).
6. `--diff <base>`: 계약 파일(`engine/domain/{model,events,serde,content}.py`, `engine/ports.py`, `server/app/dto.py`, `server/app/ads_port.py`, `server/api/viewmodels.py`, `ads/domain/*.py`, `contracts/datasets.py`)이 바뀌면 `docs/contracts/` 아래 문서도 같은 PR에서 바뀐다. 최상위 또는 두 번째 단계의 새 폴더가 생기면 `paldo/README.md`도 같은 PR에서 바뀐다.

통합 태스크(INT-xx)의 문서는 판정 결과(`docs/evidence/INT-xx.md`)이고, 미통과 항목의 원인은 담당 흐름의 트러블 기록에 남긴다. 시간은 주관 태스크(E-07-03, E-09-04, E-11-01)에 들어 있다.

## 11. GitHub Issues로 관리하기

**원본 원칙**: 태스크 정의(할 일, 완료 조건, 시간, 선행)의 원본은 **이 저장소의 마크다운**이다. 조건을 바꾸려면 마크다운을 고치는 PR을 낸다(계약 변경과 같은 승인 규칙). GitHub Issues는 **진행 관리**(담당자, 상태, 토론, 막힌 것)에 쓴다. 이슈 본문은 `tools/tasks_to_issues.py`가 마크다운에서 만들므로 이슈 본문을 직접 고치지 않는다(다음 동기화 때 덮어쓴다). 토론과 진행 메모는 이슈 **댓글**에 쓴다.

- 이유: 평가가 저장소 검토 방식이라 조건이 저장소에 남아야 하고, 조건 변경이 PR 리뷰를 거쳐야 "조건만 만족하면 결과가 나온다"는 전제가 지켜진다. 이슈 본문을 원본으로 하면 누구나 조건을 고칠 수 있고 기록이 저장소 밖에 남는다.

**이슈 종류와 라벨**(정의: [`.github/labels.yml`](../../.github/labels.yml))

| 라벨 | 뜻 |
|---|---|
| `flow:A` ~ `flow:E` | 흐름 |
| `flow:presentation` | 발표 트랙(S-xx). 담당은 P-24 |
| `day:11-05` ~ `day:11-12` | 태스크 날짜 |
| `type:task`, `type:integration`, `type:decision` | 태스크, 통합(INT), 결정 대기(P-xx) |
| `blocker` | 시연·통합을 막는 결함(3절). 보류로 닫을 수 없다 |
| `evidence-fail` | `상태: 실패` 증빙을 병합한 태스크(완료 아님) |
| `status:blocked` | 선행 태스크나 결정 대기 때문에 착수 못 함 |
| `review-required`, `asset` | `[검수]`, `[에셋]` 태스크 |
| `bug`, `fix`, `contract-change` | 결함, 수정 PR, 계약 변경 PR |
| `engine`, `web`, `infra`, `ml`, `ads`, `content`, `llm` | 결함 이슈의 영역 |

**마일스톤**: `통합 1 (11/7)`, `통합 2 (11/9)`, `통합 3 (11/11)`, `발표 (11/12)`. 태스크는 자기 날짜 이후 첫 마일스톤에 들어간다(11/5~7 → 통합 1, 11/8~9 → 통합 2, 11/10~11 → 통합 3, 11/12 → 발표). 결정 대기는 기한 날짜로 같은 규칙을 따른다. 날짜별 보기는 `day:` 라벨로 한다. 마일스톤을 통합 단위로 둔 이유는 "통합까지 끝나야 할 일이 다 닫혔는가"가 감독의 핵심 질문이기 때문이다.

**이슈 만들기·동기화**
```
python -m tools.tasks_to_issues --dry-run                       # 기본. 만들 라벨·마일스톤·이슈를 출력만 한다
python -m tools.tasks_to_issues --hours                         # 흐름별 일별 시간표(문서화 포함)
python -m tools.tasks_to_issues --apply --repo OWNER/NAME       # 실제로 만든다(gh CLI 로그인 필요)
python -m tools.tasks_to_issues --apply --repo OWNER/NAME --assign A=login1,B=login2,...   # 담당자 지정(발표 트랙은 P-24 뒤 S=login)
python -m tools.hours_report --until 11-05                     # 계획 대비 실제 소요 시간(흐름 × 날짜)
```
- 이슈 제목은 `[<ID>] <제목>`, 본문 첫 줄에 `<!-- task-id: <ID> -->` 표식이 있다. 같은 ID의 이슈가 있으면 새로 만들지 않고 본문·라벨·마일스톤만 갱신한다(멱등). 이슈의 열림·닫힘 상태, 담당자(`--assign`을 주지 않으면), 댓글은 건드리지 않는다.
- 선행 태스크는 본문에서 `#번호` 링크로 바뀐다(두 번째 단계에서 갱신).
- 태스크 문서를 고치는 PR이 병합되면 같은 명령으로 다시 동기화한다(E 담당, 매일 오후 5시 병합 뒤).

**PR과 이슈 잇기**
- **PR 하나 = 태스크 하나.** PR 템플릿([`.github/pull_request_template.md`](../../.github/pull_request_template.md))의 `Task:` 줄은 본문에 **정확히 1개**, ID도 1개다(`Task: E-05-02`). 결정 반영 PR은 `Task: P-xx`.
- 이슈 연결 줄은 `Closes #<번호>` 또는 `Refs #<번호>` 중 **정확히 하나**만 쓴다. 다른 닫기 키워드(`Fixes`, `Resolves`, `Close`, `Closed` 등)를 쓰면 `evidence` 체크가 실패한다(검사를 거치지 않고 이슈가 닫히는 것을 막는다).
- 조건을 모두 만족한 PR은 `Closes #<이슈 번호>`를 쓴다. CI `evidence` 체크가 그 태스크 ID로 `check_evidence --complete`를 돌려, 실패하면 병합이 막힌다. 그래서 **이슈는 `--complete`를 통과한 PR의 병합으로만 닫힌다.**
- 일부만 했거나 `상태: 실패` 증빙을 병합하는 PR은 `Refs #<번호>`를 쓰고 이슈에 `evidence-fail` 라벨을 붙인다. `Refs` PR은 바뀐 증빙에 `--format`만 돌린다.
- PR 본문은 워크플로에서 환경 변수(`PR_BODY`)로 넘기고 셸 명령에 직접 넣지 않는다. 변경 파일 비교 기준은 PR의 base 커밋(`github.event.pull_request.base.sha`)이다.
- **push 이벤트**(병합 뒤 `main`에 올라온 커밋)에는 PR 본문이 없으므로 테스트 체크(`core`, `django`)와 "그 push에서 바뀐 증빙"의 `--format`만 돌린다(비교 기준은 `github.event.before`). `evidence`의 PR 본문 검사와 `docs --diff`는 `pull_request`에서만 돌린다.
- 병합에는 작성자가 아닌 1명의 승인이 필요하다(3절 ⑧).
- 이슈를 손으로 닫지 않는다. `check_evidence`는 GitHub를 조회하지 않으므로, 손으로 닫힌 태스크 이슈는 INT-11 #11에서 닫힌 태스크 이슈 목록(`gh issue list --state closed --label type:task`)과 `check_evidence --all --until` 통과 목록을 대조해 찾는다.
- **태스크 ID를 바꾸거나 태스크를 다른 파일로 옮기면**(예: 11/5 발표 트랙 분리, E 에셋 재배치) 동기화는 새 ID 이슈를 만들고 옛 이슈는 건드리지 않는다. `--apply`가 "원본에 없는 열린 이슈" 목록을 출력하므로, PM이 옛 이슈에 새 이슈 링크를 댓글로 남기고 닫는다(이 경우만 손으로 닫는다. 옛 ID는 태스크 문서에 없으므로 `check_evidence --all` 대상이 아니다). 이슈를 처음 만든 뒤에는 ID를 바꾸지 않는 것이 원칙이다.

**PM 감독 방법**(매일)
1. 마일스톤 화면: 다음 통합 마일스톤의 진행률. 오늘 날짜 라벨(`day:11-0X`)로 걸러 **오늘 닫혀야 할 이슈 중 열린 것**을 본다.
2. `blocker` 라벨 열린 이슈: 0건이어야 한다. 있으면 스탠드업 첫 안건.
3. `evidence-fail`, `status:blocked` 라벨: 재배치 대상.
4. `type:decision` 열린 이슈 중 기한이 오늘인 것: PM이 결정하고 결과를 README 7절에 반영하는 PR을 낸 뒤 그 PR로 닫는다.
5. 오후 5시 병합 뒤 `python -m tools.check_evidence --all --until <오늘>`(E-05-02) 결과가 녹색인지.
