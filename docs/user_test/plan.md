### 버전 값 기록

일반 판(E-08-14)은 판 메타에 버전 3개를 남긴다: `rule_version`·`engine_version`은 배포 코드(`RULE_PARAMS_VERSION`, `ENGINE_VERSION`), `content_version`은 운영 설정 `PALDO_CONTENT_VERSION`. 실험 회차(8절)를 열 때는 `/admin/sessions`의 회차 등록에 같은 값을 넣는다.

- 값은 태그 `v-usertest-1`을 체크아웃한 상태에서 아래 명령으로 읽어 E-08-04 증빙에 적는다. 집계 도구 결과의 `versions`(판 메타 조합별 판 수)가 이 값 한 줄인지 E-09-01에서 확인한다.
- 태그의 커밋 SHA(`git rev-parse "v-usertest-1^{commit}"`)도 따로 적는다. SHA는 어떤 코드가 배포됐는지를, 버전 값은 판이 어떤 규칙·엔진·콘텐츠로 진행됐는지를 가리킨다. 둘은 서로를 대신하지 않는다. 테스트 서버에 올라간 커밋의 SHA가 태그(`blocker` 수정으로 `v-usertest-2`를 만들었으면 그 태그)의 SHA와 같은지 확인해 증빙에 적는다.

| 필드 | 읽는 곳·명령 | 참고: 11/8 `dev`(52c08ea) 값 |
|---|---|---|
| `rule_version` | `python -c "from engine.domain import params; print(params.RULE_PARAMS_VERSION)"` | `rule-0.6.decision-1` |
| `engine_version` | `python -c "from engine.domain.model import ENGINE_VERSION; print(ENGINE_VERSION)"`(E-08-14부터 단일 출처) | `paldo-engine` |
| `content_version` | `python -c "import json; print(json.load(open('content/bundle_v1.json', encoding='utf-8'))['content_version'])"` | `content-1.0.1`(11/9 성향 hothead 해명 변형 한 줄 어조 수정으로 올림) |

- 참고 열은 태그 전 값이다. 증빙에는 태그에서 읽은 값을 적는다.
- **콘텐츠 적재 확인.** 운영 게임은 판의 `content_version`으로 Mongo `content` 컬렉션에서 그 버전을 읽는다(`server/infra/content_store.py`). 같은 버전은 다시 적재할 수 없다(`content_version_exists`).
  - `content-1.0`은 C-07-04 운영 인계 때 실제로 읽혔다([`ops/proxy/README.md`](../../ops/proxy/README.md) "운영 인계 범위"). 적재된 내용이 태그의 `content/bundle_v1.json`과 같은지 대조한 기록은 없다. `bundle_v1.json`은 11/7 E-07-05에서도 바뀌었다.
  - 11/9에 `content-1.0.1`로 올렸으므로(대사 어조 한 줄) 운영 Mongo에는 아직 없다. 11/10 09:00 배포 때 후보 커밋으로 `tools.load_content`를 한 번 적재한 뒤 대조하고, 일반 판용 `PALDO_CONTENT_VERSION`도 `content-1.0.1`로 둔다.
  - 그래서 **11/10 09:00 배포 전에** 후보 커밋에서 대조한다(C-08-04 1번. 11/8에 준비·1차 대조, 11/10 09:00에 그 시점 후보 커밋으로 재대조). 운영 DB 읽기 권한이 있는 환경에서 `MongoContentSource(<content 컬렉션>).load(<후보 커밋의 content_version>)`의 결과와, 후보 커밋의 `tools.check_content.load_bundle(Path("content/bundle_v1.json"))` 결과(`pathlib.Path`로 넘긴다)가 같은지 본다.
  - 다르면 `bundle_v1.json`의 `content_version`을 올린 커밋을 `dev`에 병합하고 그 커밋으로 적재한다(`python -m tools.load_content content/bundle_v1.json`). 배포·리허설·태그와 버전 값 읽기를 그 커밋에서 한다. 배포 커밋과 서버 콘텐츠 버전이 어긋나지 않게 하려는 것이다.
  - 대조·적재와 후보 커밋 배포는 C가 한다([C-08-04](../tasks/C_infra.md), 11/8 PM 결정).

### SHA 유지

- 리허설(10:30)부터 18:00 클로즈까지 테스트 서버의 커밋을 바꾸지 않는다. 테스트 중 배포하면 같은 테스트 안에서 판 조건이 달라지기 때문이다. `dev` 병합은 막지 않는다(병합된 변경은 18:00 뒤에 배포한다).
- 예외는 `blocker` 수정뿐이다(적용 승인 E):
  - 수정 커밋을 `dev`에 병합하고 그 커밋에 새 태그 `v-usertest-2`를 만든다. 리허설 뒤 병합된 다른 변경도 함께 들어가므로 바뀐 흐름을 확인하고 6인 판 1판을 다시 완주한다.
  - 버전 값을 다시 읽고, 테스트 서버를 `v-usertest-2` 커밋으로 다시 띄운다. 바꾼 시각을 E-09-01 증빙에 적는다(그 시각 앞뒤 판은 집계 도구 `versions`로 구분된다).
- 테스트 서버에 올라간 최종 태그와 커밋 SHA는 E-08-04 증빙에 적는다.

- 판이 끝날 때마다 한 번 보여 준다.
- **전체 건너뛰기**: "건너뛰기"를 누르면 네 문항을 모두 건너뛰고, 건너뜀을 기록한다(B-07-02).
- 점수 문항(1~3)은 셋 다 답하거나 전체를 건너뛴다. 자유 의견만 비워 둘 수 있다.
- 건너뜀은 `skipped=true`와 점수 셋 `null`로 저장하고, 응답과 같은 `survey_submitted` 이벤트로 낸다. 한 번 응답하거나 건너뛴 판은 바꿀 수 없다(P-29, [api.md](../contracts/api.md) 2-2절).
- 점수 평균·보상에는 응답(`skipped=false`)만 쓰고, 응답률은 응답 수 ÷ 판 수로 센다(건너뜀은 분모에만, [events.md](../contracts/events.md) 2절).
- 설문 점수는 개인별이 아니라 여러 판을 모은 값으로만 분석과 전략 조정에 쓴다(privacy.md 3·4절). 억울함은 높을수록 나쁜 방향이므로, 다른 두 항목과 함께 평균·보상으로 쓸 때의 방향 처리는 집계하는 쪽(E-10-03, D-09-02)이 정한다.

`test_human`(6절 규칙의 실행 방법): 정식 테스트 판은 먼저 13:00~18:00으로 자른다(오픈 전·마감 뒤에 시작한 판 제외, 남은 판의 마감 뒤 이벤트 제외, `ut-freeze-1.1`, 지표 집계도 같은 기본값). 문장은 입력 문장 수와 같은 기준. PM을 뺀 정식 테스트 참가자(문장이 없어도 판을 한 사람 모두) 가명을 정렬해 시드로 섞고 floor(n/2)명을 평가로(홀수면 평가 쪽이 1명 적다, 11/8 확정). test_human = 사전 테스트 PM 문장(`pm: true`) + 평가 사용자 문장 − 개인정보 검수 제외(학습 쪽에도 적용). 검수 결과와 학습·개발 세트는 필수 입력이다. 평가 사용자와 학습 쪽·외부 세트 사용자 교집합 0, 정규화 문장 교집합 0을 검사하고 하나라도 있으면 동결하지 않는다. 동결 기록은 Delta 버전 대신 동결 폴더의 `manifest.json`(파일별 바이트 수·sha256)이다(11/8 사용자 결정).

검증: 로컬 Mongo·SQLite에서만 끝에서 끝까지 확인했다(11/8). 운영 DB에서의 실행과 수치 대조는 읽기 전용 계정을 받은 뒤 한다.
