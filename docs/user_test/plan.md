### 회차 등록 버전 값

`/admin/sessions`의 회차 등록은 버전 3개(`rule_version`·`engine_version`·`content_version`)를 받는다. 셋이 모두 있어야 하고 각 값은 영문·숫자·`_` `.` `-` 1~80자다(`server/app/test_sessions.py` `TestSessionService.create`). 이 값은 판 메타에 그대로 남는다.

- 값은 리허설 태그 `v-usertest-1`을 체크아웃한 상태에서 아래 명령으로 읽어 E-08-04 증빙에 적는다. 사전·정식 회차와 늦은 참가자 회차에 모두 같은 값을 넣는다.
- 태그의 커밋 SHA(`git rev-parse "v-usertest-1^{commit}"`)도 따로 적는다. SHA는 어떤 코드가 배포됐는지를, 버전 값은 판이 어떤 규칙·엔진·콘텐츠로 진행됐는지를 가리킨다. 둘은 서로를 대신하지 않는다. 11/9 테스트 서버에 올라간 커밋의 SHA가 이 값과 같은지 확인해 증빙에 적는다.

| 필드 | 읽는 곳·명령 | 참고: 11/8 `dev`(52c08ea) 값 |
|---|---|---|
| `rule_version` | `python -c "from engine.domain import params; print(params.RULE_PARAMS_VERSION)"` | `rule-0.5.decision-1` |
| `engine_version` | 고정 문자열(`tools/run_engine_games.py`의 `ENGINE_VERSION`, 모듈 문서 [`web`](../modules/web.md) 운영 실행 6번) | `paldo-engine` |
| `content_version` | `python -c "import json; print(json.load(open('content/bundle_v1.json', encoding='utf-8'))['content_version'])"` | `content-1.0` |

- 참고 열은 태그 전 값이다. 회차에는 태그에서 읽은 값을 넣는다.
- **콘텐츠 적재 확인.** 운영 게임은 판의 `content_version`으로 Mongo `content` 컬렉션에서 그 버전을 읽는다(`server/infra/content_store.py`). 같은 버전은 다시 적재할 수 없다(`content_version_exists`).
  - `content-1.0`은 C-07-04 운영 인계 때 실제로 읽혔다([`ops/proxy/README.md`](../../ops/proxy/README.md) "운영 인계 범위"). 적재된 내용이 태그의 `content/bundle_v1.json`과 같은지 대조한 기록은 없다. `bundle_v1.json`은 11/7 E-07-05에서도 바뀌었다.
  - 그래서 **태그를 만들기 전에** 후보 커밋에서 대조한다. 운영 DB 읽기 권한이 있는 환경에서 `MongoContentSource(<content 컬렉션>).load("content-1.0")`의 결과와, 후보 커밋의 `tools.check_content.load_bundle(Path("content/bundle_v1.json"))` 결과(`pathlib.Path`로 넘긴다)가 같은지 본다.
  - 다르면 `bundle_v1.json`의 `content_version`을 올린 커밋을 `dev`에 병합하고 그 커밋으로 적재한다(`python -m tools.load_content content/bundle_v1.json`). 태그 `v-usertest-1`은 그 커밋에 만들고, 리허설과 버전 값 읽기를 그 태그에서 한다. 배포 태그와 회차의 콘텐츠 버전이 어긋나지 않게 하려는 것이다.
  - 태그를 만든 뒤에 차이를 찾으면 먼저 위와 같이 `content_version`을 올린 커밋을 병합하고 그 커밋으로 적재한 뒤, 아래 "리허설 뒤 dev 병합"의 막는 문제 수정과 같은 순서(그 커밋에 `v-usertest-2` 태그, 리허설·버전 값 다시 확인, 테스트 서버를 새 태그로)를 밟는다.
  - 대조와 적재를 누가 실행할지는 정해지지 않았다(운영 DB 권한 보유자 확인 필요).

### 리허설 뒤 dev 병합

- 테스트 서버는 태그 `v-usertest-1`의 커밋에 고정되므로 리허설 뒤에도 `dev` 병합은 막지 않는다(11/8 사용자 결정으로 `main` 승격이 테스트와 분리됨). 리허설 뒤 병합된 변경은 11/9 테스트 서버에 들어가지 않는다.
- 사용자 테스트를 막는 문제(`blocker`)를 11/9 전에 고쳐야 하면(적용 승인 E):
  - 수정 커밋을 `dev`에 병합하고 그 커밋에 새 태그 `v-usertest-2`를 만든다. 이때 리허설 뒤 병합된 다른 변경도 함께 들어가므로 바뀐 흐름을 다시 확인하고 6인 판 1판을 다시 완주한다.
  - 회차 버전 값을 다시 읽는다.
  - 테스트 서버를 `v-usertest-2` 커밋으로 다시 띄운다.
- 테스트 서버에 올라간 최종 태그와 커밋 SHA는 E-08-04 증빙에 적는다.

### 참가자 등록

회차는 등록 때 참가자 가명 ID 목록을 함께 받고, 등록한 뒤에는 바꿀 수 없다(`TestSessionService.create`, 세션 관리 화면 안내 "등록한 회차는 수정하지 않습니다"). 목록에 없는 계정은 그 회차의 판을 시작할 수 없다(`prepare`가 404).

1. 11/9 12:50(11/8 사용자 결정)에 그 시각까지 가입한 계정의 가명 ID를 뽑는다. 동의·활성 계정만 뽑고 운영자 계정은 뺀다. 가입 시각 범위의 시작 값은 정해지지 않았다.
2. 정식 회차를 등록한다: 회차 ID, 1번 가명 ID 목록, 위 버전 값 3개, 8절 판 목록.
3. 12:50 뒤에 가입한 사람과 1번에서 빠진 사람은 두 번째 회차로 받는다(11/8 사용자 결정). 같은 판 목록·같은 버전 값으로, 회차 ID만 새로 정한다. 등록 시각과 담당은 정해지지 않았다.
4. 등록한 회차 ID는 모두 E-09-01 증빙에 적는다.

- 같은 계정이 같은 순번을 다시 요청하면 저장된 판을 이어 간다(판 ID가 가명 ID·회차 ID·순번으로 정해진다, `_next_plan`).

## 7. 판 종료 설문 확정본

11/6 PM 결정(세 항목 각 1문항 + 자유 의견 선택, E-06-04 2번, 기획서 2.1·7.4). 입력 필드는 계약 `SubmitSurveyInput`(`server/app/dto.py`)의 이름을 그대로 쓴다.

| 순서 | 필드 | 항목 | 문항 | 답 |
|---|---|---|---|---|
| 1 | `fun` | 재미 | 이번 판은 재미있었나요? | 5점 척도: 1 전혀 그렇지 않다 · 2 그렇지 않다 · 3 보통이다 · 4 그렇다 · 5 매우 그렇다 |
| 2 | `unfair` | 억울함 | 이번 판의 결과가 억울하게 느껴졌나요? | 5점 척도(같은 보기). 점수가 높을수록 더 억울하다 |
| 3 | `npc_plausible` | NPC 그럴듯함 | 마을 사람들의 말과 행동이 그럴듯했나요? | 5점 척도(같은 보기) |
| 4 | `comment` | 자유 의견(선택) | 더 하고 싶은 말이 있으면 적어 주세요. 이름·연락처는 쓰지 마세요. | 빈칸 허용. 저장 전 마스킹(privacy.md 2절) |

- 판이 끝날 때마다 한 번 보여 준다.
- **전체 건너뛰기**: "건너뛰기"를 누르면 네 문항을 모두 건너뛰고, 건너뜀을 기록한다(B-07-02).
- 점수 문항(1~3)은 셋 다 답하거나 전체를 건너뛴다. 자유 의견만 비워 둘 수 있다.
- 건너뜀은 `skipped=true`와 점수 셋 `null`로 저장하고, 응답과 같은 `survey_submitted` 이벤트로 낸다. 한 번 응답하거나 건너뛴 판은 바꿀 수 없다(P-29, [api.md](../contracts/api.md) 2-2절).
- 점수 평균·보상에는 응답(`skipped=false`)만 쓰고, 응답률은 응답 수 ÷ 판 수로 센다(건너뜀은 분모에만, [events.md](../contracts/events.md) 2절).
- 설문 점수는 개인별이 아니라 여러 판을 모은 값으로만 분석과 전략 조정에 쓴다(privacy.md 3·4절). 억울함은 높을수록 나쁜 방향이므로, 다른 두 항목과 함께 평균·보상으로 쓸 때의 방향 처리는 집계하는 쪽(E-10-03, D-09-02)이 정한다.
