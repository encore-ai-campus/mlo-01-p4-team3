# B 웹·API 트러블 기록

### B-07-01

- 문제: 자유 입력·렌더 API에 카드 화면이 없었고, 빈 재입력·늦은 폴링이 행동을 방해했다. 버튼 전환과 모호한 근거 선택 외에도 다중 카드의 정상 확인, 직전 상대 전달, 재입력 선택 문맥에 누락이 있었다.
- 원인: 응용 API와 htmx 연결이 부족했다. 근거 모호 상태를 전체 카드에 적용했고, 직전 상대를 공개 기록에서 읽지 않았으며 재입력은 새 문장과 버전만 전달했다. 기존 일부 화면 시험은 해석 결과를 교체해 실제 문맥 문제를 놓쳤다.
- 대응: 카드·문장 조각과 반응 요청을 연결하고 해석기는 조립 중 한 번 생성한다. 빈 재입력과 늦은 폴링을 처리하고 근거 후보 두 개 선택을 지원한다. 확인 가능 여부는 카드별로 판정하며, 공개 캐묻기에서 직전 상대를 찾고 선택 인물·근거·직전 상대를 재입력에 전달한다.
- 결과: 실제 기준선 추가 회귀 3개는 수정 전 모두 실패·수정 후 통과했다. 최종 화면 22개·실제 기준선 계약 3개 통과, Django 112개 중 109개 통과·MySQL 3개 건너뜀. 이전 Chrome에서는 최종 추가 폴링 0건·페이지 오류 0건·광고 웹소켓 한 연결을 확인했고, 2.5초 지연 중 클릭 1회가 명령 1건으로 반영됐다. 이번 추가 개선은 HTTP 시험으로 확인했다. [상세 증빙](../evidence/B-07-01.md)

### B-05-01

- 문제: 초기 worktree에서 Django를 시작하려면 다른 태스크에 배정된 모듈이 필요했다.
- 원인: 통합 설정과 URL 목록에 계정, 화면, 운영자 세션 등록이 함께 들어 있었다.
- 대응: Django 골격 설정과 상태 확인 경로 3개를 분리했다. 골격의 `/readyz`는 DB 준비 상태를 확인한다.
- 결과: Django 6.1.2와 메모리 SQLite에서 시험 2개가 통과했다. MySQL 8.4.11에 연결한 경로 3개는 200을, DB 종료 후 상태 확인 경로 2개는 503을 반환했다.

### B-05-02

- 문제: 이관한 API 파일과 시험이 후속 태스크의 계정 ORM, 회의·복기 템플릿, 회차 조립을 참조했다.
- 원인: 통합 작업 폴더의 코드를 파일 단위로 복사할 때 JSON API와 후속 연동이 같은 파일에 있었다.
- 대응: JSON 경로 열 개와 서비스 조립만 등록했다. Django 세션 인증과 가명·소유권·동의 검사를 유지하고, 시험에서는 계정 프로필과 게임 포트를 주입했다.
- 결과: Django 6.1.2에서 시험 42개가 통과했다. 녹화 판 13단계가 픽스처와 일치했고, 저장 경합 뒤 같은 명령 ID는 재생하고 다른 ID는 409로 처리했다.

### B-05-03

- 문제: 이관한 화면 시험과 미리보기가 아직 병합되지 않은 계정·회차 모델에 의존했다. 최신 manifest의 이미지 수는 초기 태스크의 예시 수량보다 많았다.
- 원인: 통합 미리보기의 시험 조립을 그대로 가져왔고, 이후 에셋에 스프라이트와 표정 변형이 추가됐다.
- 대응: 운영 화면에서는 기존 세션·가명 검사와 DTO를 유지했다. 미리보기와 시험만 녹화 판·시험용 가명 프로필을 조립한다. 정적 이미지 시험은 manifest를 순회한다.
- 결과: 녹화 판 13단계의 전체·조각 HTML과 manifest 이미지 102개(광고 소재 8개 포함)를 검사했다. 누락된 응답이나 파일 바이트 불일치는 0건이었다.

### B-06-01

- 문제: 기본 녹화 판에는 결선 단계가 없었다. 기존 화면에는 투표·점 대상 버튼과 금줄 반응이 없었고, 점괘 공개 폼에서 실제값만 선택할 수 있었다.
- 원인: 녹화 판은 본투표에서 감금이 결정된다. 기존 회의 폼은 대상을 드롭다운으로 골랐고, 화면 모델은 공개 감금 기록과 실제값 이외의 공개 선택지를 전달하지 않았다.
- 대응: 공개 투표·감금 기록을 화면에 표시하고 투표·결선·점치기에 대상별 버튼을 적용했다. 실제 점괘와 낮에 공개할 결과를 분리하고, 실제 엔진 HTTP 시험으로 확인했다.
- 결과: 녹화 판 13단계를 완료했다. 실제 엔진에서 본투표와 결선이 각각 6표를 공개했고, 결선 후보 외 요청은 422, 재동점은 무감금으로 표시했다. 감금 대상의 금줄 반응과 실제값을 보존하는 점괘 공개도 검증했다.

### B-06-02

- 문제: 동시 명령 시험과 부하 실행기가 미병합 계정 모델과 Mongo 저장소에 의존했다.
- 원인: 여러 태스크를 합쳐 실행하던 코드에서 B의 명령 처리 시험과 실제 저장소 검증이 분리돼 있지 않았다.
- 대응: Django 세션·CSRF 검사를 거쳐 20개 요청을 같은 버전에서 경합시켰다. C의 저장소 계약을 따르는 메모리 대역으로 B의 재전송·경합 처리를 시험했다.
- 결과: 다른 ID는 수락 1건·409 19건, 같은 ID는 수락 1건·재생 19건이었다. 두 경우 모두 저장 버전이 한 번 증가했다. Compose Mongo 부하 시험은 C-06-01 저장소 인수 후 진행한다.

### B-06-04

- 문제: 관리자 로그인에서 잠금을 우회할 수 있었고, 같은 계정으로 다시 로그인하면 기존 세션 ID가 유지됐다. 주소별 가입 제한은 공유기 뒤 참가자의 가입을 막을 수 있었다. MySQL 회귀 시험에서 이미지 응답을 읽은 뒤 다음 요청이 실패했다.
- 원인: 관리자는 별도 인증 폼을 썼고 이전 가입 정책은 주소별로 집계했다. 이미지 시험이 Django 시험 클라이언트가 닫은 스트리밍 응답을 다시 닫아 시험 트랜잭션의 DB 연결도 닫혔다.
- 대응: 관리자 로그인에 공통 잠금을 적용하고, 성공 응답의 세션 키가 이전과 같으면 교체했다. 최신 계약에 맞춰 가입 제한과 주소 카운터를 제거했다. 이미지 시험의 응답 종료는 Django 시험 클라이언트에 맡겼다.
- 결과: MySQL 8.4.11에서 같은 주소의 동시 가입 6건이 모두 302였고, 로그인 실패 5회 뒤 15분 잠금을 확인했다. 일반·관리자 재로그인 뒤 이전 쿠키는 401이었다. 이전 스키마의 계정 프로필·잠금·세션을 보존했고 Django 시험 66개가 통과했다.

### B-06-03

- 문제: 이전 회차 초안은 참가자가 목록의 임의 시드를 골라 시작할 수 있었고, 같은 판의 시작 버튼을 다시 누르면 새 판이 생성될 수 있었다.
- 원인: 초안은 시드가 목록에 있는지만 확인했다. 게임 시작은 매번 무작위 판 ID를 만들었다.
- 대응: 참가자의 첫 미종료 순번으로 시작을 제한하고, 회차·참가자·순번에서 계산한 판 ID로 이미 시작한 판을 이어 간다. 광고 가명 발급과 대응표는 판 시작에서 분리했다.
- 결과: 승인된 `base6` 시드 4개를 순서대로 진행했고, 다시 시작 요청을 보내도 순번당 판과 시작 이벤트는 하나였다. 두 참가자의 실제 엔진 첫 판 배정이 일치했다. 로컬 Mongo에서 같은 로그인 세션에 대한 동시 발급 20건이 모두 같은 광고 가명을 반환했다.

- 추가 문제와 원인. htmx 폼으로 판을 시작하면 폼의 이동 분기가 먼저 실행되어 302를 반환했다. 기존 시험은 일반 폼과 htmx JSON만 확인했다.
- 대응. htmx 폼도 200 회의 조각으로 응답하도록 이동 조건을 수정했다. CSRF 검사와 같은 판 재요청을 포함하는 회귀 시험을 추가했다.
- 결과. 수정 전 새 시험은 302 응답으로 실패했다. 수정 후 htmx 폼은 200 조각을 반환했고, 전체 Django 시험 80개 중 77개가 통과했다. MySQL 전용 3개는 SQLite 실행에서 건너뛰었다.

### B-07-05

- 문제: 연결 시 읽은 Django 세션을 계속 사용하면 로그아웃 후 열린 웹소켓이 비콘을 중계할 수 있다. 동기 광고 요청을 이벤트 루프에서 실행하면 다른 HTTP 요청도 기다린다.
- 원인: 연결 범위 세션은 캐시되며 광고 게이트웨이는 동기 호출이다.
- 대응: 비콘마다 새 세션 저장 객체로 인증 상태·사용자 활성·인증 해시를 확인하고 중계는 `sync_to_async(thread_sensitive=False)`를 사용한다. 중계 슬롯은 serve와 분리한다.
- 결과: 로그아웃·만료·비밀번호 변경 후 비콘은 4401이었다. 전용 시험 8개, 광고·계층 계약 33개, 브라우저 클라이언트 Node 시험이 통과했다. 실제 Daphne에서도 인증 연결·중계·세션 폐기를 확인했다. Windows 시험 종료 때 프로세스 트리를 정리하도록 보완했다.

합계만 받던 `hello`에서는 대기열 초과와 페이지 이탈을 구분할 수 없었다. P-29의 사유별 보고·합계 검증과 서버의 전송 제한 집계를 적용했다. Daphne의 `/metrics`에서 대기열 초과 2건·페이지 이탈 1건을 확인했다. VM·실제 게임 저장소 부하 비교와 D의 가짜 광고 제공자 변경 검토는 남아 있다. [서버 설계](../../server/DESIGN.md)
### B-07-02

- 문제: 수첩·설문 JSON API는 있었지만 화면이 없었고, 설문 htmx 응답은 완료 조각이 없는 204였다. 확정 설문이 요구한 전체 건너뛰기도 표현할 수 없었다.
- 원인: 이전 DTO는 점수 세 개를 필수로 받았다. 일반 설문 폼도 라디오 선택이 필수여서 같은 폼으로는 빈 상태의 건너뛰기를 보낼 수 없다. 확신도 저장은 값만 비교해 다음 날·결선의 동일 값도 재전송으로 간주했다.
- 대응: 주민별 슬라이더·투표 확신도·정상 설문·완료 조각을 연결했다. P-29 반영 뒤 건너뛰기를 별도 폼으로 보내고, 서버가 점수 셋 `null`과 빈 의견을 확인하도록 했다. 수첩 중복 비교에 날짜·단계를 포함하고 이벤트 본문 형식은 유지했다.
- 결과: 투표 간 반복 저장 회귀 2개가 수정 전 실패·수정 후 통과했다. 관련 시험 35개·격리 MySQL 전체 120개가 통과했다. 같은 투표의 동일 재전송은 추가 0건, 다음 날·실제 엔진 결선의 첫 저장은 각각 1건이다. 앞선 Chrome 시험은 의심도 73·확신도 88과 정상·건너뜀 설문 완료 재조회를 확인했고 관련 오류 0건·가로 넘침 없음이었다. 설문 API의 204·400·409 처리도 유지됐다. 실제 Mongo·Kafka 수신은 C 인수 뒤 확인한다.
