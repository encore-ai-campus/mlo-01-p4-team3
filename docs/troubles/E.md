### E-05-01 저장소·결정 기록·담당 배정·이슈 생성

- 대응: 보호 규칙은 운영 규칙으로 대체했다(병합 전 작성자 외 1명 승인과 CI 4개 통과를 사람이 확인하고 병합은 PM이 한다. 병합 방식은 저장소 설정으로 merge commit만 허용). `tasks_to_issues --assign`이 흐름 담당으로 덮어쓰게 고쳤고(로그인 비교는 대소문자 무시), 옛 이슈 3개는 새 ID를 적은 댓글과 함께 not planned로 닫았다.

### E-05-02 GitHub Actions와 증빙·문서·비밀정보 검사
- 문제: 원래 조건 5 문구("`password=`/`passwd`/`secret`/`token` 값")를 그대로 구현하면 저장소 전체 검사에서 비밀이 아닌 39줄이 걸렸고(광고 픽스처의 serve 토큰 자리 가짜 이름 19줄, 그 생성 코드 19줄, CI 예시의 MySQL 빈 암호 허용 설정 1줄), 규칙을 고친 뒤에도 조건 5 문구 자체의 대역 표기(`docs/tasks/E_pm.md` 84행, 점 네 개 IPv4 3개)가 사설 IP로 걸렸다. 11/5에는 두 가지가 더 생겼다. 첫째, GitHub Actions CI가 PR 하나에 브랜치 push·PR·병합 push로 세 번 돌아 약 30분을 썼다(11/5 하루 약 15회·140분). 조직 저장소 68개가 무료 플랜 분량 월 2,000분을 함께 쓴다. 둘째, CI 대신 넣은 `pre-push` 훅에서 precheck가 돌 때 그 단위 테스트가 임시 저장소가 아닌 실제 저장소에 `git init`·commit·config를 했다(작업 브랜치 이동, `core.bare=true`·`user.name` 설정).
- 원인: 키 이름 부분 문자열 일치는 게임 용어(`secret_id`, `secrets`)·광고 serve 토큰 자리의 가짜 이름과 실제 비밀을 구분하지 못한다. 대역을 점 네 개 주소로 적은 문구는 검사 규칙이 정의상 잡는 형식이다. 11/5 CI 분량은 이벤트마다 전체 검사를 다시 도는 구성 때문이었다. 훅 사고는 git이 훅에 넘기는 `GIT_DIR`·`GIT_INDEX_FILE` 등 저장소 지정 환경 변수가 precheck의 하위 프로세스까지 이어졌기 때문이다. 그래서 테스트 안의 `git` 명령이 임시 폴더 대신 그 변수가 가리키는 실제 저장소에 적용됐다.
- 대응: PM 결정(11/4)으로 규칙 확정 — 키 이름의 마지막 조각 일치 + 문자열 값, 파일·키 단위 예외 목록 `tools/secrets_allowlist.txt`(4항목, 죽은 예외는 실패). 대역 표기는 원본 문구를 `10/8` 형식으로 고치기로 함(PM 세션 반영). 구현은 바꾸지 않음. 11/5 PM 결정으로 Actions CI를 폐지했다. 같은 검사를 로컬 한 명령 `python -m tools.precheck`(README 3절 ②)와 `git push` 때의 `.githooks/pre-push`로 돌리고, PR 본문에 결과 한 줄을 붙인다. 이에 맞춰 조건 1·3·6을 바꿨다. 훅 사고는 실제 저장소 설정을 원래대로 되돌렸다. 훅은 precheck 호출 때만 `git rev-parse --local-env-vars`를 지우고(훅 자신의 git 명령에는 유지), precheck는 `clean_env`로 하위 명령 환경에서 같은 변수를 뺀다. 물려받은 `GIT_DIR`이 다른 저장소를 바꾸지 않는지 회귀 테스트를 넣었다. 임시 clone에서는 커밋 때만 `git -c user.name=… commit`으로 신원을 주고 설정 파일에 쓰지 않는다.
- 결과: 예외 적용 전 39줄 → 예외 4항목으로 0줄. 원본 문구 수정 전에는 3줄이 남는다(`python -m tools.check_secrets`). 11/5 뒤: 워크플로 파일 0개(`.github/workflows/` 없음), precheck 한 번 33~36초(테스트 380개, 이 증빙의 실행들). 임시 clone 훅 푸시 시험에서 위반 커밋 푸시 차단 1건·정상 커밋 푸시 1건, 실제 저장소 로컬 설정 변경 0건. 증빙 [`docs/evidence/E-05-02.md`](../evidence/E-05-02.md)

### E-06-01 템플릿 대사
- 문제: 원본 완료 조건을 문구대로 하면 엔진과 어긋나는 곳이 세 군데 있었다. "모든 반응 템플릿에 `{fact}`"를 회의 발언까지 넓히면 실행 중 `KeyError`가 난다. 점괘 공개는 무당(플레이어) 전용이라 성향별로 만들어도 쓸 경로가 없다. 행적 진술은 엔진이 ID로 찾아 사실 문장으로 쓰므로 성향 말투를 넣을 자리가 아니다. 검사 스크립트 첫 판은 없는 성향 ID를 가진 템플릿에서 표를 만들다 `KeyError`로 멈췄다(Codex 리뷰 지적).
- 원인: 엔진은 회의 발언에 `format(target=…)`, 캐묻기 대체 문장에 `format(fact=…)`만 넘기고, (행동 유형, 반응)이 맞는 첫 공용 템플릿의 `variants[0]`만 쓴다. 공용 해명 `t_explain`은 캐묻기 사실 문장으로도 쓰인다. 표 작성 함수는 성향 목록에 있는 열만 미리 만들었다.
- 대응: PM 세션 답(11/6)에 따라 `{fact}` 필수는 캐묻기 반응만, 점괘 공개·행적 진술은 공용 1개 + 변형 2개로 두었다(원본 문구 변경은 PM). 공용 템플릿의 ID·선택 필드·순서는 그대로 두고 성향별 템플릿을 더했으며, 엔진 호출 기준 쓰임별 허용 자리표시자 표로 검사한다. 없는 성향은 열을 더해 세도록 고치고 테스트를 추가했다.
- 결과: 템플릿 11 → 47개(성향별 36), 필수 조합 누락·중복 0건, `{fact}` 누락 0건, 자리표시자 오탈자 0건, 최소 변형 2개. 증빙 [`docs/evidence/E-06-01.md`](../evidence/E-06-01.md)

### E-06-07 LLM 벤치마크
- 문제: 시험 실행에서 세 가지가 어긋났다. Kanana-2-3B는 모델 로드 뒤 채팅 템플릿에서 `TemplateSyntaxError: Encountered unknown tag 'generation'`으로 멈췄다. Qwen3-4B 가중치 메모리는 파일 크기(2.50 GB)보다 큰 4,046 MiB로 나왔다. 지연은 생성보다 프롬프트 처리(약 180 토큰에 5~10 s)에서 대부분 나왔다.
- 원인: Kanana 템플릿은 HF 학습용 태그 `{% generation %}`를 쓰는데, 일반 jinja2에는 이 태그가 없다. 가중치는 llama.cpp가 파일 매핑(`CPU_Mapped` 2,363 MiB)과 AVX2용 재배열 사본(`CPU_REPACK` 1,683 MiB)을 따로 로그에 남기는데, 이 둘을 한 값으로 더했다. 출력이 짧아(평균 10~22 토큰) 프롬프트 처리 비중이 크다.
- 대응: `generation` 태그를 본문 그대로 통과시키는 jinja 확장을 넣고 테스트를 추가했다. 가중치는 `weights_mib`(매핑)·`weights_repack_mib`·`weights_total_mib`로 나눠 기록했다. Codex 리뷰 지적에 따라 생성 실패가 있으면 결과를 쓰지 않게 했고, 다른 기기 결과는 측정 커밋이 같을 때만 받게 했다. 프롬프트 처리 비중은 보고서에 적어 E-07-07(프롬프트 길이)과 E-08-09(접두어 재사용)로 넘겼다.

### E-07-06 LLM MVP 제출 (코랩 노트북)
