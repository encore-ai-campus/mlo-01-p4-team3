### D-08-02 CTR·페이싱과 시나리오

- 문제: 기존 serve는 사전 CTR만 사용하고 페이싱·탐색 하한을 적용하지 않았다. 평가 6천 요청의 시나리오 2 한 시드는 최종 CTR 오차 22.58%였다. 기존 개발 DB 적용·광고 서버 기동이 자동 승인 검토에서 차단됐다.
- 원인: 확정 집계·버전 저장/재적재 연결이 없었다. 작은 시드별 소재×지면 표본의 변동이 있었고, 캠페인 이동 이력은 소재별 사후분포를 덮어쓸 수 있었다. 승인 검토는 기존 공유 DB·서비스 변경 범위의 명시적 승인이 부족하다고 판정했다.
- 대응: 전체 확정 셀을 캠페인 이동 이력까지 소재×지면으로 재합산하고 멱등 버전·60초 캐시·5분 제어를 연결했다. 6천 요청 결과를 보존하고 같은 분포/시드에서 1만2천 요청을 측정하며 온라인 오차도 별도로 보고했다. 실제 서비스 검증은 기존 테스트 스키마에서 수행하고 개발 DB 적용·기동 명령은 승인 대기로 남겼다.
- 결과: 11/9 B/D Daphne와 격리 MySQL로 세 지면의 실제 serve·웹소켓 비콘·클릭·랜딩을 통과했다. 요청 ID 12건과 serve ID 3건을 대조하고 아웃박스 9건을 확인했다. 검증기의 HTTP 로그 필터 오류를 수정 후 전체 재실행했다. 웹 원본의 serve_id 필드가 없어 대조 표에서 보완한 사실과 실제 gold/B 인계 미충족 항목은 [D-08-02 증빙](../evidence/D-08-02.md)에 기록한다. 결론은 알고리즘·회계·제어 루프 동작 검증이다. app-01 검증 프로필이 운영과 같은 Mongo DB를 가리켜 시험을 거절했다. loopback의 별도 Mongo replica set과 임시 SQLite 계정 DB로 격리했다. 시험 패키지의 콘텐츠 파일 누락을 보완한 뒤 정상 5분과 장애 4종 각 5분을 완료했다. 게임 API 15,000건의 오류는 0건이지만 장애별 p95 증가 542.802~666.232ms로 실패했다. 실패 클릭의 홈 복귀 경로에서 게임 상태 조회가 약 11배 늘었다. 보완 전 B-08-03 조건 2는 미충족이었다. 홈 복귀를 경량 안내로 바꾼 dev 44a6206으로 동일 10명·5분 × 5구간을 재시험한 결과 홈 복귀 0건, 상태 조회 구간당 3,000회, 게임 오류 0건, p95 증가 −40.240~−14.249ms로 조건 2의 측정 기준을 충족했다. C 실제 기준선·환입 후 대사는 모두 불일치 0건이다. 실제 Delta 집계로 CTR 3행·페이싱 11행을 저장하고 재실행 중복 방지, 61초 뒤 서비스 재시작 없는 새 버전 반영, 세 지면의 후속 이벤트 9건 버전 고정과 확정 과금 0건을 확인했다. 조건 7의 실제 C 입력 전송은 11/9 13:56 KST였다. 보호 설정·무인 sudo 제약에 따른 운영자 수동 실행과 실제 B/C 연결 경로 확인, 시스템 Python·실행 ID 보완 및 B 장애 재시험의 병목을 기재했다. 11/9 사용자가 지연 이력을 보존한 완료 판정과 PR 제출을 승인했다.

### D-05-01 의도 기준선과 인물·근거 매칭 v0
- 문제: 다중 의도 문장 `훈장은 수상하지만 머슴은 결백해`에서 첫 절이 옹호로 분류됐다. 인용 질문형을 규칙으로 해석할 때도 다른 라벨의 최대 확률이 점수로 남을 수 있었다.
- 원인: 연결어 `하지만`을 통째로 제거하면서 `수상하다`의 서술어 어미를 잃었다. 강제한 라벨과 모델의 최대 확률 라벨도 항상 같지는 않았다.
- 대응: 연결어를 분리할 때 `하다`를 보존하고, 인용 질문형에는 해당 라벨의 확률을 사용한다. 실제 해석기로 기존 계약 시나리오 3개와 분류·매칭·문맥·검증 테스트를 실행한다. 공유 포트와 엔진 스키마는 수정하지 않고, 의심 이유 질문의 언급 인물은 기존 `Command.target`, 수신자는 `Command.addressee`에 보존한다.
- 결과: 실제 구현 테스트와 측정값은 [D-05-01 증빙](../evidence/D-05-01.md)에 기록한다. 학습·평가의 원본 계보를 분리하고 낮은 기준선 성능도 그대로 보고한다. `tools/`의 표준 라이브러리 의존 규칙에 따라 벤치마크 CLI만 `tools/perf/`, ML 평가 실행은 `intent/evaluation.py`에 둔다. 샌드박스 임시 폴더 권한 때문에 실패한 기존 테스트는 같은 명령을 샌드박스 밖에서 재실행한다.

### D-05-02 BERT 후보 확인
- 문제: 최초 Hugging Face Xet 방식 가중치 전송이 진행되지 않았고, KLUE-RoBERTa-small 개별 모델 카드에는 라이선스가 없었다.
- 원인: 다운로드 중 가중치 임시 파일과 로드 시작 로그만 남고 추론으로 진행하지 않는 것을 확인했다. KLUE API의 라이선스도 null이며, 공식 프로젝트의 CC-BY-SA-4.0과 개별 가중치 조건을 같다고 확정할 수 없었다.
- 대응: 이번 측정용 자식 프로세스만 중지하고 일반 HTTPS로 재시도했다. KoELECTRA는 공식 PyTorch 가중치를 weights_only로, KLUE는 safetensors로 로드했다. 양쪽을 동일 CPU 조건으로 실측하고, 라이선스를 명시한 KoELECTRA-base-v3를 선택했다. 제출 검사에서 `HF_HUB_DISABLE_IMPLICIT_TOKEN` 설정이 키 이름 때문에 비밀정보로 탐지됐다. 설치된 `huggingface_hub`의 `constants.py`·`utils/_headers.py`에서 인증 토큰 자동 전송을 끄는 불리언 설정임을 확인하고, 저장소 규칙대로 `tools/secrets_allowlist.txt`에 해당 파일·키만 사유와 함께 등록했다.
- 결과: 두 후보 각각 추론 200회와 40문장 표본 전체 미세조정 10 step 완료. p95는 KoELECTRA 154.527ms, KLUE-small 48.012ms, 1,000문장 1 epoch 예상은 각각 341.669s/177.298s였다. 표본·외삽 방법·RSS 정의·라이선스 근거는 [D-05-02 증빙](../evidence/D-05-02.md)에 기록했다.

### D-06-02 광고 원장
- 문제: 기존 메모리 원장에서 날짜 경계 환입 뒤 일 합계 -1밀리원을 재현했다. 로컬 MySQL 전환 검증에서 자정 귀속일 불일치와 Kafka 로컬 재시험 오류를 확인했다.
- 원인: 기존 캠페인 공통 나머지가 과거 날짜의 환입액에 영향을 줬다. D는 UTC 날짜, C는 Asia/Seoul 날짜를 기준으로 삼았다. 로컬 브로커는 IPv4로 열려 있지만 Windows에서 브로커가 광고한 localhost가 IPv6로 먼저 해석됐다. 토픽이 이미 있는 재시험에서는 관리자 클라이언트에 빈 생성 목록도 넘겼다.
- 대응: PM PR #238의 CPM 건별 내림·원과금 반대 부호 환입 기준을 MySQL에 적용했다. 귀속일은 C와 같은 Asia/Seoul로 바꾸고 회귀 시험을 추가했다. 루프백 Kafka 연결은 IPv4로 지정하고 누락 토픽만 생성한다. pending은 만료 작업자가 자동 재판정하고 이벤트별 최초 수신 시각을 사용한다. 재사용한 서비스는 새 응답의 serve를 저장하고 클릭 처리 순서가 뒤집혀도 마지막 수신 시각을 후퇴시키지 않는다. Creative 표시 메서드를 복구했다. PM 결정 전 검토 기록은 커밋 `4490172`에 보존했다.
- 결과: 실제 MySQL·Kafka 테스트 37개 통과. 100건 경합 중 10건 승인, 예산 사용 100밀리원, 동시 환입 24건 중 1행을 확인했다. 로컬 Kafka는 4건 수신·3건 고유, 재판정 2건의 환입 1행, 만료 작업 재시작 후 해제 1건이다. 후속 확인에서 ad-01의 작업자 3개가 웹과 분리돼 실행 중이며 C-08-02 시험의 실제 환입 1건과 재대사 불일치 0건을 확인했다. [D-06-02 증빙](../evidence/D-06-02.md) 참고.

### D-07-02 씐 자 확률 모델 첫 학습·평가
- 문제: 기존 로컬 환경에 LightGBM이 없었고, 이벤트 변환·감사 초안이 완료 판과 캐묻기 반응을 실제 형식대로 처리하지 못했다. 독립 검토에서 음성 후보 누락·존재하지 않는 투표 대상·결정 정책 불일치·진실 시각 역순을 재현했다. 11/8에는 전략 평가의 seed 중복 허용과 routine의 합법 폴백 처리, 최신 dev 테스트의 PyMySQL·Prometheus 의존성 누락을 확인했다.
- 원인: 현재 `finish()`는 `completed`를 발행하지 않으며 반응은 `legal_kinds=[]`에서 `kind=react`로 기록한다. 후보의 부분집합 검사와 기존 합법성 검사만으로는 대상·버전·시각 경계를 모두 검증하지 못했다. 사용자 VM의 시스템 Python 경로에 네 패키지가 없었고 venv용 ensurepip도 누락됐다. venv 패키지 보완 뒤에는 PySpark wheel 생성 중 Errno 122(할당량 초과)로 중단됐다.
- 대응: 분리된 worktree·Python 3.14 환경에서 종료+진실 인접·시각 순서·공개 기록 기준 후보 전체를 검증한다. 기존 `legal_problem`·`vote_conflicts`에 대상·정책 검사를 더했다. 학습과 별도 평가의 게임·seed 중복을 거부하고 실제 새 전략을 선택한 밤 이후 관측을 분리한다. 폴백은 실제 선택 횟수로 공개하며 필수 의존성은 이 작업 환경에만 지정 버전으로 설치했다.
- 결과: 로컬 `rule-v0` 200판과 전략 평가에서 합법 행동·마을 추론 위반은 각 0건이다. VM은 venv 보완과 홈 TMPDIR 재시도 후 사용자 직접 실행(11/8 20:38:12 KST)에서 Python 3.14.4와 지정 패키지 4개 import에 성공했다. dev PR #267의 결정에 따라 C의 `baseline-0` export를 원본과 대조해 D 특징으로 바꿨다. Windows가 SQLAlchemy 2.1.8 확장 DLL을 차단해 이 실행 전용 경로에 동일 버전의 순수 Python wheel을 설치했다. 재실행에서 Delta 14,460행의 두 모델 학습과 MLflow 저장을 확인했다. 최신 학습·파이프라인 테스트 42개가 통과했다. [D-07-02 증빙](../evidence/D-07-02.md)
### D-06-03 합성 광고 트래픽 v2
- 문제: 구 생성기는 서버 HTTP 대신 직접 경매했고, 합성 serve·확정 이벤트 ID에 실행 구분이 없었다. 임의 토큰은 no_serve가 아니라 bad_signature이며 작은 5% 표본은 4종 공격을 모두 만들지 못했다.
- 원인: 정답 모델과 생성·경매가 한 객체에 있었고 온라인 서버는 UUID를 발급했다. no_serve는 정상 서명·미만료·serve 부재와 최초 수신 뒤 2분 유예를 모두 만족해야 한다. 클릭 비율은 정수 표본으로 반올림된다.
- 대응: 정답 모델만 공용 함수로 추출해 기존 난수 순서를 유지했다. 생성기는 표준 라이브러리 HTTP 클라이언트로 기존 Django API를 호출하고, 별도 시험 프로세스의 표준입력으로만 시간·정상 서명 orphan 토큰을 제어한다. 합성 serve ID는 실행 ID 포함 요청 ID 앞부분·해시와 syn: 접두어를 사용해 실제 serve UUID와 격리한다. 검토에서 요청 ID를 serve ID로 그대로 쓰면 실제 serve를 덮어쓸 수 있음을 공격 테스트로 재현해 수정했다. 회귀에는 고정 CTR 입력, 수용 측정에는 원래 CTR 10,000회 표본을 사용한다. 시험 중 소스를 수정하면 재현 해시가 달라지므로 최종 소스로 재실행한다.
- 결과: 시나리오마다 실제 HTTP serve 10,000회에서 무효 클릭은 0/4/18건, 무효 과금과 재전송으로 인한 추가 예약·과금은 각각 0건이었다. 세부 판정과 재현 결과는 [D-06-03 증빙](../evidence/D-06-03.md)에 기록한다. D-05-03 문서 검사에는 기존 다섯 번째 글머리표 오류가 남아 있다.

### D-10-01 재학습과 롤백
- 문제: 첫 격리 실행의 Git 소유권 검사, SQLite 연결, 체크포인트 후보 등록에 실패했다. PR 전 리뷰에서 봇 보정의 중단 판 제외 누락도 확인했다.
- 원인: 작업 사본과 실행 계정의 소유자가 달랐다. Windows 실행 정책은 SQLAlchemy 2.1 네이티브 확장을 차단했고, MLflow 3의 `runs:/` 등록은 체크포인트에 없는 MLflow 모델 메타데이터를 찾았다. 보정 필터에는 동의·삭제·부하 조건만 있었다.
- 대응: 실행별로 사본 경로만 Git 신뢰 목록에 지정하고 별도 SQLAlchemy 2.0의 순수 Python 경로를 사용했다. 일반 체크포인트 등록은 아티팩트 URI와 기존 run ID로 버전을 생성하도록 했다. 보정에는 스냅숏 안의 유효한 종료 이벤트를 요구했다.
- 결과: Git 기준 SHA와 격리 SQLite를 검증했다. 등록 재시도는 같은 후보 버전 1과 run ID를 반환했다. 중단·마감 이후 종료 판 제외 테스트와 종료 합성 입력 재측정도 통과했다. [D-10-01 증빙](../evidence/D-10-01.md)

### D-10-02 맥락 CTR·페이싱·CPC 자동 입찰
- 문제: 격리 Spark의 첫 실행이 마스터 호스트 이름을 해석하지 못했고, MLflow는 SQLAlchemy 네이티브 DLL 로드에서 중단됐다. 광고 HTTP 회귀에서는 기존 관리자 폼 2건과 경매 픽스처 7건에 새 입력과 호출 인수가 영향을 줬다.
- 원인: 네트워크를 끈 Docker의 임의 호스트 이름과 Windows 애플리케이션 제어 정책이 각각 Spark·SQLAlchemy 초기화를 막았다. 새 입찰 하한을 필수 필드로 두었고 기존 `rank_ctr` 대체 함수에 새 인수를 넘겼다.
- 대응: 컨테이너 호스트 이름을 루프백으로 고정하고 같은 버전의 순수 Python SQLAlchemy를 해당 실행의 `PYTHONPATH`에만 넣었다. 입찰 하한 미입력은 1밀리원으로 처리하고 기존 경매 호출 인수를 복원했다.
- 결과: Spark는 확정 CTR 학습 576행과 대사 불일치 0건을 기록했다. 시나리오 6 최대 CTR 상대오차는 3.16%이며 MLflow에 후보를 등록했다. 재시험과 버전 전환은 [D-10-02 증빙](../evidence/D-10-02.md)에 기록했다.
