# C-11-01 실제 스택 장애 복구 시험

- 커밋: 38abc0d42eea8897749b60fb084c341ed966193b
- 작성자(흐름): C
- 환경: 네 장애는 운영 후보 38abc0d, 추가 성능은 별도 전체 후보 79da6f1·실제 엔진/DB/광고와 두 Daphne+Caddy. 합성 계정·게임/광고 load_test 표식.
- 상태: 부분 완료. 네 장애 전량 대사와 광고 폭주·CPU 보호 통과. DB 통신 지연의 p95 증가 실패, 공유 MySQL 승격과 새 LLM 서빙 장애 검증은 미완료다.

## 명령

```sh
# 정지 대상 호스트에서 자동 복구를 먼저 준비한다.
sudo systemd-run --unit="$RECOVERY_UNIT" --on-active=90s /bin/systemctl start "$TARGET_UNIT"
sudo systemctl stop "$TARGET_UNIT"
# Spark 강제 종료 시험은 정상 배치 commit 확인 후 수행했다.
sudo systemctl kill --kill-whom=all --signal=SIGKILL paldo-bronze
# 실제 API로 합성 판을 진행한 뒤 명시적으로 재기동한다.
sudo systemctl start "$TARGET_UNIT"
sudo systemctl stop "$RECOVERY_TIMER"
python -m tools.reconcile_game_events --mongo "$PRIVATE_MONGO_METADATA" --published "$PRIVATE_KAFKA_METADATA" --bronze "$PRIVATE_BRONZE_METADATA" --out "$PRIVATE_RESULT"
```

## 출력

각 장애 전에 합성 판을 시작하고, 장애 동안 실제 HTTP 게임 명령으로 완주했다. 판당 15회씩 총 60회에서 HTTP 오류는 0건이었다. 입력·세션·DB는 실제 스택을 사용했고 수집 이벤트에는 load_test=true를 확인했다. 웹 전용 포트는 시험 뒤 종료했고 합성 계정 4개를 비활성화했다. 인증 세션 4개와 복사 인증 파일 2개를 제거했다.

| 장애 | 주입과 복구 | 정지 전 시각~active 확인 | API 요청/오류 | 결과 |
|---|---|---|---|---|
| Kafka 한 브로커 | 3브로커·18파티션 ISR 3 확인 후 한 노드 정지·복구 | 07:51:09~07:51:30 KST, 21초 | 15/0 | 완주 |
| Mongo Primary | Primary 식별 후 정지, 다른 노드에서 판 진행, 원래 노드 재합류 | 07:55:51~07:56:25 KST, 34초 | 15/0 | 완주 |
| 광고 서버 | PJ4 광고 unit 정지 후 게임 진행·광고 복구 | 07:59:50~08:00:09 KST, 19초 | 15/0 | 완주 |
| Spark | 공식 Bronze 강제 종료 후 자동 재시작, 같은 checkpoint 재개 | 08:07:40~08:08:01 KST, 21초 | 15/0 | 완주·재적재 대조 통과 |

위 시간은 운영자 기록의 정지 전 시각부터 active 확인까지 측정 구간이며, 별도 장애 감지 시간과 자동 재선출 소요만을 분리 측정한 값은 아니다. 복구 시간 합격선은 P-13 인계를 따른다.

Mongo에는 네 판이 각각 95개의 이벤트를 가졌고 미발행은 0건이었다. Kafka 380건을 전량 회수하고 공식 Delta와 대조해 고유 수·연속 seq·본문 hash가 일치했다. Delta 누락·원본 중복·hash 불일치는 모두 0이다.

사전 점검 중 공식 Bronze가 `human_identity_missing`으로 재시작을 반복함을 발견했다. 일반 판의 `session_id=null`을 거부한 오래된 조건을 [수정 PR #371](https://github.com/encore-ai-campus/mlo-01-p4-team3/pull/371)로 복구했다. 같은 checkpoint에서 batch 135·136의 commit이 새로 완료된 뒤 강제 종료 시험을 진행했다.

MySQL Replica의 `pj4` 채널은 IO/SQL Yes, 지연 0이지만 공유 PJ3 기본 채널은 IO No·오류 13114였다. 상세 오류는 원본이 필요한 binlog를 이미 제거했다는 내용이며 누락 구간은 634개 트랜잭션이다. 전체 인스턴스를 승격하기 전에 누락분/백업 복구·fencing·되돌림 검증이 필요해 시험하지 않았다. GTID 건너뛰기·PJ3 덮어쓰기·복제 채널 재설정은 수행하지 않았다. 이번 동결 후보의 게임 경로는 템플릿 응답이다. 오후 dev에 추가된 E-11-13 LLM 서빙의 정지 검증은 별도 미실행이다.

## 이력 조회 병목과 비교 시험 통제

최초 보호 시험은 같은 합성 계정을 반복 사용해 구간마다 완료 판 이력이 늘었다. 또한 웹 한 프로세스로 측정했다. 이후 두 웹+Caddy 단계 계측에서 `load` 누적 p95 1202.336ms와 게임 API p95 1368.694ms를 관측했다. 새 판 시작 경로가 진척의 모든 판을 하나씩 읽고 상태·진실을 복원하는 구조를 확인했다. 따라서 이 실행들의 지연 증가를 광고 장애의 인과 효과로 판정하지 않는다. 원 기록은 [이력 누적 진단](perf/C-11-01/protection_single.json)과 [두 웹 단계 진단](perf/C-11-01/protection_dual.json)으로 보존한다. 정식 비교는 같은 운영 소스·두 웹+Caddy·구간별 새 합성 계정·같은 요청 속도로 다시 수행한다.

독립 초안 `4ca94e4`를 검증한 뒤 오후 dev에서 같은 목적의 기존 구현을 확인했다. 최종 PR은 중복 메서드를 제거하고 dev `92aece2`의 `MongoGameRepository.unfinished_open_game_ids`와 명시적 `GameService.find_open_games` 조립을 채택한다. 진척의 시작 순서·삭제된 판 건너뜀·회차 판 제외를 유지하고, 소유권·중단·CAS는 기존 경로를 사용한다. 웹 소스의 새 운영 배포는 하지 않았다. 성능 검증은 초안이 포함된 전체 격리 후보 `79da6f1`로 고정했으며 최신 dev의 새 LLM·화면·모델 전체 검증으로 확대하지 않는다.

최신 dev의 조회를 실제 Mongo의 고유 일회용 컬렉션에서 재확인했다. 완료 판·일반 진행 판·회차 판과 없는 ID를 섞은 동일 이력에서 기존 경로 203번 find·3102.049ms, 일괄 조회 한 번 find·2.861ms였고 결과 ID와 순서가 같았다. 이는 해당 조회만의 한 번 측정이며 전체 API p95가 아니다. 운영 게임 문서는 바꾸지 않았고 시험 컬렉션을 제거했다. 조립·기존 저장소 회귀 3개와 일반 판 시작·중단 Django 회귀 35개가 통과했다.

## 게임 경로 보호 최종 실측

같은 격리 후보 `79da6f1`·Daphne 두 개·loopback Caddy round-robin, 구간별 새 합성 계정 네 명, 초당 한 게임 명령·각 180초다. 실제 엔진·Mongo·계정 MySQL·내부 광고 HTTP를 사용했다. 운영 30명 성능 또는 최신 모델 추론 성능의 증빙은 아니다. 아래 값은 [한도64 결과](perf/C-11-01/protection_candidate64.json)에 있다.

| 구간 | 게임 요청/오류 | API p95(ms) | 정상 대비 증가(ms) | 판정 |
|---|---:|---:|---:|---|
| 정상 광고 | 720/0 | 374.067 | 0 | 기준선 |
| 광고 DB 목적지의 쿼리 왕복 통신에 3000ms 지연 | 720/0 | 558.287 | 184.220 | 실패(50ms 초과) |
| 광고 요청 10개 worker, 실제 요청량 10.069배 | 718/0 | 423.511 | 49.444 | 통과 |
| 노트북3 CPU 압박 | 720/0 | 396.898 | 22.831 | 통과 |

노트북3은 실제 호스트의 논리 CPU 16개 중 14개 worker를 낮은 우선순위로 240초 실행했고 측정 중 CPU 49~50%를 확인했다. 모든 게임 측정 구간을 포함했다. DB 지연은 광고 VM에서 실제 MySQL 목적지·TCP 3306에만 적용했다. 자동 복구 타이머를 먼저 만들고 수동 finally 복구로 기존 pfifo_fast의 bands/priomap을 재확인했다.

한도40 후보의 광고 부하에서 게임 HTTP 500 한 건과 광고 오류를 발견했다. 예외는 계정 SQL `OperationalError`였고 서버 접속 한도40·최대 사용41·한도 초과 누적525를 확인했다. 메모리 여유를 확인해 원값을 보호 백업하고 64로 시험 적용한 뒤 위 구간을 반복했다. 접속 초과 카운터는 525에서 늘지 않았고 메모리 여유 2112MiB·서비스 active를 확인해 `SET PERSIST`로 유지했다. 재시작과 스키마·계정 변경은 없었다. [용량 기록](perf/C-11-01/mysql_capacity.json)

이 조정 후에도 DB 지연 시 증가184.220ms는 실패다. 계정 SQL 누적 p95도 정상150.998ms에서213.062ms로 커졌다. 저장소별 p95는 합산하지 않는다. 원인을 단정하거나 전체 기준 통과로 처리하지 않으며, 계정 DB/웹 요청 경계의 추가 분석이 남는다. [한도40 실패](perf/C-11-01/protection_candidate40.json)와 [동결 소스 새 계정 비교](perf/C-11-01/protection_frozen_fresh.json)도 보존했다.

모든 시험 뒤 합성 계정48개 비활성화·로그인 세션48개 삭제·미사용 합성 회차48개 제거·인증 복사본13개 제거를 확인했다. 시험 웹 두 개와 시험 프록시를 종료하고 CPU 예약 작업을 제거했다. 게임 이벤트 증빙과 원본 실패 기록은 보존했다.
