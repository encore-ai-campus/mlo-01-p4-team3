# C-08-04 콘텐츠 대조·사용자 테스트 준비
- 커밋: 46eeb1add7f6602c84c7000d16ffd5b0f676a344
- 작성자(흐름): C
- 환경: 2026-11-08~10 실제 PJ4 VM, Python 3.14.4.
- 상태: 부분 완료. 아래 미완료 조건을 유지하고 Refs PR로 제출한다.

11/8에는 운영 paldo_web의 content-1.0과 후보 5315516의 bundle을 같은 DTO로 읽고 정규 직렬화 SHA를 대조해 일치했다. 11/9에는 dev 4e5c703의 content-1.0.1이 운영 Mongo에 아직 없음을 실제 조회로 확인했다.

**조건 2·6 운영 확인:** 11/10에는 실제 배포된 후보 `46eeb1a`를 유지했다. 10:57부터 두 Daphne와 Caddy 2.11.9가 활성 상태였고 아웃박스도 같은 후보 경로에서 동작했다. 두 포트의 `/healthz`와 `/metrics`는 모두 200, CA 검증을 켠 HTTPS 홈은 200, 익명 wss 업그레이드는 101이었다. 두 로그 파일이 각각 생성됐고 고정 Host relay 적용 후 Prometheus의 `web-1`과 `web-2`가 모두 `up=1`이었다. 태그 SHA 대조와 인증된 일반 판 시작의 별도 검증은 대기다.

**미완료 조건 3:** 4th_private 실제 전달 위치를 로컬·접근 가능한 GitHub 저장소·연결 Drive에서 찾지 못했다. 경로를 확인하기 전에는 계정을 만들지 않았고 자격정보를 다른 곳에 기록하지 않았다. reader 도구의 경로 우회/덮어쓰기 guard와 dev/main 거절은 단위 시험했다. 운영 read·쓰기 거절 code13은 **아직 실행하지 않았다**.

**미완료 조건 4:** PM #267의 D 접속 전달을 추가 반영했다. 광고 DB·TLS·Garage 공용 설정의 보호 경로와 pj4/ 쓰기 금지, D 읽기 prefix를 정리한 인계 초안은 저장소 밖에 있다. 실제 D가 접근 가능한 전달 위치와 수신 확인은 미완료다. 증빙에 계정 원문이나 보호 경로를 복사하지 않는다.

11/9 사전 검증에서 운영 설치본 Caddy 2.6.2가 `health_fails`를 인식하지 못했다. 별도 바이너리 v2.11.8로 후보 Caddyfile의 운영 환경값 검증과 Daphne 템플릿 unit의 `systemd-analyze verify`를 통과했다. 격리 비교 앞단은 HTTP 스킴과 loopback bind를 명시했다. Caddy 공식 패키지 2.11.9는 저장소 서명·패키지 SHA-256을 검증한 뒤 기존·후보 설정을 모두 검증했다. 이전 Caddy 패키지와 설정은 복구용으로 확보했다.

11/9 app-01 사전 검증에서 2프로세스 p95는 197.693ms, 1프로세스는 390.770ms였다. 11/10에는 실제 운영 후보 `46eeb1a` 소스의 격리 Daphne·Caddy에서 InMemory, 스크립트 엔진으로 각 30명·3분을 측정했다. 2프로세스 p95는 218.762ms, 1프로세스는 400.064ms였다. 두 경우 모두 HTTP 5,400건, HTTP 오류 0건, 웹소켓 비콘 오류 0건이다. 2프로세스 명령 저장은 2,499건·2,481건으로 분산됐다. 별도로 실제 운영 두 대상의 5분 Prometheus p95 추정값은 712.5ms(요청 증가량 추정 약 163건)였다.

11/10 운영 Mongo에서 `content-1.0.1`이 조회됐고 실제 배포 후보 `46eeb1a`의 번들과 DTO가 일치했다. 두 Daphne가 읽는 웹 프로필에도 같은 콘텐츠 버전이 설정돼 있다.

조건 7은 후보에 `backfill_surveys` 명령이 있는지 테스트 서버에서 도움말로 확인했다. 격리 설문 테스트 6건과 마감 뒤 보충 이벤트 집계 테스트를 통과했다. 실제 보충은 11/10 18:00 KST 직후 실행하고 성공 후 스냅숏을 확보한다. 조건 8은 B-10-07에서 확정한 화면 설정과 E 요청이 필요하다.

```sh
python -m unittest tests.ops.test_user_test_ops -v
```
