## 11/9 잔여 조건5 HTTP 수신 검증

새 worktree `task/B-06-04-http-privacy`를 최신 dev에서 분리했다. 운영 코드·디자인은 변경하지 않았다. `test_accounts`의 기존 인증 시나리오를 재사용하고 기본 포트 시험과 별도 D HTTP 수신 시험으로 제공자만 바꾼다.

시험 순서: 초대 코드 오답 → 가입·동의 → 로그아웃 → 대문자 ID 로그인 → 세 지면 요청 → 녹화 게임 완주 → 종료 지면 요청 → 중복 가입 → 오답5회·잠금·없는 ID → 비로그인 광고401·호출 증가0 → 관리자 비밀번호 초기화 규칙 거부. 같은 실행에서 B 파일 로그·아웃박스·지표·광고 DTO를 확인한 뒤 D 수신 본문·헤더·파일 로그를 대조했다.

`ad_privacy_host.py`는 별도 루프백 프로세스에서 D의 원본 Django WSGI·뷰·AdService를 실행한다. 메모리 광고 저장소와 시험 캠페인만 주입하고 대상 제한은 시험 안에서 해제했다. HTTP 응답을 만들어 주는 B 대역 서버는 사용하지 않았다. D의 DB·광고 운영 설정은 변경하지 않았다.

- D 수신4건 모두200, 광고 제공4건. 본문은 B DTO와 정확히 일치하고 허용 헤더는 Host·Content-Length·Content-Type·X-Request-ID뿐이다.
- 별도 광고 UUID1개를 사용하며 계정 가명·세션 키·판 ID·쿼리 위조값·로그인 ID/대문자 ID·없는 ID·비밀번호/오답/초대 코드 등 인증 입력 검출0건. D 로그4건의 request_id도 수신·B 응답과 일치한다.
- SQLite 관련 회귀38건·26.677초:35건 통과·계정 정렬/행 잠금3건 건너뜀. 로그 `out/handoff/http-privacy-regression.log`.
- 격리 MySQL8.4.11 관련 회귀38건·33.214초 전부 통과·건너뜀0. 같은 주소 동시 가입6건 모두302·동시 로그인 실패5건 잠금도 포함한다. 로그 `out/handoff/http-privacy-mysql.log`.
