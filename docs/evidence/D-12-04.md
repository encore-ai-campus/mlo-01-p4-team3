# D-12-04 광고 운영자 관리 화면과 게임 웹 연동 검증

- 커밋: 6a1a18a2a4ba7eb98ae28fb547f1452d9afff9ab
- 작성자(흐름): D
- 환경: Windows 로컬, Python 3.14.6, Django 6.1.2, MySQL 8.4.11, Compose 프로젝트 `paldo-dev`. 전용 광고·시험 스키마와 전용 DB 사용자. 게임 웹은 격리 SQLite 인증·메모리 회차 저장소·녹화 게임, 광고는 실제 HTTP·MySQL 원장·저장 판정, 비콘은 실제 Daphne 웹소켓 중계를 사용했다.
- 상태: 로컬 구현·검증, B/E 공동 확인 대기

위 SHA는 검증한 구현을 담은 커밋이다. 브라우저 및 회귀 검증은 dev `3b25dc9`의 로컬 변경에서 실행했다. 측정 소스의 SHA-256은 [로컬 실행 JSON](perf/D-12-04/local-flow.json)의 `source_sha256`에 기록한다. 제출 전에 dev `c4f717c`를 반영하고 CSS 파일 끝 빈 줄 하나를 정리했다. 운영 광고 서버 설정·데이터는 사용하지 않았다. B의 그림 대조·로비/결과·비콘 및 클릭 중계와 E의 복기 화면 공동 확인은 대기 중이다.

## 명령

프로젝트 `requirements/web.txt`를 설치한 이 작업 공간의 `.venv`를 사용한다. 아래 명령은 격리 MySQL 연결 환경을 설정한 뒤 실행한다. 접속값은 Git 무시 경로 `out/d1204-runtime/connection.json`에서 프로세스 환경으로 읽었으며 출력·증빙에 넣지 않았다.

```powershell
python -m ads.manage test tests.ads.test_reporting tests.ads.test_admin_flow --noinput --verbosity 2
# 광고 전체 검사에서는 tests/ads/test_*.py의 모듈 이름을 모두 명시한다.
python -m ads.manage test tests.ads.test_http tests.ads.test_persistent_http tests.ads.test_mysql_ledger tests.ads.test_optimization tests.ads.test_privacy_cleanup tests.ads.test_workers tests.ads.test_worker_stack tests.ads.test_reporting tests.ads.test_admin_flow --noinput
python -m django test server.tests.test_ad_slots server.tests.test_assets server.tests.test_ad_identity_reads server.tests.test_ad_events server.tests.test_ad_client server.tests.test_ws --settings=server.paldo_web.test_settings --noinput
node server/tests/test_ad_slots_js.cjs
python -m tools.check_docs --task D-12-04
python -m tools.check_docs --diff origin/dev
python -m tools.check_structure --diff origin/dev
python -m tools.check_evidence D-12-04 --format
python -m tools.check_evidence D-12-04 --complete
python -m tools.precheck --quick --with-assets
git diff --check
```

브라우저 조립은 무시 경로의 `out/d1204-runtime/browser_run.py`·`game_host.py`·`browser.mjs`로 실행했다. 루프백 임의 포트에 두 서비스를 띄우고 현재 저장소의 관리자 폼으로 소재 기본 경로와 지면을 저장했다. 게임 브라우저에서 각 그림을 보이게 스크롤한 뒤 실제 가시성 타이머·웹소켓 ACK를 기다렸다. Chrome 원격 디버깅으로 두 폭·두 테마를 확인하고 캡처했다. 전용 게임 세션 쿠키는 광고 관리자 쿠키와 이름을 분리한 시험 설정을 사용했다. 생성한 웹·브라우저 프로세스는 검증 후 종료했다.

Kafka 통합은 Linux 컨테이너의 Python 3.14.4·Django 6.1.2·confluent-kafka 2.16.1과 별도 Kafka 4.3.2 브로커에서 실행했다. 시험 컨테이너는 브로커와 네트워크를 공유하고, 저장소는 읽기 전용으로 연결했다. `PALDO_ADS_TEST_KAFKA=127.0.0.1:9092`, 컨테이너 임시 로그 경로와 전용 MySQL 시험 스키마를 지정한 뒤 아래 명령을 실행했다.

```bash
python -m ads.manage test tests.ads.test_worker_stack.WorkerStackTests.test_real_kafka_replay_and_rejudge --noinput --verbosity 2
```

광고 전체 회귀에서 `ReserveConnectionTests.test_concurrent_serves_keep_budget_total`이 `AdSession` 동시 생성 중 MySQL 1213 교착으로 두 번 실패했다. `ads/infra/mysql_store.py`의 세션 잠금 행 생성을 배타 잠금 upsert로 수정한 뒤 관련 4개와 광고 전체를 다시 실행했다. 기존 동시성 시험의 40건 예약 합계가 일치했다. 로컬 `out/d1204-runtime/`에 최초 실패 로그 `ads-tests-first-concurrency.log`, Windows 회귀 로그 `ads-tests-final.log`, 공통 사전 검사 로그 `precheck-final.log`를 보존했다.

Windows 회귀에서 브로커 설정 없이 생략한 Kafka 통합 1개를 이어서 실행했다. Windows 애플리케이션 제어 정책이 클라이언트 DLL을 차단해 Linux에서 검증했다. 브로커 ACK 직후 발행기가 실패한 상황을 재현했으며, 재전송과 중복 재판정 후에도 환입은 1행이었다. 결과는 로컬 `out/d1204-runtime/ads-tests-kafka-linux.log`에 보존했다. 시험 종료 후 전용 시험 스키마와 임시 브로커가 정리됐다.
