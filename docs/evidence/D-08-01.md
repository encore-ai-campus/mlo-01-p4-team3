NPC별 계측은 엔진의 원래 clock을 감싸 첫 반환 시각과 100ms 마감을 정확히 기록하며 판정을 그대로 전달한다. 같은 snapshot ID에 포트 호출 시작/끝·어댑터의 실제 잠금 대기 시작/끝·엔진 결과·일반/결선 구분을 연결한다. 시각은 서버 monotonic 초이며 HTTP 요청의 UTC epoch/monotonic 기준점을 함께 남겨 변환한다. 즉시 폴백해 대기를 시작하지 않은 호출의 대기 시각은 null이다. 운영 설정은 시험 계측을 연결하지 않는다.

원본을 남기지 않은 11/10 추가 확인 회차의 관측은 18/2,552건(0.705%)이며, 공식 판정 회차에서 제외한다. 11/10 결과는 아래 이력과 로컬 원본에 보존했다. 11/11에는 사용자가 요청한 어제 시험 임시 서버 폴더 6개와 로컬·서버의 오래된 소스 압축본 8개씩을 사용 프로세스·절대 경로·날짜를 확인한 뒤 삭제했다. 로컬 수정은 dev 병합 전에 복구 zip과 git stash로 보호했다.

병합 후 기준 1회 직후 모델 켬 2회를 같은 커밋·모델·명령·시간·worker 구성으로 연속 측정한다. 모델 켬 두 회차가 모두 각 기준을 충족해야 통과한다. 시작한 모든 시도를 보존하며 기준 초과 회차가 나오면 추가 판정 재시도 대신 그 자료로 ②-a/②-b 선택을 요청한다. 새 묶음 등록·무효 판정은 PM 결정에 따른다.

## 11/10 공통 처리 최적화 후 동급 VM 재측정

사용자의 최적화·재측정 지시에 따라 **요구사항·계약 문서, 공개 API·공통 포트·JSON 스키마·계약 버전을 변경하지 않고** 구현 내부를 개선했다. `serde`는 dataclass 타입의 주석 해석·필드 정보만 최대 256종 재사용하며 입력별 검증과 새 결과 객체 생성은 유지한다. JSON 값·판 상태·진실·검증 결과를 캐시하지 않는다. 계약 회귀 162개, 엔진 회귀 221개, Mongo 조립·일반 판 시작·중단·계측 Django 회귀 47개가 통과했다. 격리 Mongo 8.0.34에서 실제 저장소 회귀 12개도 통과했다. 추가한 실제 Mongo 시험은 기존 전체 상태 조회 판정과 ID 조회를 비교하며 완료·회차·없는 판 제외, 순서·중복, 기본값 필드 부재, 다음 조회의 상태 갱신 반영을 확인한다. 타입 정보 재사용과 조회 연결은 수정 전 실패를 확인한 뒤 구현했다.

## 11/10 기준 API 지연·취소 요청 후속 분석

PM 결정 전 가능한 진단으로, 같은 날 저장한 연속 측정의 요청별 원본을 시작/명령으로 나눠 다시 대사했다. 기존 측정과 같은 nearest-rank p95를 사용했다. 서버에 새 부하를 보내거나 과거 측정값을 바꾸지 않았다.

| 요청 종류 | 기준 요청 수 | 기준 클라이언트 p95 | 모델 켬 요청 수 | 모델 켬 클라이언트 p95 |
|---|---:|---:|---:|---:|
| 새 게임 시작 | 392 | 2,445.675ms | 427 | 2,674.526ms |
| 게임 명령 | 4,541 | 1,483.547ms | 4,488 | 1,466.628ms |

기준 시작 요청의 Django `server_total` p95는 2,183.460ms, 요청 안의 저장소 `load` 누계 p95는 1,284.381ms, 엔진 `new_game` p95는 8.233ms다. 기준 명령 요청도 `server_total` p95 1,269.731ms로 높지만 엔진 `apply` p95는 39.510ms다. 각 p95는 서로 다른 요청에서 나올 수 있어 빼거나 합해 시간 비중으로 해석하지 않는다. 명령 요청도 느리므로 새 판 시작 경로만 개선해서 API 1초를 충족한다고 단정할 수 없다. 기존 계측 밖의 미들웨어/스케줄링 등 잔여 시간은 추가 분리가 필요하다.

코드에서 `GameService.start`→`unfinished_open_games`가 계정 진척의 과거 판 ID를 순회하고, `MongoGameRepository.load`가 완료 판도 전체 `GameState`·`GameTruth`로 역직렬화하는 경로를 확인했다. `serde._dataclass_from`은 매 dataclass 객체마다 `typing.get_type_hints`를 다시 호출한다. 원인 분리용 **로컬 모의 실험**에서 실제 규칙 v0로 완료한 판 하나를 읽기 전용 가짜 collection으로 반환하게 했다. 완료 이력이 1/5/10/20개면 완료 판 조회도 각각 1/5/10/20회이며, 10개 조회 프로파일에서 타입 해석이 1,760회 발생했다. 이는 서버에서 각 요청이 몇 판을 읽었는지 직접 센 자료는 아니다.

다섯 표본 평균에서 완료 이력 10개 순회는 145.750ms였고, 타입 정보만 실험 프로세스 안에서 최대 256종으로 캐시한 비교는 35.935ms였다. 20개는 398.783→64.954ms였다. 알 수 없는 필드·필수 필드 누락·잘못된 타입의 세 입력이 같은 `SchemaError`로 거부되는 것도 대사했다. **운영/공통 소스에 캐시를 적용하지 않았으며**, 이 Windows Python 3.14.6의 단일 프로세스 CPU 실험을 동급 VM 부하 합격이나 최적화 안전성 전체 증명으로 삼지 않는다. 공통 타입 해석 재사용과 완료 판 조회 축소를 최적화 후보로 전달한다. 전체 판 상태·진실 또는 사용자별 판 결과를 캐시하는 제안이 아니다.

모델 켬 오류 1건은 benchmark ID `54d8626118dd4fb6ac8af6c75c0f31a4`인 `/games` 시작 요청이다. 클라이언트 5,004.802ms, 같은 ID의 Caddy status 0·duration 5.004981528초를 확인했다. 같은 시각 웹 38543에는 `CancelledError`가 미들웨어의 async/sync 응답 경로에서 전파된 로그가 있다. 이 오류의 서버 응답 ID·단계 헤더가 없고 미연결 시작 완료 로그도 없어, 취소 traceback을 그 요청에 ID로 확정 연결하거나 특정 저장소 함수에서 5초를 썼다고 소급 확정할 수 없다. 클라이언트 5초 제한이나 합격 기준은 늘리지 않았다.

이 대사 공백을 다음 실행에서 메우도록 **시험용** `BenchTimingMiddleware`에 취소 시 `bench_request_aborted` 로그를 추가했다. 검증한 benchmark ID·서버 요청 ID·취소 종류·누적 단계 시간만 남기고 본문·쿠키·예외 원문은 기록하지 않는다. 취소를 다시 전파하고 요청 컨텍스트를 정리한다. 회귀를 먼저 로그 누락으로 실패시킨 뒤 계측 테스트 4개를 통과했다. 이 계측은 원래 연속 측정 이후 변경이므로 과거 source manifest와 원본은 그대로 보존하며 새 30명 부하를 통과했다고 주장하지 않는다.

PM에게 결정 요청할 범위는 ① ②-b와 공통 API 병목 최적화의 우선순위·담당·추가 시간, ② 공식 API 판정 지표/구간(현재 세 지표 모두 1초 초과, 기준 변경 없이는 그대로 미충족), ③ 운영 라벨·series 부재의 B-09-01/E-09-01 대사 범위다. ②-b는 잠금 대기를 줄일 후보로 유지하되, 공통 CPU 비용 개선만으로 폴백이 줄어드는지는 재측정 전까지 미확정이다. `87fddf9`와 이슈 open·PR 보류를 유지한다.

원본 분석은 `out/d08-01/paired-final/api-diagnosis.json`, CPU 모의 실험은 `start-history-probe.json`, 재현 스크립트는 `out/d08-01/diagnose_api.py`·`probe_start_history.py`다. 표준 계측 `docs/evidence/perf/D-08-01/api_diagnosis.json`에 분석 산출물 SHA-256을 남겼다.

## 11/10 PM 요청 기준·모델 켬 연속 진단

`87fddf970869f89fd2d7553e981089c86741ba70` 위에 시험용 계측만 보강했다. 실제 `ContentPolicyEngine`에 `suspicion=None`을 전달하는 기준 모드를 추가했으며, scripted 엔진이나 가짜 모델 기준선은 사용하지 않았다. 같은 nifi-01(2 vCPU·3,398 MiB)의 격리 Caddy·Daphne 2개·Mongo와 외부 WSL2 Ubuntu에서 동시 30명·3분 이상을 기준→모델 켬 순서로 연달아 실행했다. 모델 켬은 주 버전 `9bbee626f29b`와 이전 버전 `1afb8f051c4e`를 웹 프로세스마다 함께 로드했다. 같은 버전 worker를 늘리거나 NPC 배치 추론을 구현하지 않았다.
