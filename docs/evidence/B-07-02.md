### 실제 Mongo·TLS Kafka 후속 검증 (11/8)

- 수정 전 실제 Mongo 5개 시험 중 3개가 실패했다. 수첩 이벤트 append 뒤 보조 상태 쓰기 실패는 재요청 시 이벤트 2건이 됐고, append 응답 유실은 500이었다. 설문도 이벤트·보조 기록 사이의 실패에서 최초 내용을 고정하는 복구 계획이 없었다. 로그: `out/handoff/mongo-before.log`.
- B 응용의 독립 `effects` 저장에 마지막 참가자 저장 계획을 먼저 보존했다. 계획은 마스킹된 값·이벤트 봉투·고정 중복 방지 키를 갖고, append 후 상태를 저장한다. 읽기·재요청에서 미완료 계획을 복구한다. 수첩 A→B→A는 새 기록이며 같은 단계의 같은 입력은 한 건이다. 설문은 최초 응답/건너뜀을 복구하고 다른 내용은 409다. C 코드·계약·스키마는 바꾸지 않았다.
- 보조 기록은 같은 Mongo의 `state`·`effects` 독립 저장과 기존 임대를 사용한다. 실제 append 성공 직후 연결 응답 유실, 상태 쓰기 전 실패·성공 직후 응답 유실을 주입했다. 새 Python 프로세스에서 조회·재전송하고, 독립 프로세스 둘의 동일 수첩과 서로 다른 설문 경합도 실행했다.
- 태스크의 세 기록을 분리했다: 수첩 → 투표 직전 확신도 → 설문. 실제 Mongo 아웃박스 → C `Publisher`/`KafkaSender` → TLS Kafka `paldo.player` 순서로 수신했다. 정상 응답은 3건, 건너뜀도 논리 3건이다. 건너뜀 설문을 같은 event_id로 한 번 더 전송하면 원본 4건이 수신되고 C `plan_game_events`는 3건으로 중복 제거한다. 이미 저장된 event_id/hash로 다시 처리할 새 행은 0건이다. Kafka 전송 자체의 exactly-once를 주장하지 않는다.
- 정상 점수 4·2·5와 건너뜀 true·null 3개·빈 의견이 수신 본문에 그대로 있다. 내부 `_saved_context`·`comment_digest`와 개인정보 원문은 이벤트에서 0건이다. 최종 아웃박스 미발행은 0건, 두 판 각각 전체 24개 이벤트가 발행됐다.
- 로컬 Compose의 평문 Kafka에 맞춰 C의 TLS 필수 검증을 완화하지 않았다. 시험 전용 모듈로 Kafka 4.3.2에 상호 TLS·CA/hostname 검증을 구성했다. 초기 localhost의 IPv6 연결은 Docker의 IPv4 루프백 포트에 닿지 않아 간헐 실패했다. IPv6 실패·IPv4 성공 대조 뒤 로컬 설정에 `broker.address.family=v4`를 명시했다. 브로커·토픽·Producer 연결 준비는 측정 대상과 분리한다.

### 최신 dev 재검수 (`36a30cb`, 11/7)

PR #212(A-07-02)의 엔진 변경을 반영했다. 이전 `2d4a350` 이후 API·이벤트·태스크 계약의 변경은 없다. 반영 전 작업 파일을 저장소 밖에 백업했고, 반영 후 기존 변경의 SHA-256 일치를 확인했다. 위 커밋은 구현 SHA가 아닌 검수 기준 dev다. 최종 PR에서는 구현 커밋의 SHA로 갱신하고 PR 본문을 포함해 다시 검사한다.
