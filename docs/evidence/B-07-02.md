## 출력

### 투표 확신도 기록 누락 개선

다음 날 투표와 본투표→결선에서 같은 값(의심도 73·확신도 88)을 다시 저장하는 회귀 2개가 수정 전 모두 실패했다. 값만 비교하던 처리를 날짜·단계까지 비교하도록 수정했다. 같은 투표 안의 동일 재전송은 추가 이벤트 0건이고, 다음 날·결선의 첫 저장은 각각 1건이다. 내부 `_saved_context`는 보조 저장에만 보존하고 `notebook_updated` 이벤트 본문은 기존 `entries`·`vote_confidence` 두 필드를 유지한다. 이벤트의 날짜·단계·`paldo.player` 토픽, 화면 값 복원과 게임 버전 비소비를 함께 검증한다.

수정 후 수첩·설문·입력 검증·상호작용 시험 35개가 통과했다(3.210초). 다음 날은 녹화 판, 결선은 실제 `PaldoEngine`의 동점 시나리오로 확인했다. 로그: `out/handoff/B-07-02-confidence-before.log`·`out/handoff/B-07-02-confidence-after.log`. 기존 사전 검사가 놓친 투표 간 반복 저장을 이번 회귀로 보완했다.

격리 MySQL 8.4.11·Django 6.1.2에서 전체 서버 시험 120개가 건너뜀 없이 통과했다(46.999초). 시험 후 임시 MySQL 프로세스·데이터 디렉터리를 정리했다. 로그: `out/handoff/B-07-02-confidence-mysql-run.log`·`out/handoff/B-07-02-confidence-mysql-tests.log`. 계정·세션은 실제 MySQL이며 게임·보조 저장은 대역이다. UI 배치·입력 형식은 바꾸지 않았으며 이번 개선의 브라우저 재실행은 하지 않았다.

PR 초안을 포함한 사전 검사도 통과했다. `precheck: 통과 (구조·비밀·테스트·문서·증빙, 테스트 701개, base e360e85, 68초)`. 로그: `out/handoff/B-07-02-confidence-precheck.log`. 실제 Mongo·Kafka 보존 검증, 구현 커밋과 증빙 SHA 갱신은 남아 있다.

### 최신 dev 재검수 (`36a30cb`, 11/7)

PR #212(A-07-02)의 엔진 변경을 반영했다. 이전 `2d4a350` 이후 API·이벤트·태스크 계약의 변경은 없다. 반영 전 작업 파일을 저장소 밖에 백업했고, 반영 후 기존 변경의 SHA-256 일치를 확인했다. 위 커밋은 구현 SHA가 아닌 검수 기준 dev다. 최종 PR에서는 구현 커밋의 SHA로 갱신하고 PR 본문을 포함해 다시 검사한다.

Django 회귀 86개 중 83개 통과, MySQL 전용 3개 건너뜀(35.524초). 정상 설문·전체 건너뛰기, 동일 요청 재전송과 다른 내용의 409, 마스킹·이벤트 중복 방지를 메모리 대역으로 재검증했다. 결과는 out/handoff/review-36a30cb.log에 있다. 실제 Mongo의 재시작 후 보존과 Kafka paldo.player 수신은 미검증으로 남기고 Refs로 준비한다.
