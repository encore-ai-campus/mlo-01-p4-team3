## 인계와 제한

GameRepository는 collection을 주입받는다. B 조립에서 MongoGameRepository·MongoProgressRepository·MongoContentSource에 전용 컬렉션을 주입하고 공통 클라이언트의 기본 DB·TLS 연결은 PALDO_MONGO_URI로 설정한다. class import만으로 네트워크 연결·데이터 생성은 하지 않는다.

지표는 기본 Prometheus registry에 등록되므로 B의 기존 `/metrics`에서 수집할 수 있다. 측정은 실제 엔진 초기 상태의 순차 저장이며 동시 사용자 게임 API 부하 성능과 다르다. 원자 게임 문서는 Mongo 문서 용량 한도의 영향을 받으므로 Outbox 장기 보관·삭제 정책은 후속 운영 작업이다.

11/7 저장소 시험은 기존 허용 DB의 고유 컬렉션을 사용했다. 11/8 최초 설치 폴더의 기존 보호 관리자 파일을 찾아 정상 root 역할 인증을 검증한 뒤 전용 paldo_web DB·readWrite 앱 계정으로 분리했다. 기존 사용자 비밀번호·인증 설정·원본 데이터는 보존했다. 아래 전환 증빙은 앞의 저장소 벤치마크와 구분한다.


## 11/8 전용 DB 전환·운영 검증

```sh
python -m ops.provision_mongo --admin-profile "$PRIVATE_ADMIN_PROFILE" --ca "$PUBLIC_MONGO_CA" --seed "$MONGO_SEED_HOST" --replica-set "$MONGO_RS" --source "$OLD_APP_DB" --target "$DEDICATED_APP_DB" --app-user "$NEW_APP_ROLE" --profile-out "$PRIVATE_APP_PROFILE" --backup-dir "$PRIVATE_BACKUP_DIR"
# 합성 계정만 존재함을 확인, 웹 입력 정지 → Outbox pending 0 → 발행기 정지
# 같은 명령에 --apply 추가, 성공한 새 앱 프로필만 웹에 주입 → 웹/발행기 재개
python -m tools.reconcile_game_events --mongo "$PRIVATE_MONGO_METADATA" --published "$PRIVATE_KAFKA_METADATA" --bronze "$PRIVATE_BRONZE_METADATA" --out "$PRIVATE_RESULT"
python -m unittest tests.contract.test_mongo_isolation_guard -v
```

6개 컬렉션의 24문서·옵션·인덱스를 root 전용 확장 JSON/manifest로 백업하고 새 DB에 복사해 전량 hash를 대조했다. 관리자 프로필은 원래 Mongo VM에서만 읽고 웹에는 대상 DB readWrite 앱 프로필만 전달했다. 다른 DB 조회는 ERROR 13으로 거부됐다. 기존 DB/계정/인증 설정은 보존하고 새 설정 실패 시 원래 runtime으로 재개하도록 준비했다. 전환 중 실참가자는 없었고 자동 재개 타이머를 병행했다.

전환 후 content-1.0·기존 게임/회차·공개 HTTPS health 200·다른 물리 노트북 Chrome의 경고 UI → wss 101·Secure 쿠키를 확인했다. 같은 웹 호스트의 보호 합성 세션으로 새 게임을 완료했고 다음과 같이 새 전용 DB→Kafka→공식 Delta가 일치했다. 쿠키/관리자 비밀번호는 다른 호스트로 내보내지 않았다. 새 앱 자격정보만 보호 관리 경로로 전달했다. 임시 검증 웹/Caddy는 종료했고 운영 웹·Outbox·bronze는 재개했다.
