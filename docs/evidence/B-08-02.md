# B-08-02 프리셋 선택·8인 판 화면

- 커밋: 23f7f1c08b1207cc5057c3301d2f1293f4f92ec4
- 작성자(흐름): B
- 환경: Windows, Python 3.14.6, Django 6.1.2, 격리 MySQL 8.4.11, Compose MongoDB 8.0.34 Replica Set. 화면은 시험 전용 메모리 저장소·공개 녹화, 브라우저는 Chrome·Playwright 1.65.0.
- 상태: 실패

위 SHA는 최신 반영 dev 기준이며 이번 구현은 사용자 확인 전 미커밋이다. 최초 기준 `d7f73e0`에 PM 결정 PR #271의 `c15cbab`, 사용자 테스트 일정·집계 PR #272의 `9440d76`, C 광고 집계 PR #274의 `23f7f1c`를 순서대로 반영했다. 각 반영 전 작업 파일·스테이징 패치를 별도 백업하고 파일별 SHA-256으로 원본 보존을 확인했다. P-08에 따라 초기 공개값은 `base6`만 유지하고 8인은 화면 시험에서만 임시 공개했다. 이번 소스의 커밋 SHA는 커밋 승인 뒤 갱신한다.

로컬 구현·자동/브라우저 검증은 통과했다. 최신 일정에서는 B-08-02의 태그 대기를 제거했다. 현재 dev 빌드로 6인 1판을 공동 완주하고 발견한 화면·API 이슈의 수정 결과를 E가 재확인하는 조건이 남아 있다. 이 공동 확인은 아직 수행하지 않았으므로 PR은 `Refs #34`로 준비한다. 11/10 E-08-04의 태그 기반 테스트 서버 리허설 화면 확인은 B-09-03이며 이 태스크의 선행 조건이 아니다. 자동 시험을 공동 확인으로 대신하지 않는다.

## 명령

```powershell
python -B -m server.tests.record_large8
python -B server/manage.py test server.tests.test_preset_screens --settings=server.paldo_web.test_settings --noinput --verbosity=0
python -B -m out.handoff.run_pr_mysql
python -B -m server.tests.preset_render_bench
node out/handoff/preset-browser.cjs
python -B server/manage.py test server.tests.mongo_game_sessions --settings=server.paldo_web.mongo_test_settings --noinput --verbosity=0
python -B -m tools.precheck --pr-body out/handoff/B-08-02-pr.md
```

`run_pr_mysql`는 비공개 접속값을 출력하지 않는 로컬 보조 실행기이며 임의 포트의 격리 MySQL 8.4.11로 전체 `server.tests`를 실행한다. 운영/개인 MySQL은 변경하지 않는다. 실제 Mongo 팩토리 시험도 고유 시험 컬렉션을 정리한다. 공용 실행은 `python -B server/manage.py test server.tests --settings=server.paldo_web.mysql_test_settings --noinput`이다.

### 최신 dev 23f7f1c 반영과 PR 준비(11/9)

PR #274의 C 광고 집계 변경 13개 파일을 그대로 반영했다. 관련 계약·B 실행 코드와 겹치는 변경은 없었다. 작업 파일 31개와 스테이징 패치를 ZIP으로 백업한 뒤 fast-forward 반영했고, 31개 파일 모두 백업 SHA-256과 일치했다. 이번 증빙 갱신 외 B 실행·시험·픽스처와 서버·웹 라우팅·설계는 그대로이며 기존 문서가 현재 구현을 설명한다.

### 최신 dev 9440d76 반영과 공동 확인 기준 정정

### 브라우저 확인

경로: 인증 홈 → 여성/남성 초상 선택 → 게임 → 심문 단계 → 모순 질문의 진술 0·1개 제출 차단/2개 허용 → 지난 밤 정상 질문 200·버전 3 화면 → 8인 15화면 → 종료. 새 ID·같은 명령 재전송 동작은 기존 코드 그대로 유지했다.

- Browser plugin not available: 기존 설치 Playwright 1.65.0과 Chrome을 사용했다. 추가 의존성은 설치하지 않았다.
- 로컬 Daphne HTTP, 1280×900·390×844. 페이지 제목·URL·본문·오류 화면 없음·상호작용·스크린샷을 확인했다. 콘솔/페이지 오류·HTTP 리소스 실패·가로 넘침 0건.
- 저장한 화면을 직접 열어 초상 선택·8인 줄바꿈·모바일 심문 체크박스와 제출 버튼에 겹침·잘림이 없는 것을 확인했다. 기존 임시 에셋을 사용한다.
- 원자료는 로컬 `out/handoff/b0802-browser.log`, 스크린샷은 저장소 밖 백업의 `B-08-02-qa/home-desktop.png`, `interrogation-mobile.png`, `large8-desktop.png`, `large8-ended-mobile.png`다. 시험 쿠키·임시 계정 DB·브라우저 조립 스크립트는 무시 경로에만 둔다.
- 첫 브라우저 시험의 404는 시험용 가짜 광고의 기본 이미지 경로였다. 시험 대역을 `empty=True`로 바꾼 뒤 같은 경로를 재실행해 오류 0건을 확인했다. 운영 광고 구현을 바꾸지 않았다.

### 렌더 측정 범위

[표준 결과 JSON](perf/B-08-02/render_large8.json). 이전 dev `c15cbab`의 미커밋 구현에서 15화면 각 10회, 총 150회의 Django Client 전체 HTML 응답 시간을 측정했다. p50 12.031ms, p95 20.179ms다. 별도 합격 지연 기준이 없는 기록 항목이며 임의의 합격선을 만들지 않았다. 최초 `d7f73e0` 측정(p50 22.177ms·p95 33.115ms)은 로컬 `render-large8-first.json`에 보존했다. 두 실행의 속도 차이를 PM 문서 변경이나 최적화 효과라고 주장하지 않는다. 임시 SQLite·메모리 녹화 조립이며 브라우저 표시·실제 DB·운영 엔진·동시 부하 수치가 아니다. 측정기는 운영 설정 환경 변수도 시험 설정으로 덮어쓰고 메모리 DB를 확인한 뒤 실행한다. 이미 Django가 초기화된 프로세스에서는 실행을 거부한다.
