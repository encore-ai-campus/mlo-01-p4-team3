# D-06-02 광고 MySQL 원장·아웃박스·Kafka 발행
- 상태: 실패
- 커밋: edae4616debc762282ae1e5c3d12c11ff7ee40cd
- 작성자(흐름): D
- 환경: Windows, Python 3.14.6, Django 6.1.2, 테스트 전용 MySQL 8.4.11, 로컬 Compose Kafka 4.3.2.

조건 1~6은 로컬 실제 스택에서 통과했다. 조건 7의 시험용 재판정은 통과했고 C-08-02 실제 silver 발행과 Delta 대사는 미검증이다. 조건 8은 C-06-03의 광고 웹·발행 배포 증빙이 추가됐으며, 세 작업자의 실제 운영 실행 확인이 남아 있다. 상태 표기는 태스크 전체 판정이며 로컬 테스트 결과와 구분한다. 위 SHA는 검증 시 작업 트리의 기반 커밋이다.

## 변경 이력

- 착수 검토 커밋 `4490172`에는 이전 `BudgetBook`의 날짜 경계 환입(-1밀리원) 재현과 PM 전달 초안이 남아 있다.
- dev PR #238(`f276345`)의 ads-0.6은 CPM 건별 내림, 나머지 이월 폐지, 예약액과 확정액 일치, 원래 과금 귀속일에 반대 부호 환입, 순액 대사를 확정했다. 이 기준을 사용해 MySQL을 연결했다.
- dev `d10ac85`를 추가 반영했다. C-08-02는 여전히 D-06-02를 선행으로 명시하고, D-06-02 조건 7도 C의 실제 재판정 검증을 요구한다. 로컬 구현을 먼저 검증한 뒤 C와 연동할 수 있으나 기존 최종 합격선은 그대로다.
- C-06-03 증빙은 광고 토픽·계정 준비, Replica 복제 미완료, D 서버 접속 설정 주입 미실행을 기록한다. 이 작업에서 운영 Primary·Replica나 ad-01에 접속하지 않았다.
- 후속 코드 검토에서 pending이 재전송에 의존하는 문제, 별개 이벤트의 최초 수신 시각 혼용, 서비스 재사용 시 첫 serve 참조, 순서가 뒤집힌 클릭의 세션 시각 후퇴, Creative 표시 메서드 이동을 확인했다. 각각 수정하고 회귀 검증했다. 독립 검토는 사용량 한도로 중도 종료돼 최종 전체 검토 승인은 받지 못했다.

## 구현·검증 순서

- [x] 최신 dev의 ads-0.6 금액·환입 기준을 병합하고 메모리 계약을 재검증했다.
- [x] MySQLLedger의 예산 행 잠금·예약·확정·해제·환입과 트랜잭션 롤백을 검증했다.
- [x] 정상 HTTP 진입점을 MySQLAdStore에 연결해 요청·판정 재생과 공개 이벤트 원자성을 검증했다.
- [x] Kafka 발행 ACK·재발행과 재판정 환입, 만료 프로세스 재시작을 실제 로컬 스택에서 검증했다.
- [x] 만료 작업자에 pending 자동 재판정을 연결하고 최초 수신 시각과 개별 이벤트의 만료 기준을 검증했다.
- [ ] C-08-02 실제 silver·Delta 연동과 ad-01 운영 프로세스 배포를 확인한다.
