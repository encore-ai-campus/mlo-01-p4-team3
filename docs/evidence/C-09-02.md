# C-09-02 개인정보 재유입 차단과 보존 준비

- 커밋: 7b7ae4b 기반
- 작성자(흐름): C
- 환경: Spark 격리 Delta, Kafka 토픽 설정, 광고 MySQL 임시 스키마, NiFi의 Garage, 웹 VM
- 상태: 격리 저장소 삭제와 보존 대상 목록 예약 완료. 실제 11/10 테스트 스냅숏과 운영의 파생물 검증은 대기.

격리 Delta에 두 원본을 쓴 뒤 하나를 삭제하고 제외 목록을 적용해 같은 입력을 재처리했다. 삭제 대상은 0건, 비대상은 1건을 유지했다. 감사에는 재처리 2건의 offset 0–1, 삽입 0건, 기존 중복 1건, 제외 1건이 남았다. 게임 가명과 광고 세션 가명·재판정 키는 계약 시험에서 분리 검증했다.

Kafka 10개 토픽의 `retention.ms=86400000`, `segment.ms=604800000`와 broker 점검 주기 `300000`을 읽었다. 설정 합계 추정은 8일 5분이다. 원문과 설문 저장 경로의 `mask_version=b-mask-1` 기록을 코드에서 확인했다.

검증한 필터를 운영 Bronze에 반영하고 보호 제외 목록을 비운 상태로 기동했다. 기존 체크포인트와 Delta 경로로 스트림이 정상 재개됐다. 운영 참가자 삭제 요청은 이 검증에 사용하지 않았다.

후속 검증에서 격리 Django 계정의 비활성화·세션 삭제와 운영자 보호를 확인했다. 실제 Mongo의 고유 컬렉션에서 대상 판·진척·상호작용을 각각 1건 삭제하고 회차에서 대상 가명만 제거했다. 재실행의 신규 삭제는 0건이며 다른 참가자와 후속 광고 삭제용 대응표는 보존됐다. 계정 최종 삭제는 게임 및 대응표가 비고 외부 저장소 검증을 확인한 뒤 호출한다.

MySQL 임시 스키마에서 대상 과금·환입과 광고 요청을 정리하고 비대상 원장과 일 예산 잔액 500을 유지했다. 두 번째 실행의 삭제는 0건이다. 검증 후 임시 스키마와 전용 인증정보를 폐기했다.

격리 Delta의 Bronze·게임 Silver·광고 Silver에서 각각 2·1·1건을 삭제했다. 각 테이블에 비대상 행 1건이 남았고 재실행에서는 0건이 삭제됐다. 격리 테이블에만 `VACUUM 0`을 사용했다. 이전 버전을 읽을 수 있는 상태에서 시작해 실제 파일 3개가 제거된 뒤 해당 버전의 파일을 읽을 수 없는 것을 확인했다.

Garage 테스트에서 승인한 객체 1개를 삭제했고 재실행은 0건이었다. 인접 비대상 객체는 계속 읽혔다. 웹 VM의 보존 타이머 다음 실행은 2026-12-12 00:00 KST로 확인했고, 기한 전 호출은 입력을 읽기 전에 거부됐다.
