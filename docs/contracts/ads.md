# 광고 시스템 계약 (D 소유: ads/ 전체)

기획서: `../paldo_design_v1.md` 9장(v1.2의 8장, v1.1의 14장. 크로스체크 6을 반영한 판). 코드 기준은 다음 세 파일이다.
- `ads/domain/model.py`: 데이터
- `ads/domain/rules.py`: 규칙
- `ads/domain/events.py`: 이벤트

예시는 `fixtures/ads/`, 테스트는 `tests/contract/test_ads.py`에 있다.

## 1. 계층

| 폴더 | 계층 | 역할 |
|---|---|---|
| `ads/domain/` | 도메인(표준 라이브러리만) | 경매, 2등 가격, 예산 예약·확정·해제, 페이싱, CTR 베타·톰슨, serve 토큰, 유효 판정, 건별 대사 |
| `ads/app/` | 응용(예정) | 광고 요청, 비콘, 클릭 처리 흐름. 도메인과 인프라를 순서대로 부른다 |
| `ads/infra/` | 인프라(예정) | MySQL 원장(Primary 트랜잭션, `charge_id` 유일 제약, 아웃박스 행), Kafka 발행기, CTR·페이싱 값 적재 |
| `ads/web/` | 표현(예정) | Django 뷰(내부 API, 비콘, 클릭 리다이렉트, 가상 랜딩), Django admin(캠페인 관리) |
| `ads/testing/` | 테스트 지원 | `FakeAdProvider` |

- 의존 방향: `ads/web → ads/app → ads/domain`, `ads/infra → ads/domain`.
- 실행(11/4 PM 결정 #1·#15): 광고 서버는 독립 Django 프로젝트(`ads/project/` 설정·URL, `ads/manage.py`)로 ad-01에서 돈다. 게임 웹 설정과 공유하지 않는다. 예약 만료 해제, 환입 소비자, 광고 아웃박스 발행기는 웹 서버와 별도 프로세스다.
- 게임 엔진(`engine/`)과 광고는 서로 import하지 않는다. 게임 서버는 `server/app/ads_port.py`의 `AdProvider` 포트만 쓴다. 포트에서 `ads.domain.model`의 요청·응답 DTO만 공유한다.

## 2. 데이터 모델
- **금액**: 모두 정수 **밀리원**(`_mw`, 1원 = 1000)으로 누적한다. 청구서에는 원 단위로 내려 적는다. 부동소수 금액은 쓰지 않는다.
  - **1건 금액**(11/7 PM 결정, 나머지 이월 폐지, `ads-0.6`): 과금 1건의 금액은 그 건의 청구 단가만으로 정한다. CPC는 청구 CPC, CPM은 `floor(청구 CPM / 1000)`이다(`rules.charge_amount_mw`). 다른 건이나 처리 순서에 따라 달라지지 않는다. 예약액과 확정액이 같다.
- **구조**: 광고주 → `Campaign` → `Creative`.
  - 캠페인 속성: 지면, 과금 방식(cpc, cpm), `max_bid_mw`, `daily_budget_mw`, `Targeting`(프리셋, 판 결과, 재방문, 시간대), 기간, 상태
  - **1건 최대 청구액**(11/7 PM 결정): 최대 입찰가로 정한 한 건의 청구 상한이다. CPC는 `max_bid_mw`, CPM은 `floor(max_bid_mw / 1000)`이다(11/7 PM 결정으로 올림 → 내림, 1건 금액과 같은 식). 4절 예산 필터가 이 값을 쓴다.
  - **등록 검증**(11/7 PM 결정): `daily_budget_mw`가 1건 최대 청구액보다 작은 캠페인은 저장을 거부한다(admin 폼의 `daily_budget_mw` 오류, 도메인 `rules.validate_campaign_budget(billing, max_bid_mw, daily_budget_mw)`의 `ValueError`). 받아 주면 예산 필터에 항상 걸려 한 번도 나가지 않는 캠페인이 생기기 때문이다. 자동 입찰(`target_cpc_mw`)이 입찰가를 바꿔도 기준은 `max_bid_mw`다.
  - 소재의 랜딩은 사이트 안 가상 경로다. 화면에는 "광고"로 표시한다.
- **지면(`AdSlot`)**: `lobby_banner`, `result_banner`, `review_side` 세 곳이다. 회의, 투표, 밤 화면에는 예외 없이 광고를 넣지 않는다(추궁 답변 대기 지면 `llm_wait`은 11/6 PM 결정으로 삭제, `ads-0.5`).
- **지면 규격(`SLOT_SIZES`, P-19, 11/5 PM 잠정 확정, `ads-0.3`)**:

  | 지면 | 규격(가로×세로 px) |
  |---|---|
  | `lobby_banner`, `result_banner` | 728×90 |
  | `review_side` | 300×250 |

  - 소재 이미지는 지면이 아니라 **규격마다 1장**이다. `Creative.image_path`는 기본 경로이고, 지면별 실제 파일은 `slot_image_path(image_path, slot)`이다(예: `/static/ads/gat.png` → `/static/ads/gat__728x90.png`). 소재가 나가는 지면들의 규격 수만큼 파일이 있다.
  - 광고 서버는 `AdCreativeView.image_path`에 요청 지면의 `slot_image_path` 결과를 넣는다(`FakeAdProvider`도 같다). 화면(B)은 그 경로를 그대로 쓰고, 이미지 크기는 `SLOT_SIZES[slot]`로 잡는다.
  - 픽스처 `fixtures/ads/campaigns.json`의 `slot_sizes`는 같은 값의 사본이다(에셋 검사 도구가 파이썬 import 없이 읽는다). 규격을 바꾸면 `SLOT_SIZES`를 고치고 픽스처를 다시 만든다.
- **`SlotPolicy`**: 지면 최저 eCPM, 사전 CTR μ, 사전 강도 κ(기본 200), 빈도 제한(세션당 같은 소재 serve 3회).
  - **최저 eCPM 하한**(11/7 PM 결정, `ads-0.6`): 지면 최저 eCPM은 100원(`MIN_RESERVE_ECPM_MW = 100_000`) 이상이다. 만들 때 `validate_reserve_ecpm`이 검사해 미만이면 `ValueError`다. CPM 청구 단가 ≥ T ≥ 최저 eCPM이므로 CPM 1건 금액은 100밀리원 이상이고, 건별 내림 손실은 1건당 1밀리원 미만(1% 미만)이다. 손실은 노출 수에 비례해 쌓인다(예: 청구 CPM 100,999밀리원 1,000회 = 정확값보다 999밀리원 적음).

## 3. API

| 호출 | 경로 | 입력 → 출력 |
|---|---|---|
| 게임 서버 → 광고 서버(내부 HTTP) | POST `/ads/v1/serve` | `AdRequest` → `AdResponse`(JSON) |
| 게임 서버 → 광고 서버(내부 HTTP, 비콘 중계) | POST `/ads/v1/impression` | `{token, visible_ratio, visible_ms, occurred_at_ms}` → 204 |
| 게임 서버 → 광고 서버(내부 HTTP, 클릭 중계) | GET `/ads/v1/click?t=토큰` | 302, `Location`은 상대 경로 `/ads/landing/<creative_id>`(판정 결과와 무관하게 항상 이동). 브라우저 기준으로는 보통 소재 랜딩, 광고 서버 실패·시간 초과·회로 차단 때는 게임 서버가 302 `/`로 보낸다(ports.md 5절) |
| 게임 서버 → 광고 서버(내부 HTTP, 랜딩 중계) | GET `/ads/landing/<creative_id>` | 가상 랜딩 HTML |
| 브라우저 → 게임 서버 | GET `/ads/slot/{slot}` | htmx 지연 로드 조각. 안에서 `AdGateway.fetch`를 호출한다 |
| 브라우저 → 게임 서버 | 웹소켓 `/ws/game/`의 `ad.impression` 메시지, GET `/ads/click?t=토큰`, GET `/ads/landing/<creative_id>` | 게임 서버가 위 세 내부 호출로 넘긴다([api.md 7절](api.md)) |

- **serve 토큰**(HMAC-SHA256): serve ID, 세션 가명 ID, 지면, 발급 시각, 만료(30분)를 담는다. 서버가 발급했다는 것만 증명한다. 서명 키는 인프라 비밀 저장소에 두고 저장소에는 넣지 않는다.
- **비콘**: 브라우저는 광고 면적의 50% 이상이 1초 이상 보였을 때 게임 서버 웹소켓으로 보내고, 게임 서버가 광고 서버에 넘긴다.
- **게임 서버 중계**(11/4 PM 결정 #2를 같은 날 (a) 브라우저 직접 호출에서 (c)로 변경): 브라우저는 게임 서버 출처에만 접속한다. 내부 사용자 테스트를 HTTPS로 하면 HTTP 광고 서버로 가는 비콘(페이지 안 요청)이 혼합 콘텐츠로 막히고, 클릭은 막히지는 않지만 HTTPS 화면에서 HTTP 주소로 빠져나가기 때문이다. 비콘·클릭·랜딩은 게임 서버가 내부 주소(`PALDO_ADS_INTERNAL_URL`)로 부른다. 광고 서버는 비콘 본문을 `Content-Type`과 무관하게 JSON으로 파싱하고, 비콘·클릭은 serve 토큰으로 검증하므로 Django CSRF 검사에서 제외한다. 브라우저용 공개 주소는 두지 않는다. **경로·본문·응답 형식은 그대로라 `ads-0.3`을 유지한다**(바뀐 것은 호출 주체와 출처 처리, 클릭 `Location`의 상대 경로).
- 게임 서버의 serve 호출과 중계 호출(비콘·클릭·랜딩)에는 `X-Request-ID`가 붙고, 광고 서버는 그 값을 로그 `request_id`로 남긴다(결정 #14, ports.md 5절).
- `AdResponse.beacon_path`·`click_path`는 광고 서버 내부 경로다. 게임 웹은 이 값을 브라우저에 넘기지 않는다. 브라우저에는 `serve_token`만 주고, 비콘은 웹소켓 `ad.impression`, 클릭은 게임 웹 `/ads/click?t=`로 받는다(api.md 7절, B-07-03·B-07-05).

## 4. 경매 (`run_auction`)
1. **후보 필터**를 통과하지 못하면 `ServeCandidate.filtered`에 사유를 남긴다.
   - 지면·타기팅 불일치(`targeting`)
   - 예산 부족(`budget`): 예약+확정 합계와 1건 최대 청구액(2절, 최대 입찰가 기준)의 합이 일 예산보다 크다. 낙찰가는 경매 뒤에 정해지므로 필터는 상한으로 판단한다. 그래서 하루 끝 무렵 남은 예산이 1건 최대 청구액보다 적으면 실제 낙찰가로는 들어가더라도 멈춘다. 남는 돈은 최대 1건분이고, 예산 초과가 구조적으로 생기지 않는 쪽을 택했다(11/7 PM 결정).
   - 빈도 제한(`frequency`)
   - 페이싱 확률(`pacing`)
   - 최저 eCPM 미만(`reserve`)
2. **순위 점수 eCPM**:
   - CPC: 입찰가 × 순위 CTR × 1000. 순위 CTR은 톰슨 샘플이고, 하한은 0.0001이다.
   - CPM: 입찰가.
3. **낙찰**(단일 슬롯 2등 가격):
   - 기준 점수 `T = max(2등 eCPM, 지면 최저 eCPM)`. 후보가 1개면 T는 지면 최저 eCPM이다.
   - 청구 단가: CPC는 `floor(T / (1000 × 승자 순위 CTR))`, CPM은 `T`. 둘 다 최대 입찰가를 넘지 않는다(`capped`).
   - 예: CTR 2%, T=1000원이면 청구 CPC는 50원이다.
   - 동점은 `sha256(request_id|campaign_id)`로 정한다. 같은 요청이면 같은 결과다.
   - 경매 입력은 **캠페인당 후보 1개**다. 소재는 캠페인 안에서 먼저 고른다. 같은 캠페인 후보가 둘이면 오류다.
   - 후보가 없으면 광고를 내지 않는다(`filled=false`).
4. **과금**: CPC는 유효 클릭 1건마다 청구 CPC를 청구한다. CPM은 유효 노출 1건마다 `floor(청구 CPM / 1000)`밀리원을 청구한다(2절 1건 금액).
   - **기획서 대비 결정**(11/7 PM 결정, 나머지 이월 폐지): CPM 1건 금액에는 1/1000 밀리원 단위가 생긴다. 이전 계약은 캠페인별로 나머지를 이월해 누적 합을 맞췄다. 그러면 1건 금액이 처리 순서에 따라 달라져, 원래 귀속일에 기록하는 환입이 다른 날 나머지의 영향을 받아 귀속일 합계가 음수가 되고(예산 초과로도 이어짐), 지면·시간대 집계와 charge_id 건별 대사도 맞지 않았다(D-06-02 착수 전 보고). 그래서 건마다 밀리원 미만을 버린다. "청구 CPM 999밀리원이면 모두 무료"가 되는 문제는 2절 최저 eCPM 하한(100원)과 5절 불변조건(0원 과금 금지)으로 막는다.
5. 캠페인 안에서 소재를 고를 때도 톰슨 샘플링을 쓴다. CPM의 탐색이 이것이다. 캠페인별 탐색 노출 하한(하루 노출의 5%)은 페이싱과 별도로 둔다. 이 하한은 아직 기준 구현과 합성 생성기에 없으며, D가 구현한다.

## 5. 예산 (`BudgetBook`가 기준 동작이고, MySQL이 같은 동작을 구현한다)
- **예약**: serve 시점에 1건 금액(2절)을 예약한다(CPC는 청구 CPC 1회분, CPM은 노출 1회분). 확정해도 금액은 바뀌지 않는다. 예약액은 낙찰 뒤의 실제 청구 단가 기준이라 4절 필터의 1건 최대 청구액 이하다. 따라서 혼자 처리되는 serve는 필터를 통과하면 예약도 들어간다. 다만 같은 캠페인의 다른 serve가 필터와 예약 사이에 먼저 예약하면, 아래 원자적 예약이 이 serve를 거부할 수 있다. 그때는 경매를 다시 하지 않고 광고를 내지 않는다(`filled=false`, 그 후보의 사유는 `budget`). 이 경우 예약·과금 행은 남기지 않는다(11/7 PM 결정, Codex 지적 반영). `charge_id = serve_id + ":click"|":impression"`이며 유일 제약을 둔다.
- **확정**: 유효 이벤트가 오면 예약을 확정한다. 같은 charge_id를 다시 확정해도 효과가 없다(멱등).
- **해제**: 해제 시각(serve + 클릭 인정 기한 30분 + 판정 유예 2분, 원장 행의 `release_after_ms`)이 지나도 확정되지 않은 예약은 해제한다. 유예를 더하는 이유는 기한 직전에 유효로 판정된 이벤트의 확정이 해제와 경합하지 않게 하기 위해서다. 해제는 serve 기록 없이 원장만으로 판단한다.
- **원자성**:
  - 예약: (캠페인, 귀속일) 예산 행을 잠그거나 조건부 갱신(`committed + amt <= budget`)으로 처리한다. `charge_id` 유일 제약만으로는 서로 다른 serve의 동시 초과를 막지 못한다.
  - 판정 결과 저장, 예약 확정, 아웃박스 행은 한 트랜잭션으로 묶는다. 같은 이벤트를 다시 받으면 저장된 판정 결과를 그대로 재생한다.
  - 환입: 원과금의 (캠페인, 귀속일) 예산 행 잠금, 환입 행, 아웃박스 행을 한 트랜잭션으로 쓴다. 환입 행 `charge_id`(`<charge_id>:refund`)에 유일 제약을 둬 동시 중복 환입을 막는다.
  - 나머지 이월 상태는 없다(11/7 PM 결정). MySQL에 캠페인별 나머지 열·행을 두지 않는다.
- **불변조건**: 예약 전에 확인하고, 저장 계층에도 같은 제약을 둔다.
  - 청구 단가는 0 이상, 최대 입찰가 이하
  - CPM 청구 단가는 최저 eCPM 하한(100,000밀리원) 이상
  - 1건 금액은 0보다 크다(0원 과금 금지. 7절 순액 대사가 0원 행과 발행 누락을 구분하는 전제)
  - serve의 캠페인·과금 방식이 캠페인과 일치
- **귀속일**은 serve 시각을 Asia/Seoul로 바꾼 날짜다(C-08-02 조건 1). 이벤트의 타임스탬프는 그대로 밀리초를 기록한다.
- **환입**: 확정 뒤 silver가 무효로 다시 판정하면, 원래 행은 그대로 두고 음수 환입 행(`:refund`)을 추가한다. 재판정 결과는 `ad.rejudge` 토픽으로 오고 환입 소비자가 처리한다(events.md 5절, 11/4 PM 결정 #11).
  - 환입액은 원래 행 금액의 부호 반전이다. 환입 행은 원과금의 귀속일에 기록한다(11/7 PM 결정).
  - 원과금(`kind=charge`, 확정 상태)만 환입한다. 원과금당 1회이고, 환입 행을 다시 환입하지 않는다.
  - 불변식: (캠페인, 귀속일)마다 `committed = 예약 중 금액 + 환입되지 않은 확정 금액`, `0 ≤ committed ≤ 일 예산`. 1건 금액이 그 건만으로 정해지므로 원과금과 환입 쌍은 어느 집계 단위(귀속일, 지면, 시간대)에서도 0으로 상계된다.
- **저장**: 예약, 확정, 해제, 환입과 이벤트 아웃박스 행은 **같은 MySQL 트랜잭션**으로 Primary에 쓴다. 발행기가 Kafka로 보낸다.
- **페이싱**(`next_pacing_probability`):
  - 소진액은 확정과 예약을 합한 값이다.
  - 목표 곡선은 균등 또는 트래픽 비례다.
  - 참여 확률은 0.05~1.0 범위이고, 5분마다 조정하며, 한 번의 조정 폭은 ±0.2다.
- **갱신 값 반영**(11/4 PM 결정 #9): CTR, 페이싱 계수, 자동 입찰가는 갱신 작업이 MySQL에 버전 행(`ctr_version`, `policy_version`, `bid_version`)으로 쓰고, 광고 서버가 60초마다 다시 읽어 메모리 캐시를 바꾼다. 광고 서버를 다시 띄워도 최신 버전 행을 읽는다.

## 6. 유효 판정 (pending → valid / invalid)

| 이벤트 | 무효 사유(우선순위 순) | 비고 |
|---|---|---|
| 노출 | `bad_signature` → `expired` → `load_test` → `no_serve` → `duplicate` → `not_viewable` | serve 기록이 안 보이면 **서버 최초 수신 시각**부터 유예 2분 동안 `pending`, 지나면 `no_serve`. 클라이언트가 보낸 발생 시각은 기록만 하고 판정에는 쓰지 않는다. 만료도 최초 수신 시각으로 검사한다(재판정해도 결과 불변) |
| 클릭 | `bad_signature` → `expired` → `load_test` → `no_serve` → `duplicate`(토큰 재사용) | **클릭은 노출 증거다.** 비콘보다 먼저 도착한 클릭은 노출도 인정한다(`implied_by_click`). 그 뒤에 온 비콘은 `duplicate`. 같은 세션의 1초 내 연속 클릭은 `suspect` 표시만 하고 무효 근거로 쓰지 않는다 |

- 판정 버전(`JUDGE_VERSION`)을 이벤트에 남긴다. 광고 서버(온라인)와 Spark silver(배치)가 같은 규칙을 쓴다.

## 7. 대사와 마감
- **건별 대사**(`reconcile`): 원장의 확정 행(환입 행 포함)을 원래 charge_id로 묶은 **순액**(원과금 + 환입)과 Delta의 과금 대상 유효 건을 charge_id마다 비교한다(11/7 PM 결정, `ads-0.6`).
  - Delta 금액은 과금 대상 건만 계산한다: CPC는 유효 클릭(`:click`), CPM은 유효 노출(`:impression`, 클릭 유도 노출 포함 1회). 금액은 이벤트의 `billing`·`price_mw`로 2절 1건 금액 식을 다시 계산한 값이며 원장 `charge_mw`와 같아야 한다.
  - 순액 0이고 Delta에 없으면 환입으로 상계된 건이라 일치다. 0원 과금은 금지(5절)라 발행 누락과 구분된다.
  - 다음 다섯 가지를 센다.
  - `ledger_only`(발행 누락)
  - `delta_only`
  - `duplicate`
  - `amount_mismatch`(상계됐는데 Delta에 유효로 남은 건 포함)
  - `orphan_refund`(원과금 없는 환입 행)
- **마감**:
  - 잠정 마감: 귀속일 다음 날
  - 확정 마감: 클릭 인정 기한과 판정 유예가 지난 뒤
- Delta 쓰기는 `event_id` 기준 MERGE로 멱등하게 한다. 계층은 bronze → silver(판정, 조인) → gold(캠페인 × 지면 × 시간대)다.
- 환입은 재판정 시각이 아니라 **원과금의 귀속일·지면·시간대**로 gold에 반영한다(원래 serve와 조인). 그래야 세부 집계 단위에서도 음수가 생기지 않는다(11/7 PM 결정). 확정 마감 뒤에 온 환입의 gold 재작성 여부는 C-08-02에서 정한다(미결).
- **실현 지표**는 순위용 eCPM과 구분한다.
  - 실현 eCPM = 비용 / 유효 노출 × 1000
  - 실현 CPC = 비용 / 유효 클릭
  - 분모가 0이면 비운다.

## 8. 합성 트래픽 격리
- `source=synthetic`은 보고뿐 아니라 상태도 격리한다. 합성 전용 캠페인과 소재 복제본(ID에 `syn:` 접두어)을 쓰므로 예산, 사전분포, CTR·빈도 집계, 페이싱 상태가 실제와 섞이지 않는다.
- 생성기: `python -m tools.gen_synthetic --ads N`. 숨긴 실제 CTR은 `ad_hidden_ctr.json`에 둔다(평가 전용, 학습 입력 금지). 다음 상황을 섞어 만든다.
  - 비콘 손실
  - 클릭 먼저 도착
  - 토큰 재사용(이미 클릭한 serve에만)
  - 위조 토큰
- 실제 광고 서버 API를 거치는 생성기 `tools/ad_traffic_sim.py`(D-06-03)는 정답을 `out/ad_truth/<run>.json`(평가 전용, 광고 서버가 읽지 않음)에 둔다. 위 단위 시험용 생성기와 함께 쓴다.
- D-06-03 로컬 시험: `python -m tools.ad_traffic_sim --run-id <run> --seed 17 --requests 10000 --replay`. 별도 loopback WSGI 프로세스에서 실제 Django serve·impression·click 뷰와 메모리 `AdService`를 실행한다. 캠페인은 기존 합성 복제본만 메모리에 적재한다. 기존 서비스·MySQL에는 연결하지 않는다.
- 합성 serve ID는 `syn:` 접두어·요청 ID 앞부분·요청 해시로 결정한다(117자 이하). 실제 serve UUID와 합성 호출자가 지정한 ID가 충돌하지 않는다. 생성기는 요청·serve·이벤트·세션 ID에 실행 ID를 포함한다. 같은 시드·실행 ID·설정·서버 초기 상태면 관측 이벤트가 재현된다. 다른 실행 ID는 서버의 요청 ID 기반 톰슨 추출에도 영향을 주므로 정답 CTR은 같아도 경매 결과는 달라질 수 있다.
- `no_serve`와 만료 시험은 `ads/testing/traffic_server.py`의 시험 프로세스 표준입력으로만 제어한다. 정상 서명·미만료 토큰을 serve 저장 없이 발급한 뒤 실제 click HTTP로 pending을 확인하고, 서버 시간을 유예 2분만큼 전진시켜 같은 클릭을 재판정한다. 서명 키는 프로세스 내부 임시 값이며 출력·파일에 남기지 않는다. 운영 URL·토큰 계약에는 시험 경로나 필드를 추가하지 않는다.
- 무효 비율은 최종 클릭 중 무효 클릭의 비율이다. 유효 클릭 V 뒤 `floor(V × r / (1-r) + 0.5)`개를 네 유형에 순환 배분한다. 작은 표본의 반올림 차이와 유형별 실제 수를 정답·요약 파일에 기록한다. 비콘 누락·클릭 우선 도착은 유효 사례다.
- 학습용 생성기와 별도로, 평가용 생성기(CTR 변화, 피로, 지연 클릭, 여러 시드)는 D가 만든다.
- 합성 검증은 알고리즘, 회계, 제어 루프가 설계대로 동작하는지만 증명한다. 실제 광고 성과는 증명하지 않는다.

## 9. 개인정보
- 광고는 세션 가명 ID만 쓴다(privacy.md). 게임 쪽 플레이어 가명 ID나 판 내용(입력 문장 등)은 광고 서버에 보내지 않는다. 타기팅 맥락은 프리셋, 승패, 재방문 여부, 시간대뿐이다.
- 브라우저가 광고 서버에 직접 접속하지 않고(3절 게임 서버 중계), 게임 서버가 중계 요청 헤더를 새로 만들어 참가자의 `Cookie`·`X-Forwarded-For`·`User-Agent`·`Referer`를 넘기지 않으므로(ports.md 5절) 광고 서버는 참가자의 접속 주소·브라우저 정보를 받지 않는다.
