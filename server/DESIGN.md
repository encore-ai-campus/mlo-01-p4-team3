## B-08-02 공개 프리셋과 화면 검증

`app/presets_enabled.json`은 공개 프리셋 ID 배열이며 초기값은 `base6` 하나다. 응용 `open_preset_ids()`가 매 요청 읽고 홈과 일반 판 시작이 같은 목록을 사용한다. 파일 오류·알 수 없는 ID·중복 ID는 시작 불가로 처리한다. 추가 공개는 P-08의 평가와 PM 승인 이후 반영하며, 8인 화면 시험 통과만으로 공개하지 않는다. 고정 회차 배정과 이미 저장된 시작 UUID의 재생은 유지한다.

여성/남성 무당 선택은 기존 `StartGameInput.mudang_variant`의 `f`/`m` 값이다. 판 메타에 저장하고 기존 출력 필드로 초상을 정한다. 다른 값은 400, 값 없는 과거 녹화는 여성 초상을 쓴다. 인물 목록에 무당이 없는 기존 녹화도 초상을 표시한다. 게임 규칙·NPC 반응·이벤트 판정은 바꾸지 않는다.

명령 422 응답의 접근 로그에만 `RejectCode.value`를 `reject`로 추가한다. 수락·재생에는 추가하지 않고 본문·거절 상세 문자열은 기록하지 않는다. 심문 화면은 공개 진술 수와 지난 밤(0~오늘−1)만 전달받으며 조작한 요청의 최종 검증은 기존 엔진이다.

[검증과 대기 범위](../docs/evidence/B-08-02.md)

## B-07-05 성능 시험의 실행 경계

`server/tests/asgi_bench.py`는 B-06-02의 녹화 엔진 조립·분위수 계산·Mongo 접속값 로더를 재사용한다. 계정은 임시 SQLite, 게임·진척·콘텐츠·광고 가명은 실제 Mongo의 고유 `b0705_<UUID>_` 컬렉션 5개다. 하위 프로세스는 `asgi_bench_app.py`로만 조립하며 WSGI는 단일 프로세스의 스레드형 wsgiref, ASGI는 단일 Daphne다. 운영 팩토리·기본 설정에 시험 대역을 연결하지 않는다.

사용자별 독립 판에서 시작·명령을 초당 1회 보낸다. WSGI와 Daphne 기준선의 계정·DB·입력·빈도는 같고, 혼합 시나리오에는 사용자별 광고 HTTP와 인증 비콘을 각각 초당 1회 추가한다. 광고 3초 지연·실패는 기존 `FakeAdProvider`에 주입한다. 게이트웨이의 300ms 제한·회로 차단을 포함한 실제 동작을 측정하며, 게임 오류와 비콘 연결 오류를 숨기지 않는다. 전송 오류도 지연 표본에 포함한다.

게임 이벤트는 모두 `load_test=true`인지 확인하고 종료 시 자기 컬렉션·계정 DB·서버만 정리한다. 이 결과는 로컬 비교이며 대상 VM·HTTPS 프록시·실제 광고 HTTP·Kafka·실제 엔진 처리량 검증은 포함하지 않는다.

## B-06-02 실제 Mongo 검증

성능 CLI는 `tools/perf/api_bench.py`의 표준 라이브러리 진입점에서 `server/tests/api_bench.py`의 별도 시험 프로세스로 넘긴다. Django test client로 인증·CSRF·기존 API·응용을 통과하고 게임·진척·콘텐츠만 실제 Mongo로 연결한다. 엔진은 태스크가 지정한 녹화 가짜이며 자유 입력 보조 저장은 측정하지 않는다. 운영 설정·핸들러에는 시험 조립을 넣지 않는다.

계정 DB는 임시 SQLite 파일이고 Mongo는 실행마다 고유 접두어를 쓴다. 실제 회차 정책을 우회하는 시험 시작 정책은 이 시험 프로세스 안에서만 주입한다. 계정 가명은 실제 프로필에 UUID로 저장하며 모든 아웃박스 이벤트에 `load_test=true`를 기록한다. 시험 종료 시 해당 접두어의 정확한 5개 컬렉션과 임시 계정 파일만 정리한다. URI는 환경 → `server/.env` → Compose 루트 `.env` 순으로 읽고 결과에는 남기지 않는다. 루트 `.env`의 자동 읽기는 시험 전용이며 운영 설정은 바꾸지 않는다.

기존 20개 HTTP 동시 명령 시험은 Mongo 교체 뒤에도 같은 시나리오를 실행한다. 서로 다른 ID는 수락 1·409 19, 같은 ID는 수락 1·재생 19이고 상태 버전 증가는 1이다. 별도 시험이 422의 상태·아웃박스 불변과 재생 200·충돌 409를 실제 저장 문서로 대조한다. 네이티브 Replica Set과 Compose·VM 성능 결과를 구분한다.

dev `f24f6a8` 반영 후 같은 저장 계약과 시험 경계를 다시 확인했다. 녹화 엔진 측정과 실제 엔진·VM 통합 검증을 구분하며 결과는 B-06-02 증빙에서 관리한다.

고정 회차의 `rule_version`은 최신 엔진이 내보내는 `규칙.결정 파라미터` 문자열을 그대로 저장하고 판 메타에 고정한다. PR #241의 엔진 버전 문자 규칙과 회차 등록 검증을 일치시키며 1~80자 길이와 기존 공백·경로 거부는 유지한다. 엔진·콘텐츠 버전 검증은 기존과 같다.

`api/`는 HTTP 입력을 검증하고 응답을 만든다. `app/`은 판 시작과 명령 실행을 조정한다. 게임 상태와 진행 저장소는 [게임 서비스 조립 경계](paldo_web/composition.py)에 주입한다. 계정 저장소는 Django의 `default` MySQL이며, 접속값은 `PALDO_AUTH_DB_*`로 받는다.

## 계정과 세션

가입 시 로그인 ID를 정규화하고 비밀번호 해시, UUID 가명 ID, 동의 시각을 저장한다. 초대 코드가 설정된 경우에만 가입할 때 검증한다. 일반·관리자 로그인은 같은 잠금 규칙을 쓰며, 로그인 성공 시 세션 ID를 교체한다.

게임 API는 인증된 계정의 가명 ID로 판과 하위 자원의 소유권을 확인한다. 로그인 ID와 비밀번호 해시는 계정 DB에만 저장하며, 인증 로그에는 결과와 확인된 계정의 가명 ID를 쓴다.

## 테스트 회차

판 시작 응답은 htmx 헤더를 확인해 회의 조각을 반환한다. 일반 HTML 폼은 판 조회 화면으로 이동하며, JSON 응답은 게임 DTO를 사용한다.

활성 운영자(`is_staff`)가 회차 ID, 순서 있는 고정 판 목록, 참가자 가명, 규칙·엔진·콘텐츠 버전을 등록한다. 회차 ID는 유일하며 이미 등록한 구성은 덮어쓰지 않는다. 참가자의 첫 미종료 판이 다음 차례다. 시작 요청은 가입 때 발급된 가명으로 참가 배정과 동의를 확인한다. 같은 회차·참가자·순번은 같은 판 ID를 사용한다. 시작 이벤트에는 `source=human`, `session_id`, `player_pseudonym`이 들어간다.

[B 회차 저장소](infra/test_sessions.py)는 `PALDO_MONGO_URI`의 DB(경로 생략 시 `paldo_web`)에 `b_test_sessions`와 `b_ad_identities`를 둔다. 게임 상태·진척은 기존 게임 포트를 사용한다. 회차 저장소를 사용할 수 없으면 운영자 화면과 회차 판 시작은 503을 반환한다.

후속 광고 연동은 [서버 가명 발급 함수](api/sessions.py)에서 로그인 세션별 광고 UUID를 받는다. 대응표에는 플레이어 가명과 광고 UUID, 로그인 세션을 HMAC으로 변환한 내부 키를 둔다. C-09-02는 `ad_identities(player)`로 광고 기록을 찾고, 광고 기록을 삭제한 뒤 `delete_player(player)`로 대응표와 회차 참가 배정을 제거한다.

## 광고 신호와 ASGI

[ASGI 진입점](paldo_web/asgi.py)은 HTTP를 Django에, `/ws/game/`을 전체 출처 검사와 Django 세션 인증 뒤 Consumer에 보낸다. 허용 출처는 `PALDO_PUBLIC_ORIGIN` 하나다. 비로그인은 수락 직후 4401로 닫고, 매 비콘 전에 DB에서 세션·사용자·인증 해시를 새로 읽어 로그아웃·만료·비밀번호 변경을 확인한다. 크기 제한은 UTF-8 바이트 기준 4,096이며 초당 비콘 5개를 넘으면 연결을 유지하고 거부한다.

Consumer는 검증과 응답만 맡는다. 중계는 `ad_events` → `AdGateway` → `AdProvider` 순서이며 `sync_to_async(thread_sensitive=False)`로 동기 호출을 이벤트 루프 밖에서 실행한다. serve와 중계의 호출 상한은 각각 8이고 회로 차단기는 공유한다. 전체 300ms·연결 100ms, 재시도 없음 규칙을 유지한다. HTTP 클릭은 같은 출처 `/ads/landing/<id>`만 허용하며 실패하면 `/`로 이동한다.

광고 제공자는 `configure_ad_gateway` 주입을 우선하며, PALDO_ADS_INTERNAL_URL이 있으면 B-08-03의 HTTP 제공자를 조립한다. 운영에서 가짜로 자동 대체하지 않는다. 미조립 상태는 비콘 실패 응답과 HTTP 대체 화면으로 처리한다. 참가자 헤더나 요청 객체는 포트 인자에 전달하지 않는다. B-08-03의 실제 loopback HTTP 회귀에서 헤더 분리를 검증하며 D 인수 서버 수신 확인은 남아 있다.

`InMemoryChannelLayer`를 사용하므로 Daphne는 루프백 주소의 프로세스 하나로 실행한다. HTTPS 프록시·VM 검증은 C-07-04와 이어 간다. 로컬 Channels·Daphne 시험은 대상 VM 호환 확정이나 실제 Mongo 성능 증빙을 대신하지 않는다.

P-29에 따라 `hello`를 연결당 한 번 받는다. `dropped_by_reason`의 `queue_full`과 `page_exit`는 각각 0 이상 정수이며 합계가 `dropped`와 같아야 한다. 누락·합계 불일치·알 수 없는 사유·중복 보고는 `bad_message`로 응답하고 집계하지 않는다. 지표는 `paldo_ad_beacon_dropped_total{reason}` 하나를 사용한다. `rate_limited`는 서버가 비콘을 빈도 제한으로 거절한 때만 더한다. [웹소켓 계약](../docs/contracts/api.md#7-웹소켓과-광고-중계-114-pm-결정-b-07-05)

## 광고 지면 (B-07-03)

지면 GET은 로그인·동의를 확인하고 저장된 광고 UUID만 `AdRequest.session_pseudonym`으로 보낸다. 로그인 ID·플레이어 가명·쿠키·요청 헤더는 광고 DTO에 넣지 않는다. `SLOT_SIZES`를 읽어 크기를 정하고 응답 이미지 경로를 그대로 사용한다. 외부 출처 이미지 응답은 빈 지면으로 처리한다. 광고 서버 내부 비콘·클릭 경로는 HTML에 넣지 않는다.

광고 응답은 `paldo_ad_fetch_total{result}`로 기록한다. `ok`, `empty`, `timeout`, `error`, `busy`, `circuit_open`을 구분하며 게임 명령 처리에서는 게이트웨이를 부르지 않는다. 게이트웨이는 B-07-05 조립을 사용하고 미연결이면 빈 지면을 반환한다. 운영 설정에 가짜 광고 제공자를 자동으로 연결하지 않는다. 소재가 없는 결과는 안내문·광고 표시·링크·토큰 없이 200 빈 HTML 조각을 반환한다. htmx는 자리의 내용을 비우며 204로 기존 내용을 남기지 않는다.

병합된 B-07-05의 웹소켓·클릭 중계를 사용한다. B-07-03은 `review_side` 광고 조각까지 검증하며 복기 화면 배치는 B-10-01 범위다. C 저장소·실제 광고 서버 연결은 별도 인수 검증 대상이다.

## 검증 경계

추궁 답변은 공개 발언의 종류가 `interrogate`이고 화자가 무당이 아닌 경우로 식별한다. 화면용 `SpeechVM.is_interrogation_answer`와 같은 판정 함수를 사용하며, 폴링 응답은 공개 발언의 발언 ID·작업 ID까지 대조한다. 11/8 PM 결정(B-08-02)에 따라 최초·폴링·완료·실패·취소 재조회에서 Kanana 표기를 제거했다. API 출력 DTO·원문·이벤트 본문과 작업 수명주기는 유지한다.

해석 문맥은 명시 인물 → 선택 인물 → 직전 대화 상대 순으로 해소한다. 직전 상대가 요청에 없으면 공개 발언 중 무당과 주고받은 마지막 캐묻기에서 활동 주민을 찾는다. 시도에는 선택 인물·근거와 해소한 직전 상대만 별도로 보존하고, 재입력에도 전달한다. 재입력 때 이미 활동 인원이 아닌 인물은 제외한다. 카드별 누락 슬롯·근거 후보가 있는 경우만 확인을 막으며 정상 후보는 독립적으로 선택할 수 있다.

자유 입력은 공개 맥락만 해석기에 전달하고 원문 연락처를 마스킹한 이벤트를 아웃박스에 저장한다. 해석·재입력·닫기는 게임 버전을 소비하지 않는다. 확인·수정만 하나의 명령으로 실행하고 오래된 카드 실행은 현재 회의 화면과 409를 반환한다. JSON과 htmx 폼은 같은 DTO 검증과 응용 서비스를 사용한다. 카드의 모호한 근거 선택지는 공개 주장과 해석기의 후보를 대조해 구성한다.

[해석기 조립](paldo_web/composition.py)은 프로세스에서 게임 서비스를 공유하기 전에 해석기를 한 번 생성하고 계측 래퍼를 붙인다. Django 설정 `INTENT_PARSER_FACTORY` 한 줄에 `intent.parser.BaselineIntentParser`를 지정하면 [D-07-01 인계](../intent/README.md)의 기준선을 사용한다. 빈 문자열이면 서비스 조립에서 주입한 해석기를 사용한다. 기준선 수신 시험은 Python 3.14.6·Django 6.1.2·scikit-learn 1.9.1에서 가짜 해석기와 같은 화면 계약을 확인했다. 실제 후보·모델 버전 기록과 상태 버전 유지도 대조했다. `paldo_intent_parse_duration_seconds{stage,status}` 히스토그램으로 p95를 계산한다.

명령 저장이 확인된 뒤 렌더 작업을 등록한다. 첫 화면은 저장한 폴백을 표시한다. 폴링 결과는 작업 ID·발언 ID로 연결하며 완료 뒤 화면 새로고침에도 완료 문장이 유지된다. 생성 대사는 회의의 발언 영역에만 적용하고 진술표는 공개 `Claim`에서 그린다. 단계 전환 때 미완료 작업을 취소하고 `render:<job_id>:<status>` 키로 최종 이벤트를 중복 없이 기록한다. A-07-03 운영 조립은 Mongo 보조 저장과 템플릿 렌더러를 연결하며, P-31 (나)에 따라 런타임 LLM을 호출하지 않는다. 배포 환경에서의 연결 확인은 통합 검증 범위다.

수첩·확신도는 `SaveNotebookInput`, 설문은 `SubmitSurveyInput`으로 검증한다. HTML 폼도 같은 숫자 범위·필수값·알 수 없는 필드 거부 규칙을 사용한다. 수첩과 설문은 게임 상태 버전을 올리지 않는다. 수첩 저장과 투표 확신도 저장은 각각 `notebook_updated`, 설문은 `survey_submitted` 이벤트를 `paldo.player` 아웃박스에 넣는다.

종료된 판의 설문은 [API 계약 2-2절](../docs/contracts/api.md#2-2-판-종료-설문-116-pm-결정-p-29-b-07-02)에 따라 한 번 기록한다. 응답은 `skipped=false`와 1~5점 세 개를 받는다. 기존 요청에서 `skipped`를 생략하면 false로 처리한다. 전체 건너뛰기는 `skipped=true`와 점수 셋 `null`, 빈 의견으로 기록한다. 같은 요청의 재전송은 204와 이벤트 추가 0건, 내용이나 건너뜀 여부가 바뀐 요청은 409다. 점수와 건너뜀 상태를 섞은 요청은 400이다.

자유 의견은 마스킹한 뒤 저장하고 `mask_version`을 이벤트에 담는다. 마스킹 결과가 같아도 다른 원문을 구분할 수 있도록 판별 HMAC(서버 비밀키로 만든 비교값)을 보조 설문 기록에 둔다. 이벤트와 응답에는 이 비교값을 넣지 않는다. 이전 기록에 `skipped`가 없으면 일반 응답으로 해석하고, 비교값이 없는 이전 기록은 저장된 마스킹 결과를 기준으로 비교한다.

### B-07-02 인수·계약 확인

확신도 화면의 5단계 버튼은 0·25·50·75·100을 보낸다. API의 0~100 정수 허용은 유지하고, 기존 비단계 값은 변경 없이 표시한다.

수첩의 동일 값 재전송은 같은 날짜·단계 안에서만 생략한다. 다음 날 투표나 본투표→결선에서는 값이 같아도 새 이벤트를 기록한다. 중복 비교용 `_saved_context`(`day`, `phase`)는 `InteractionStore`의 수첩 기록에만 두고 이벤트 본문·화면 DTO에는 넣지 않는다. 이전 기록에 이 값이 없으면 첫 저장을 새 기록으로 처리한다. A-07-03이 추가한 영속 보조 저장과의 통합에서도 이 메타데이터의 보존을 확인한다.

- B 응용은 `edit_effects`에 `participant:notebook`·`participant:survey`의 마지막 저장 계획을 먼저 보존한다. 계획에는 마스킹된 저장 값·기존 형식의 이벤트 봉투·고정 중복 방지 키만 둔다. 그다음 C의 `append_events`로 이벤트를 저장하고 보조 상태를 반영한다. 두 문서의 공통 트랜잭션을 가정하지 않는다.
- append 또는 보조 상태 저장의 응답이 유실돼도 계획은 보조 상태 롤백과 독립적으로 남는다. `participant_records`는 쓰기·공개 화면 조회 전에 같은 이벤트 키로 미완료 저장을 복구한다. 복구한 값이 이미 반영됐으면 이벤트를 다시 추가하지 않는다. 마지막 계획은 덮어쓸 때까지 유지한다. 다른 값으로 수첩을 다시 저장하면 새 계획·키를 만들므로 A→B→A도 세 번 기록한다.
- 설문은 최초 계획을 복구한 뒤 입력을 비교한다. 같은 응답·건너뜀은 204, 다른 내용은 409이며 첫 이벤트와 저장 값이 바뀌지 않는다. 원문 의견 대신 마스킹된 의견과 내부 비교용 digest만 보존한다. 계획·digest·`_saved_context`는 화면 DTO와 이벤트 본문에 넣지 않는다.
- B의 `WebMongoGameRepository.append_events`는 PyMongo 연결 예외만 기본 `ConnectionError`로 바꾼다. 참가자 저장·복구 중에는 공개 503으로 반환하고, 다음 조회·재요청이 복구를 이어 간다. 엔진을 다시 호출하거나 게임 상태 버전을 소비하지 않는다.
- 실제 Mongo 보존·새 Python 프로세스 재시작·두 프로세스 경합과 C 발행기를 통한 TLS Kafka 수신을 [B-07-02 증빙](../docs/evidence/B-07-02.md)에 기록한다. Kafka 발행은 at-least-once이며 같은 `event_id` 재전송은 C 소비자 중복 제거로 처리한다. 단일 로컬 TLS 브로커 시험은 VM 3브로커 장애·복제·Spark 적재 판정을 대신하지 않는다. [이벤트 계약](../docs/contracts/events.md)

계정 기능은 격리 MySQL에서 검증했다. 고정 판 배정은 실제 엔진과 녹화 엔진으로 시험하고, B 회차 저장·광고 가명 대응표는 [로컬 Mongo 시험](tests/README.md)으로 확인한다. B-06-03의 게임·진척·콘텐츠·회차 연결은 임시 Replica Set과 실제 엔진·HTTP·Daphne 재기동으로 확인했다. VM 계정 DB와 실제 광고 요청은 별도 통합 환경에서 확인한다.

## B-06-03 Mongo 실행 자원 조립

`WebMongoGameRepository`는 C 저장소의 commit에서 나온 PyMongo `ConnectionFailure` 계열만 기본 `ConnectionError`로 변환한다. `AutoReconnect`·`NetworkTimeout`도 포함한다. B 응용의 기존 계약대로 같은 인자로 한 번만 재시도하며 엔진을 다시 실행하지 않는다. 첫 저장이 성공했다면 두 번째 CAS의 `VersionConflict` 뒤 저장 응답을 `200·replayed=true`로 돌려준다. 권한·입력·실행 제한 오류는 변환하지 않는다. 드라이버 내부의 자동 재시도와 B 응용의 1회 재시도는 별개다.

`paldo_web/mongo.py`의 `open_mongo_runtime(engine=..., suspicion=..., uri=None)`이 C의 게임·진척·콘텐츠 저장소와 B의 회차 정책을 연결한다. URI를 생략하면 기존 `PALDO_MONGO_URI` 설정을 읽고 DB 경로가 없으면 `paldo_web`을 사용한다. 기본 컬렉션은 `games`, `progress`, `content`, `b_test_sessions`, `b_ad_identities`다. 같은 클라이언트를 공유하며 majority read/write concern을 사용한다. 기존 B 회차·광고 컬렉션 이름과 스키마는 바꾸지 않는다. 기존 데이터의 재생성·마이그레이션은 없다.

엔진·의심 모델은 호스트 조립에서 명시적으로 주입한다. `engine.testing`·메모리 게임 저장소를 자동 대체로 연결하지 않는다. 모델을 `None`으로 명시하면 실제 엔진의 규칙 투표 경로를 사용한다. 시작 시 Replica Set을 확인하며 미설정·Standalone·접속 실패는 조립을 거부한다. 예외 메시지에 URI·인증 값을 넣지 않는다. 콘텐츠는 미리 적재한 정확한 `meta.content_version`으로 읽고 최신 버전으로 바꾸지 않는다. 미적재 버전으로 시작하면 내부 KeyError를 노출하지 않고 503 서비스 오류로 반환한다.

반환 자원의 `configure()`는 HTTP 처리 전에 게임·회차 서비스를 함께 설치한다. `prepare_start`는 이 자원의 회차 저장소와 게임 조회 함수에 고정해 전역 서비스 교체로 다른 연결이 섞이지 않게 한다. 요청 처리가 끝난 뒤 `close()`로 클라이언트를 닫는다. 기존 `PALDO_GAME_SERVICE_FACTORY`의 함수에서는 `runtime.factory_service()`를 반환한다. 이 경로는 게임 전역 잠금을 다시 잡지 않고 같은 회차 서비스를 등록한다. `configure()`는 요청 처리 전 명시적 설치 경로에 사용한다.

B-06-03은 고정 회차·가명·게임 저장 연결 범위다. 이 실행 자원 자체는 `InteractionStore`·해석기·렌더러를 주입하지 않는다. A-07-03의 `server.infra.game_factory.build_game_service`가 그 위에 실제 엔진·규칙 의심도 기반 가짜 의심 모델·기준선 해석기·템플릿 렌더러와 영속 `b_interactions`를 연결한다. B-06-02 부하는 이 운영 팩토리를 사용하지 않고 녹화 엔진과 정확한 5개 시험 컬렉션만 사용한다. Kafka 발행·수신과 VM 통합은 별도다. 테스트의 단서 추가는 진척 포트의 보존 확인이며 E-09-08의 자동 해금 로직 검증이 아니다.

실제 시험은 고유 `collection_prefix`를 사용해 5개 컬렉션을 분리하고 그 접두어의 컬렉션만 삭제한다. 운영은 기본 접두어를 사용한다. 로컬 MongoDB 8.3.7 단일 노드 Replica Set에서 확인했으며, C의 MongoDB 9.0.4 VM 저장소 시험과 B의 로컬 통합 시험을 구분한다. 로컬 Compose 부하는 B-06-02에서 확인했다. VM·ASGI 비교는 B-07-05, 전체 통합 판정은 PM이 맡고 실패는 원래 구현 태스크에서 보완한다(B-07-04 취소, 11/7 결정).

## B-06-03 완료 조건 재확인

가명·동의·고정 회차·광고 가명 대응표는 기존 계정/회차/Mongo 조립으로 처리한다. 최신 dev에서 실제 Mongo 8개와 격리 MySQL 서버 156개 회귀를 통과했다. 운영 조립과 PM의 브라우저 재시작 판정은 병합됐으며 전체 통합 미완료를 이 기능의 미구현으로 표시하지 않는다. [완료 근거](../docs/evidence/B-06-03.md). 실제 광고 요청 검증과 VM 성능은 해당 후속 태스크 범위다.

## B-06-04 광고 식별자 검증

광고 지면 요청은 `ensure_ad_identity`로 얻은 광고 UUID만 `AdRequest.session_pseudonym`에 넣는다. 인증 입력·계정 가명·세션 쿠키·판 ID는 광고 DTO에 넣지 않는다. 계정 회귀 시험이 가입부터 판 종료·인증 실패까지의 파일 로그·이벤트·지표·광고 포트를 함께 검사한다. HTTP 클라이언트는 B-08-03에서 구현했고 광고 서버 실제 수신 검증은 D 인수 후 범위다. 이번 테스트 대역을 운영 조립에 사용하지 않는다. [검증 범위](../docs/evidence/B-06-04.md).

## B-08-01 결과·진척·시작 선택

결과 화면은 `PlayerView.result`의 승패·종료 사유·날짜·중단 여부와 기존 공개 감금 기록을 사용한다. 복기 DTO의 역할·비밀을 가져오지 않는다. 일반 판·고정 회차의 시작 폼은 기존 `StartGameInput.ending_choice`를 전달한다. 응용이 본인 진척의 `endings_unlocked`를 검사해 잠긴 선택을 400으로 거부하고, 메타에 선택값을 고정한다. 일반 판의 같은 시작 UUID와 같은 고정 판 재요청은 처음 저장한 결말·초상을 유지한다. 최신 공개 프리셋 파일·서버 랜덤 시드·명령 응답 유실 복구·Kanana 표기 제거는 유지한다.

`story_view.py`는 B의 `server/story_catalog.json`에서 요청한 콘텐츠 버전의 단서·결말 공개 문안을 읽는다. 판은 `GameMeta.content_version`, 진척은 `PlayerProgress.content_version`으로 고른다. 버전이 비어 있을 때만 현재 E 묶음의 버전을 사용한다. 보관본은 E 원문의 단서 ID·문장과 결말 ID·제목·문장만 복사하며 획득 조건은 넣지 않는다. 진척에는 수집한 단서만 전달하고 마을 승리·정상 종료에만 선택 결말 원문을 표시한다. 콘텐츠 파일을 갱신해도 이전 버전 보관본을 읽으므로 기존 판·진척의 문안은 유지된다. 알 수 없는 버전은 다른 버전 문안으로 대체하지 않는다.

배포 절차: E가 버전을 올린 단서·결말을 제공하면 B가 같은 버전 키의 보관본을 추가하고 `test_packaged_catalog_matches_current_authored_public_text`를 통과시킨다. 기존 버전 키와 문안은 삭제·덮어쓰지 않는다. 문안 수정도 새 콘텐츠 버전으로 추가한다. 이 보관본은 웹 표시용이며 엔진의 ContentSource·C 저장소·공통 DTO는 변경하지 않는다. 운영과 시험은 같은 보관본을 쓰며 시험용 새 버전은 실행 중 대역으로만 주입한다.

### E·PM 인수 및 확정 필요: 선택형 도전

B-08-01은 도전 옵션 선택을 요구하지만 도전 3종의 구현·300판 공개 판정은 E-09-08이다. 현재 `StartGameInput`·`GameMeta`에는 도전 필드가 없고 공개된 도전 프리셋 ID도 없다. 기획서 v1.3 3.6은 검증된 프리셋만 제공하도록 한다. B가 규칙·ID·전송 형식을 임의로 추가하지 않는다. 화면은 준비 중인 도전 3종을 비활성으로 표시하고, 알 수 없는 도전 입력은 기존 엄격한 검증으로 400을 반환한다. 이는 선택 기능 완료가 아니다.

PM·E가 도전별 식별자, 기존 프리셋으로 선택할지 별도 DTO·메타 필드로 받을지, 공개 판정 결과와 고정 테스트 회차에서 허용할지 확정해야 한다. 권장 방향은 E의 검증 결과와 옵션 계약을 먼저 공유하고 B가 선택 UI·요청·재조회 보존 시험을 연결하는 것이다. 그 전에는 Refs로만 제출하고 완료로 닫지 않는다. 진척 화면은 가짜 `ProgressRepository`로 검증하며 실제 해금·원천 이벤트 재처리는 E-09-08·C 인수 후 INT-09 11번에서 확인한다.

## B-08-03 내부 광고 HTTP 연결

환경의 PALDO_ADS_INTERNAL_URL을 settings.ADS_INTERNAL_URL로 읽는다. get_ad_gateway는 명시적 주입을 우선하고, 설정이 있으면 HTTPAdProvider → AdGateway를 한 번 조립한다. 미설정·잘못된 출처는 미연결로 처리해 기존 빈 지면·홈 복귀·돌아가기 안내를 유지한다. 호스트가 .env 값을 프로세스 환경에 주입하며 저장소에 실제 접속값을 넣지 않는다.

운영 어댑터 server/infra/ad_client.py는 serve·impression·click·landing 네 계약 경로만 호출한다. JSON은 공통 DTO로 직렬화하고 응답 DTO의 타입·요청 ID를 검사한다. 클릭의 302는 따라가지 않고 가상 랜딩 상대 경로만 받는다. HTTP 자동 재시도·환경 프록시·브라우저 Cookie/Authorization/User-Agent/Referer/X-Forwarded-For 전달은 없다. 필요한 Host·본문 길이 등 HTTP 프레이밍 외 응용 헤더는 X-Request-ID와 JSON Content-Type만 새로 만든다. 랜딩 HTML은 계약대로 중계하고 소재 이미지는 기존 게임 정적 경로 검증을 거친다.

AdGateway의 연결 100ms·전체 300ms·serve/중계 별도 동시 상한 8·공유 회로 차단(5회 실패→30초 생략)을 유지한다. 어댑터도 연결 이후 남은 전체 시간의 socket 마감으로 느린 헤더·본문을 중단한다. OS 이름 해석·스케줄링의 실제 시간은 배치 환경에서 확인해야 한다. 응답은 최대 1MiB로 제한하고 잘못된 응답은 Gateway가 error/timeout과 빈 결과로 정규화한다. 게임 시작·명령은 광고를 호출하지 않는다.

클릭 실패의 홈 복귀는 실제로 홈을 조회하므로 추가 Mongo 부하가 생긴다. accounts/views.py는 홈 한 요청 안에서 진척을 한 번만 읽어 결말 선택과 이어 하기에 함께 쓰고, 이어 하기·회차 목록이 읽는 같은 판은 요청 내부 사전으로 재사용한다. 요청을 넘는 캐시는 없으며 다음 홈 요청은 다시 읽는다. 상태·소유권·시작 UUID·회차/결말 표시와 홈 복귀 경로는 유지한다. 관련 HTTP 회귀 70건에서 재조회 횟수와 기존 화면을 확인했다.

### D 인수·실제 배치 검증 대기

- D-08-02: 실행 가능한 광고 서버의 기준 SHA, 내부 출처·포트, serve/중계 경로, 지면 3종용 소재·정적 이미지 적재, 캠페인·정책·CTR 준비 상태, 정상 serve_token과 광고 측 serve_id/request_id 조회 방법을 받는다. B에 서명 키나 광고 DB 인증을 넘길 필요는 없다.
- 실제 serve→노출→클릭을 같은 serve_id로 연결한 웹·광고 로그 각 1줄이 필요하다. 지금 B는 광고 토큰을 해독하거나 새 공개 DTO 필드를 만들지 않는다. 광고 서버가 기록한 serve_id와 request_id 대응을 인수 후 대조한다.
- D와 장애 주입 방법·복구 절차를 정한 뒤 정상 기준선과 중단·무응답·3초 지연·오류 응답을 각각 5분 측정한다. 같은 부하에서 게임 p95 증가 ≤50ms·오류율 증가 0, 비콘/클릭 실패 격리와 회로 지표를 확인한다. D에 새 장애 제어 API를 요구하지 않는다.
- app-01/ad-01 실제 배치에서는 브라우저의 광고 출처 직접 요청 0건, 네 내부 호출의 X-Request-ID 로그 대응, B-06-04의 계정 정보 비노출을 재확인한다. 현재 loopback 대역으로 이 조건들을 완료 처리하지 않는다.

시험은 server/tests/ad_http_host.py의 B 전용 HTTP 대역과 tools/perf/ad_fault_test.py → server/tests/ad_fault_bench.py → 기존 api_bench의 게임 부하·Daphne·격리 Mongo 경로를 쓴다. 임시 계정 DB·시험 컬렉션을 만들고 자기 자원만 정리한다. 부하용 HTTP 제공자는 시험 조립에서만 load_test=True를 강제한다. 운영 설정은 시험 서버·계정·장애 스위치를 import하지 않는다.
