# 서버 설계

## 계층과 저장소

`api/`는 HTTP 입력을 검증하고 응답을 만든다. `app/`은 판 시작과 명령 실행을 조정한다. 게임 상태와 진행 저장소는 [게임 서비스 조립 경계](paldo_web/composition.py)에 주입한다. 계정 저장소는 Django의 `default` MySQL이며, 접속값은 `PALDO_AUTH_DB_*`로 받는다.

## 계정과 세션

가입 시 로그인 ID를 정규화하고 비밀번호 해시, UUID 가명 ID, 동의 시각을 저장한다. 초대 코드가 설정된 경우에만 가입할 때 검증한다. 일반·관리자 로그인은 같은 잠금 규칙을 쓰며, 로그인 성공 시 세션 ID를 교체한다.

게임 API는 인증된 계정의 가명 ID로 판과 하위 자원의 소유권을 확인한다. 로그인 ID와 비밀번호 해시는 계정 DB에만 저장하며, 인증 로그에는 결과와 확인된 계정의 가명 ID를 쓴다.

## 테스트 회차

판 시작 응답은 htmx 헤더를 확인해 회의 조각을 반환한다. 일반 HTML 폼은 판 조회 화면으로 이동하며, JSON 응답은 게임 DTO를 사용한다.

활성 운영자(`is_staff`)가 회차 ID, 순서 있는 고정 판 목록, 참가자 가명, 규칙·엔진·콘텐츠 버전을 등록한다. 회차 ID는 유일하며 이미 등록한 구성은 덮어쓰지 않는다. 참가자의 첫 미종료 판이 다음 차례다. 시작 요청은 가입 때 발급된 가명으로 참가 배정과 동의를 확인한다. 같은 회차·참가자·순번은 같은 판 ID를 사용한다. 시작 이벤트에는 `source=human`, `session_id`, `player_pseudonym`이 들어간다.

[B 회차 저장소](infra/test_sessions.py)는 `PALDO_MONGO_URI`의 DB(경로 생략 시 `paldo_web`)에 `b_test_sessions`와 `b_ad_identities`를 둔다. 게임 상태·진척은 기존 게임 포트를 사용한다. 회차 저장소를 사용할 수 없으면 운영자 화면과 회차 판 시작은 503을 반환한다.

후속 광고 연동은 [서버 가명 발급 함수](api/sessions.py)에서 로그인 세션별 광고 UUID를 받는다. 대응표에는 플레이어 가명과 광고 UUID, 로그인 세션을 HMAC으로 변환한 내부 키를 둔다. C-09-02는 `ad_identities(player)`로 광고 기록을 찾고, 광고 기록을 삭제한 뒤 `delete_player(player)`로 대응표와 회차 참가 배정을 제거한다.

## 광고 신호와 ASGI

[ASGI 진입점](paldo_web/asgi.py)은 HTTP를 Django에, `/ws/game/`을 전체 출처 검사와 Django 세션 인증 뒤 Consumer에 보낸다. 허용 출처는 `PALDO_PUBLIC_ORIGIN` 하나다. 비로그인은 수락 직후 4401로 닫고, 매 비콘 전에 DB에서 세션·사용자·인증 해시를 새로 읽어 로그아웃·만료·비밀번호 변경을 확인한다. 크기 제한은 UTF-8 바이트 기준 4,096이며 초당 비콘 5개를 넘으면 연결을 유지하고 거부한다.

Consumer는 검증과 응답만 맡는다. 중계는 `ad_events` → `AdGateway` → `AdProvider` 순서이며 `sync_to_async(thread_sensitive=False)`로 동기 호출을 이벤트 루프 밖에서 실행한다. serve와 중계의 호출 상한은 각각 8이고 회로 차단기는 공유한다. 전체 300ms·연결 100ms, 재시도 없음 규칙을 유지한다. HTTP 클릭은 같은 출처 `/ads/landing/<id>`만 허용하며 실패하면 `/`로 이동한다.

광고 제공자는 `configure_ad_gateway`로 명시적으로 주입한다. 운영에서 가짜로 자동 대체하지 않는다. 미조립 상태는 비콘 실패 응답과 HTTP 대체 화면으로 처리한다. 참가자 헤더나 요청 객체는 포트 인자에 전달하지 않는다. 실제 HTTP 클라이언트의 헤더 검증은 B-08-03에서 이어 간다.

`InMemoryChannelLayer`를 사용하므로 Daphne는 루프백 주소의 프로세스 하나로 실행한다. HTTPS 프록시·VM 검증은 C-07-04와 이어 간다. 로컬 Channels·Daphne 시험은 대상 VM 호환 확정이나 실제 Mongo 성능 증빙을 대신하지 않는다.

P-29에 따라 `hello`를 연결당 한 번 받는다. `dropped_by_reason`의 `queue_full`과 `page_exit`는 각각 0 이상 정수이며 합계가 `dropped`와 같아야 한다. 누락·합계 불일치·알 수 없는 사유·중복 보고는 `bad_message`로 응답하고 집계하지 않는다. 지표는 `paldo_ad_beacon_dropped_total{reason}` 하나를 사용한다. `rate_limited`는 서버가 비콘을 빈도 제한으로 거절한 때만 더한다. [웹소켓 계약](../docs/contracts/api.md#7-웹소켓과-광고-중계-114-pm-결정-b-07-05)

## 광고 지면 (B-07-03)

지면 GET은 로그인·동의를 확인하고 저장된 광고 UUID만 `AdRequest.session_pseudonym`으로 보낸다. 로그인 ID·플레이어 가명·쿠키·요청 헤더는 광고 DTO에 넣지 않는다. `SLOT_SIZES`를 읽어 크기를 정하고 응답 이미지 경로를 그대로 사용한다. 외부 출처 이미지 응답은 빈 지면으로 처리한다. 광고 서버 내부 비콘·클릭 경로는 HTML에 넣지 않는다.

광고 응답은 `paldo_ad_fetch_total{result}`로 기록한다. `ok`, `empty`, `timeout`, `error`, `busy`, `circuit_open`을 구분하며 게임 명령 처리에서는 게이트웨이를 부르지 않는다. 게이트웨이는 B-07-05 조립을 사용하고 미연결이면 빈 지면을 반환한다. 운영 설정에 가짜 광고 제공자를 자동으로 연결하지 않는다. 소재가 없는 결과는 안내문·광고 표시·링크·토큰 없이 200 빈 HTML 조각을 반환한다. htmx는 자리의 내용을 비우며 204로 기존 내용을 남기지 않는다.

병합된 B-07-05의 웹소켓·클릭 중계를 사용한다. B-07-03은 `review_side` 광고 조각까지 검증하며 복기 화면 배치는 B-10-01 범위다. C 저장소·실제 광고 서버 연결은 별도 인수 검증 대상이다.

## 검증 경계

추궁 답변은 공개 발언의 종류가 `interrogate`이고 화자가 무당이 아닌 경우로 식별한다. 화면용 `SpeechVM.is_interrogation_answer`와 같은 판정 함수를 사용하며, 폴링 응답은 공개 발언의 발언 ID·작업 ID까지 대조한다. 최초 폴백, 모든 렌더 상태, 완료 후 재조회에서 답변 아래 `Powered by Kanana`를 표시한다. 표시 정보는 화면 모델에만 추가하며 API 출력 DTO·원문·이벤트 본문은 바꾸지 않는다.

해석 문맥은 명시 인물 → 선택 인물 → 직전 대화 상대 순으로 해소한다. 직전 상대가 요청에 없으면 공개 발언 중 무당과 주고받은 마지막 캐묻기에서 활동 주민을 찾는다. 시도에는 선택 인물·근거와 해소한 직전 상대만 별도로 보존하고, 재입력에도 전달한다. 재입력 때 이미 활동 인원이 아닌 인물은 제외한다. 카드별 누락 슬롯·근거 후보가 있는 경우만 확인을 막으며 정상 후보는 독립적으로 선택할 수 있다.

자유 입력은 공개 맥락만 해석기에 전달하고 원문 연락처를 마스킹한 이벤트를 아웃박스에 저장한다. 해석·재입력·닫기는 게임 버전을 소비하지 않는다. 확인·수정만 하나의 명령으로 실행하고 오래된 카드 실행은 현재 회의 화면과 409를 반환한다. JSON과 htmx 폼은 같은 DTO 검증과 응용 서비스를 사용한다. 카드의 모호한 근거 선택지는 공개 주장과 해석기의 후보를 대조해 구성한다.

[해석기 조립](paldo_web/composition.py)은 프로세스에서 게임 서비스를 공유하기 전에 해석기를 한 번 생성하고 계측 래퍼를 붙인다. Django 설정 `INTENT_PARSER_FACTORY` 한 줄에 `intent.parser.BaselineIntentParser`를 지정하면 [D-07-01 인계](../intent/README.md)의 기준선을 사용한다. 빈 문자열이면 서비스 조립에서 주입한 해석기를 사용한다. 기준선 수신 시험은 Python 3.14.6·Django 6.1.2·scikit-learn 1.9.1에서 가짜 해석기와 같은 화면 계약을 확인했다. 실제 후보·모델 버전 기록과 상태 버전 유지도 대조했다. `paldo_intent_parse_duration_seconds{stage,status}` 히스토그램으로 p95를 계산한다.

명령 저장이 확인된 뒤 렌더 작업을 등록한다. 첫 화면은 저장한 폴백을 표시한다. 폴링 결과는 작업 ID·발언 ID로 연결하며 완료 뒤 화면 새로고침에도 완료 문장이 유지된다. 생성 대사는 회의의 발언 영역에만 적용하고 진술표는 공개 `Claim`에서 그린다. 단계 전환 때 미완료 작업을 취소하고 `render:<job_id>:<status>` 키로 최종 이벤트를 중복 없이 기록한다. C 게임·보조 저장소와 실제 LLM 렌더러의 배포 연결은 각각 인수·INT-09 검증 대상이다.

수첩·확신도는 `SaveNotebookInput`, 설문은 `SubmitSurveyInput`으로 검증한다. HTML 폼도 같은 숫자 범위·필수값·알 수 없는 필드 거부 규칙을 사용한다. 수첩과 설문은 게임 상태 버전을 올리지 않는다. 수첩 저장과 투표 확신도 저장은 각각 `notebook_updated`, 설문은 `survey_submitted` 이벤트를 `paldo.player` 아웃박스에 넣는다.

종료된 판의 설문은 [API 계약 2-2절](../docs/contracts/api.md#2-2-판-종료-설문-116-pm-결정-p-29-b-07-02)에 따라 한 번 기록한다. 응답은 `skipped=false`와 1~5점 세 개를 받는다. 기존 요청에서 `skipped`를 생략하면 false로 처리한다. 전체 건너뛰기는 `skipped=true`와 점수 셋 `null`, 빈 의견으로 기록한다. 같은 요청의 재전송은 204와 이벤트 추가 0건, 내용이나 건너뜀 여부가 바뀐 요청은 409다. 점수와 건너뜀 상태를 섞은 요청은 400이다.

자유 의견은 마스킹한 뒤 저장하고 `mask_version`을 이벤트에 담는다. 마스킹 결과가 같아도 다른 원문을 구분할 수 있도록 판별 HMAC(서버 비밀키로 만든 비교값)을 보조 설문 기록에 둔다. 이벤트와 응답에는 이 비교값을 넣지 않는다. 이전 기록에 `skipped`가 없으면 일반 응답으로 해석하고, 비교값이 없는 이전 기록은 저장된 마스킹 결과를 기준으로 비교한다.

### B-07-02 인수·계약 확인

수첩의 동일 값 재전송은 같은 날짜·단계 안에서만 생략한다. 다음 날 투표나 본투표→결선에서는 값이 같아도 새 이벤트를 기록한다. 중복 비교용 `_saved_context`(`day`, `phase`)는 `InteractionStore`의 수첩 기록에만 두고 이벤트 본문·화면 DTO에는 넣지 않는다. 이전 기록에 이 값이 없으면 첫 저장을 새 기록으로 처리한다. C 보조 저장소 인수 시 이 메타데이터의 보존도 확인한다.

- 메모리 아웃박스로 건너뜀의 점수 세 개가 `null`이고 이벤트가 한 건임을 확인했다. C-06-01 게임 저장소·보조 `InteractionStore`와 C-06-02 발행기를 인수한 뒤 실제 Mongo 재조회·재시작, 저장 응답 유실 시 중복 방지, Kafka `paldo.player`의 `null` 보존을 확인한다. [이벤트 계약](../docs/contracts/events.md)

계정 기능은 격리 MySQL에서 검증했다. 고정 판 배정은 실제 엔진과 녹화 엔진으로 시험하고, B 회차 저장·광고 가명 대응표는 [로컬 Mongo 시험](tests/README.md)으로 확인한다. C의 게임·진척 저장소를 연결한 운영 판, VM 계정 DB, 실제 광고 요청은 통합 환경에서 확인한다.
