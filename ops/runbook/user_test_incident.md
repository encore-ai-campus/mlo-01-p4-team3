# 사용자 테스트 웹 장애 대처

사전 테스트(11/8)와 정식 테스트(11/10 13:00~18:00, 11/8 일정 변경) 도중 게임 웹이 응답하지 않을 때의 순서다. 일정은 [사용자 테스트 계획](../../docs/user_test/plan.md), 서버 기동·종료 명령은 [`ops/proxy/README.md`](../proxy/README.md)를 따른다. 접속 주소·서버 계정은 저장소에 쓰지 않는다.

장애 기준(재시작 대기·중단 기준)은 11/8 사용자 결정으로 정했다(3절). 재시작이 실패했을 때의 다음 단계는 아직 "미정"이다.

## 1. 역할

| 역할 | 담당 | 근거 |
|---|---|---|
| 현장 진행·참가자 안내·장애 판정·중단 결정 | E | E-09-01(정식 테스트 운영) |
| 서버 상태 확인·재시작(Caddy·`paldo-web` systemd unit, Mongo·계정 MySQL) | C | C-07-04 운영 인계(`ops/proxy/README.md`). 가장 몰리는 첫 시간 11/10 13:00~14:00 대기는 [C-09-05](../../docs/tasks/C_infra.md)(11/8 결정). 그 밖의 시간에는 E가 연락해 C가 원격으로 확인한다 |
| 테스트 중 버그 분류·재현·수정 | B | B-09-03 |

## 2. 장애 판정

다음 중 하나면 장애로 본다.
- 참가자 여러 명이 같은 시각에 접속 실패, 5xx 화면, 무한 로딩을 보고한다.
- 운영자 브라우저에서도 홈이 열리지 않거나, 개발자 도구 Network에서 `/ws/game/`이 101이 아니다(C-07-04 참가자 안내의 운영자 확인 항목).

한 명만 겪는 문제는 장애가 아니라 개별 대응이다: 새로고침 → 다시 로그인 → 다른 브라우저(최신 Chrome·Edge) 순으로 해 보고, 그래도 안 되면 B에 재현 절차를 넘긴다(B-09-03).

광고 지면만 비거나 "광고 없음"으로 보이는 것은 장애가 아니다. 광고 서버가 실패하면 게임은 광고 없이 계속된다(`AdGateway` 폴백, INT-09 #9). 이 경우 시각만 기록한다.

## 3. 순서

1. **기록(E)**: 시작 시각, 증상, 보고한 인원 수. 가명 ID 외의 식별 정보는 적지 않는다.
2. **참가자 안내(E)**: 4절 문구를 화면이나 구두로 알린다.
3. **서버 확인(C)**: `sudo systemctl status caddy paldo-web`, `sudo journalctl -u caddy --since '10 minutes ago'`, 웹 unit 로그. Mongo·계정 MySQL 연결 오류가 있는지 확인한다.
4. **재시작(C)**: 원인이 웹 프로세스면 `ops/proxy/README.md`의 두 unit만 재시작한다. 다른 서비스는 건드리지 않는다. 웹은 Daphne 1개로 유지한다.
5. **복구 확인(E)**: 운영자 계정으로 홈 → 판 화면 → `/ws/game/` 101을 확인한 뒤 참가자에게 재개를 안내한다.
6. **사후 기록(E)**: 끝난 시각과 원인을 E-09-01 증빙(사전 테스트면 E-08-10)과 [트러블 E](../../docs/troubles/E.md)에 적는다. 지표를 집계할 때 장애 구간을 함께 보고한다.

장애 기준(11/8 사용자 결정):
- 판정에서 5분 안에 재시작한다(4번).
- 그날 장애 시간 합계가 20분을 넘으면 그 시간대의 대응을 끝낸다(E가 판정하고 참가자에게 알린다). 지표는 그때까지의 판으로 집계하고 장애 구간을 함께 보고한다.
- 18:00 클로즈는 미루지 않는다. 마감 시각 = 스냅숏이고 집계 도구 기본값이다(`--cutoff`).
- 테스트 중 서버 커밋은 바꾸지 않는다. `blocker` 수정 배포만 예외이고(승인 E), 바꾼 시각을 E-09-01 증빙에 적는다(계획서 4절 "SHA 유지").

## 4. 참가자 안내 문구

> 서버를 점검하고 있습니다. 지금까지 진행한 판은 저장되어 있습니다. 안내드리면 페이지를 새로고침하고, 로그아웃된 경우 다시 로그인한 뒤 홈에서 "이어 하기"를 눌러 주세요. 새 계정을 만들지 마세요.

새 계정을 만들면 진행 중이던 판을 이어 할 수 없고, 한 사람이 가명 두 개로 집계된다(사용자 단위 분할이 흐려진다, 계획서 6절).

## 5. 재접속·중복 제출·판 재개 (코드가 보장하는 범위)

| 상황 | 동작 | 근거 |
|---|---|---|
| 웹 재시작 뒤 로그인 | 세션은 계정 DB에 저장된다(Django 기본 세션 저장, 유효 기간 2주). 재시작만으로는 로그아웃되지 않는다 | `server/paldo_web/settings.py` |
| 진행 중인 판 재개 | 일반 판(E-08-14): 홈에서 진행 중인 판 "이어 하기"로 같은 판을 연다. 같은 시작 토큰(`start_token`)을 다시 보내면 새 판을 만들지 않고 같은 판을 돌려준다. 실험 회차 판(계획서 8절)은 판 ID가 가명 ID·회차 ID·순번으로 정해진다 | `server/app/open_start.py`, `server/app/test_sessions.py` `_next_plan`, `web/templates/accounts/home.html` |
| 장애 직전에 보낸 명령 | 명령은 `command_id`와 `expected_state_version`을 가진다. 같은 `command_id`를 다시 보내면 저장된 응답을 돌려준다(200, `replayed=true`). 이미 적용된 뒤 새로고침한 화면에서 다시 보내면 버전 충돌 409로 현재 화면을 받는다. 서버는 명령을 자동으로 다시 적용하지 않는다 | [api.md](../../docs/contracts/api.md) 3절 |
| 설문 다시 제출 | 같은 내용은 204이고 이벤트를 더 만들지 않는다. 다른 내용은 409 | api.md 2-2절 |
| 웹소켓 끊김 | 브라우저가 1·2·4·8·16·30초 간격으로, 그 뒤 30초마다 다시 연결한다. 닫힘 코드 4401이면 다시 연결하지 않고 다음 이동 때 로그인 화면으로 간다 | api.md 7절 끊김 처리 |

명령이 저장되기 전에 끊긴 경우 그 명령은 적용되지 않는다. 참가자는 재개한 화면에서 다시 고르면 된다.

## 6. 기록 보존

- 장애 중에도 판·계정을 지우거나 다시 만들지 않는다(실험 회차를 열었다면 회차도. 회차는 바꿀 수 없고 판 ID가 회차 ID에 묶여 있다).
- 콘텐츠를 다시 적재하지 않는다. 같은 버전은 적재되지 않으며, 새 버전을 넣어도 진행 중인 판은 판 메타의 버전을 그대로 쓴다.
- Mongo `games`·이벤트·계정 DB를 손으로 고치지 않는다. 집계는 [모듈 문서 `user_test`](../../docs/modules/user_test.md)의 방법으로만 한다.
