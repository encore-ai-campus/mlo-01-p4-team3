### LLM 자원 (노트북 3)

- 노트북마다 RAM 32GB에서 Windows 몫 약 6GB를 빼면 VM에 약 26GB를 쓸 수 있다. 기존 VM 4대 × 4GB = 16GB이므로 노트북당 여유는 약 10GB다.
- **LLM은 노트북 3에 둔다.** 사양이 모두 같으므로 VM 부하가 가장 가벼운 노트북 3이 맞다. mysql-03을 끄면 ad-01·lake-storage-01·mongo-03(각 2 vCPU·4GB, 합 12GB)만 남는다. 산술로는 LLM에 최대 약 12GB를 줄 수 있지만, VMware 오버헤드와 호스트 여유가 약 2GB만 남으므로 **12GB는 상한 후보**다. 모델 파일·컨텍스트 길이·동시 슬롯 수를 먼저 고정하고, 노트북 3의 광고·Lake·Mongo 부하를 함께 걸어 호스트와 게스트의 최대 메모리·페이지아웃을 측정해 배정량을 정한다("가장 가벼움"도 이 실측으로 확인한다).
- LLM 스레드는 **P코어 수(4)에 맞춰 4~6**으로 시작해 벤치마크로 정한다. VM으로 돌리면 vCPU 6을 상한으로 둔다.
- 생성 속도는 **실측 전 가설**이었다. 메모리 대역폭(이론 51.2GB/s)을 모델 크기로 나눈 단순 상한은 3~4B Q4(약 2~2.5GB) 초당 20~26토큰, 7~8B Q4(약 4.5~5GB) 초당 10~11토큰이다. 실효율을 절반 정도로 보면 각각 초당 10~15토큰, 5~8토큰이고, 대사 한 줄(약 60토큰) 생성에 4~6초, 8~12초다. 이것은 생성 시간만이며, 최종 판단은 전체 응답 p50·p95, 동시 요청, 장시간 부하 시험으로 한다. 3~4B급을 기본 후보로 하고, 7~8B는 복기·운영 분석처럼 기다려도 되는 작업에만 시험한다. 실측 결과는 `docs/reports/llm_bench.md`.
- 노트북 3의 담당자도 같은 노트북으로 개발한다. 그래서 LLM 자원을 시간대로 나눈다(시각은 `schedule.md`).
  - **개발 시간대**: llm-01은 작게(예: 1~2B 모델 또는 정지) 두고, 각 흐름은 가짜 LLM(`fixtures/llm`)으로 개발한다. 담당자의 IDE·브라우저·로컬 Compose가 RAM을 쓴다.
  - **통합·사용자 테스트·LLM 벤치 시간대**: 담당자는 개발 도구를 줄이고 llm-01에 확정 배정량을 준다.
  - 벤치는 담당자가 실제로 개발 도구를 띄운 상태와 비운 상태를 모두 측정한다.
- **자원 몰아주기**:
  - VM 자원은 같은 노트북 안에서만 옮길 수 있다. LLM 노트북의 다른 VM은 끄거나 다른 노트북으로 옮긴다.
  - 삭제 전에 먼저 끈다(CPU·RAM은 바로 풀리고 되돌릴 수 있다). 디스크 공간이 필요할 때만 스냅샷과 함께 삭제한다.
  - LLM VM의 vCPU는 호스트 물리 코어 수를 넘기지 않는다(초과 할당은 오히려 느려진다).
  - 대안: 노트북 3의 Windows에서 llama.cpp를 직접 실행한다(가상화 오버헤드 없음). 벤치마크에서 VM 실행과 비교한다.

### 그 밖의 운영 원칙

- **디스크**: VM을 꺼도 디스크는 돌아오지 않고, 스냅샷 삭제는 병합 작업이라 시간과 추가 여유 공간이 필요하다. 노트북별 실제 여유 공간, VM별 할당·사용량, 스냅샷 구조를 확인한다. 모델 파일, Docker 이미지, 학습 체크포인트, MLflow 아티팩트, Kafka 로그(보존 1일), Delta 원본·재처리분의 보존량과 정리 기준을 정하고, 재학습·장애 복구 중 최대 동시 점유량으로 계산한다(아래 디스크 예산). 부족하면 모델·이미지·체크포인트 보관량을 먼저 점검한다. 사용 중인 media-storage-01이나 데이터 보존이 필요한 mysql-03을 임의 삭제하지 않는다.
- 노트북 4는 ML 학습(nifi-01)과 k3s 시뮬레이션(spark-worker-03)이 겹치지 않도록 실행 시간대를 나눈다.
- 사용자 테스트 중에는 llm-01(LLM)·ad-01(광고)·app-01(웹)에 학습 작업을 올리지 않는다. 학습·시뮬레이션은 nifi-01과 k3s 노드에서 돌린다.
- 설치 버전과 Python 기준은 `docs/contracts/tech_stack.md`가 원본이다.

## C-06-04 11/7 자원 결정 현황

기존 E-06-07 값은 CPU 잠정 결과다. RunPod는 11/7 사용자 의견으로 추가한 운영 후보이며 최종 확정·유료 자원 생성은 미실행이다. 상세 연결·검증·정지 절차는 [RunPod 후보 런북](runpod.md).

| 항목 | C-05-02 잠정 | E-06-07 CPU 결과 | RunPod 후보 |
|---|---|---|---|
| 모델 | 3~4B급 후보 비교 | Kanana-2-3B GGUF Q4_K_M 잠정 | E 모델·revision·GPU 호환 확인 대기 |
| 실행 | 신규 llm-01 VM 또는 Windows | Windows 직접 잠정 | 외부 GPU Pod의 E LLM 서비스, 미생성 |
| CPU·스레드 | 노트북 3 공유 | 8스레드 | 실배정·벤치 후 확정, CPU 결과 전용값 재사용 금지 |

C-06-04 완료를 위해 GPU·비용·시간 확정, 실제 평가 지연/메모리, B→E 렌더·취소 통합 검증과 자원표 갱신이 남았다. 기존 CPU안은 비교 근거로 보존하고 RunPod 결과로 덮어쓰지 않는다.
